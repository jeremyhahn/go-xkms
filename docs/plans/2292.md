# #2292: refresh re-check runs as the refresh token's own user

## Objective

On an embedded xkmsd node, refresh answered 401 after PIV or WebAuthn
login: the user re-check ran under the public route's identity-less context.
Ruling 953: the re-check runs as the validated refresh token's user, never
as the service principal, with no new grant and no access-check bypass.

## Slices

1. Plan. 2. test(auth) login_wiring_test.go: refresh after PIV login
   rotates (rbac off/on); a user disabled after login gets 401.
3. fix(auth): `QRDBUserResolver` binds the token's stored subject inside
   `ResolveUser` only. 4. Changelog fixed-2292-refresh-recheck-user.md.

## Status: unblocked without the go-qrdb seam (ruling 973)

The re-check reads the token's user through the embedded node's own user
service (`auth.NewNodeUserClient`, 05a76c661), wired on `Server.nodeUserSource`
and `apimodule.WithNodeUsers`; a remote-qrdb host keeps the qrdb client.

## PR #2296 Codex findings (DS-9556)

apimodule host forwards the service-context binder; node user adapter and
invite routes bind the trusted tenant; buildRESTConfig uses xkmsd's logger.

## Ruling 1029 (B): scope is system-tenant passkey login

PR #2296 is narrowed to passkey login in the tenant the relying party
serves (the system tenant on xkmsd). Codex P1s on head 0e2cacd39:

1. Invite store calls (create, lookup, redeem) run on a system context
   (`inviteStoreContext`); the user operations keep the invite's tenant.
   Test: pkg/server/webauthn_tenant_ceremony_test.go, full redemption over
   an RBAC-enforcing embedded node.
2. Invite enrolment for an account outside the RP's configured tenant is
   refused with `ErrInviteTenantNotServed` (REST 403), after the token is
   looked up (ruling 1041 (2)). Tests: servicer_invite_tenant_test.go,
   servicer_invite_unknown_tenant_test.go, handlers_invite_tenant_test.go.

## Ruling 1041 (review at a92290061)

1. `UserStore` carries `TenantID()`; `Service.UserStoreTenant` returns a
   typed `*UserStoreTenantUnsetError` for a store naming no tenant, never
   the system tenant. Test: pkg/webauthn/service_tenant_test.go.
2. An unknown invite answers the same error for any tenant.
3. The refresh-token store runs as the embedded node's service principal
   on public routes (login and registration finish carry no identity): its
   KV calls are bound to `Node.ServiceContext` (`token.WithCallContext`,
   #2287); the user calls of those routes go through the node user service.

Tenant-aware passkey login is a separate SPEC row. Out of scope:
pkg/embeddednode/serviceprincipal/ (the grant) stays unchanged.
