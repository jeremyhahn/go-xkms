# GO-2026-6911: mcp-go streamable HTTP client follows Location

## Cause

mcp-go v1.3.0's `client/transport.StreamableHTTP` follows a redirect's
`Location` header and resends the request, bearer token and extra headers
to the new origin (SSRF + credential leak). No fixed mcp-go release exists.

## Traces (govulncheck, 2026-11-20)

1. `pkg/acme/api/swagger/swagger.go:281` AssetHandler -> http.HandlerFunc
   -> go-qrdb `pkg/api/mcp` boundedBodyHandler -> mcp-go server ->
   go-qrdb `replica_forward.go:251` forwardToLeader ->
   `client.NewStreamableHttpClient` -> `transport.NewStreamableHTTP`.
2. `pkg/mcptool/client.go` Connect -> mcp-go `client.Client.Start` /
   `Initialize` and Close -> `client.Client.Close` -> `StreamableHTTP.*`.

Trace 2 exists although Connect already hands mcp-go's `client.Client` the
go-xkms transport (`pkg/mcptool/streamable.go`, never follows a redirect,
#2081): `client.Client` calls its transport through an interface, and
go-qrdb puts a `transport.StreamableHTTP` into the same field type, so the
call graph resolves every `client.Client` method to the vulnerable one.

## Fix (slices, in order)

1. test: `pkg/mcptool` guard test that no non-test file imports mcp-go's
   `client` package or names `transport.(New)StreamableHTTP`; redirect test
   on a tools/call after a good handshake (bearer + extra headers never
   reach the redirect target). The guard fails before the fix.
2. fix: `pkg/mcptool` drives the MCP handshake (server/discover, legacy
   initialize fallback, notifications/initialized) and tools/call itself on
   the go-xkms transport (`streamSession`). `NewClientWithSession` takes a
   `Session` interface (CallTool + Close) so in-process tests keep passing
   mcp-go's in-process client; production code no longer calls
   `client.Client` at all. Removes trace 2.
3. docs: this plan + changelog.

## Out of scope / remaining

- Trace 1 is inside go-qrdb (replica forwarder of its MCP server, linked
  through `go-qrdb/pkg/server` for the embedded node). go-xkms cannot remove
  it without a go-qrdb release that stops using mcp-go's streamable client;
  go.mod is not changed in this lane. govulncheck keeps reporting
  GO-2026-6911 through that trace until go-qrdb ships the fix.
- Result after slice 2 (2026-11-20): govulncheck lists no trace through
  `pkg/mcptool`; all five remaining traces (NewStreamableHTTP, Close,
  SendNotification, SendRequest, SetRequestHandler) run through go-qrdb
  `pkg/api/mcp/replica_forward.go` forwardToLeader.
- No govulncheck ignore, allowlist or exclusion: the finding is real while
  go-qrdb's path exists, and hiding it would hide that.
