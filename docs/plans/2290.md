# #2290: node unbootable after a reboot, pebble WAL replay fails encfs block authentication

Objective: an embedded xkmsd node (passphrase barrier, local encfs pebble) boots after an unclean stop with every synced record intact; a boot-completion failure after unseal is precise and does not crash-loop.

## Root cause (reproduced in pkg/server/wal_reboot_test.go)

The cause is in go-qrdb v0.51.0-alpha pkg/seal/encfs, not in the barrier epoch or the seal store:

1. **A damaged trailing WAL block is fatal.** `encryptedFile.ReadAt` (encfs.go) decrypts the last on-disk block, and when the bytes fail GCM it returns `ErrAuthFailed` (block.go:20) instead of `io.EOF`/`io.ErrUnexpectedEOF`. Pebble's WAL replay tolerates a torn tail in its own record framing, but it treats any other read error as fatal: "pebble: error when replaying WAL: encfs: block authentication failed". `TestWALReboot_DamagedTailReplays` hits the board's exact error with a WAL tail cut by 1 or 100 bytes, or zero-extended by 1 or 4096 bytes.
2. **The trailing block is rewritten in place.** `encryptedFile.flushTailLocked` (encfs.go) writes the partial tail block at the same physical offset with a fresh nonce on every Sync, and does not advance `flushedSize`. `flushFullBlockLocked` later overwrites the same region again with the full block. A power cut while that overwrite is only partly persisted leaves a block that is half old ciphertext and half new, and that block fails authentication. With plain pebble the same cut would only lose the tail.
3. **Unsynced tail lost on unclean stop.** encfs holds up to 4 KiB of WAL bytes in memory (`tail`) until Sync or Close, and the embedded node's KV Put returns before pebble syncs. A kill or power cut loses acknowledged writes. In the tests, 64 Puts all left the WAL at its 133-byte header until Close, and 9 of 2000 were lost (`TestWALReboot_UncleanStopReopensIntact`, `...EpochRotationAcrossUncleanRestarts`).

Epoch rotation is not the cause: `TestWALReboot_CleanRestartsThenUncleanStop` rotates the epoch on every unseal (4 times) and replays fine. The DEK is barrier-wrapped in the file header, and a wrong key would fail the header unwrap, not a block. The board's WAL size, 69,632 bytes, is an exact multiple of 4096, which no encfs layout normally produces (133 + 4124·k + partial). That points to a zero-extended or page-torn tail (point 1). The preserved board WAL would show which: compare its trailing block against the 4124-byte framing.

## Fix needed in go-qrdb (out of this lane: no replace, no module-cache patch)

- pkg/seal/encfs `encryptedFile.ReadAt` / `newReadFile`, when opened for WAL replay: treat an unauthenticated **trailing** block (and a short trailing block) as end of file (`io.ErrUnexpectedEOF`), so pebble's torn-tail handling applies. Interior blocks still return `ErrAuthFailed`.
- Durability: KV writes the node acknowledges must reach a synced WAL (pebble.Sync, or a Sync before the ack), or the qrdb API must document that it does not.
- Optional and design-level (ruling 947: owner decides): stop the in-place partial-block rewrite, for example by appending sync-sized blocks.

## go-xkms side

- `serveSealedWindow` (pkg/server/sealed_window.go:96) already wraps the failure as `QRDBNodeError{Stage: "complete boot after sealed window"}` with the encfs cause reachable (`TestWALReboot_BootCompletionFailureIsPrecise` passes).
- Not done here: keeping xkmsd up after a post-unseal boot failure instead of exiting into a sealed restart loop (cmd/xkmsd/main.go runProcess). This changes daemon/systemd behaviour and needs a decision.
