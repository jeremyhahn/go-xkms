# #2290: node unbootable after a reboot, pebble WAL replay fails encfs block authentication

Objective: an embedded xkmsd node (passphrase barrier, local encfs pebble) boots after an unclean stop with every synced record intact; a boot-completion failure after unseal is precise and does not crash-loop.

## Root cause (reproduced in pkg/server/wal_reboot_test.go)

The cause is in go-qrdb v0.51.0-alpha pkg/seal/encfs, not in the barrier epoch or the seal store:

1. **A damaged trailing WAL block is fatal.** `encryptedFile.ReadAt` (encfs.go) decrypts the last on-disk block, and when the bytes fail GCM it returns `ErrAuthFailed` (block.go:20) instead of `io.EOF`/`io.ErrUnexpectedEOF`. Pebble's WAL replay tolerates a torn tail in its own record framing, but it treats any other read error as fatal: "pebble: error when replaying WAL: encfs: block authentication failed". `TestWALReboot_DamagedTailReplays` hits the board's exact error with a WAL tail cut by 1 or 100 bytes, or zero-extended by 1 or 4096 bytes. encfs authenticates up to 4096 plaintext bytes per block, so treating an unauthenticated trailing block as EOF can still lose the whole last block, several records: the guarantee is the synced prefix only. The reproduction separates a synced prefix (run 0, clean Close and reboot) from an unsynced tail (run 1) and asserts run 0 only (Codex round 3). Open: after the prefix reboot pebble keeps one WAL (000007.log, 133 bytes) and appends the tail to it, so the test's check that the damaged WAL holds only the tail fails; without that check delta=-100 replays and -1, 1, 4096 fail at boot completion.
2. **The trailing block is rewritten in place.** `encryptedFile.flushTailLocked` (encfs.go) writes the partial tail block at the same physical offset with a fresh nonce on every Sync, and does not advance `flushedSize`. `flushFullBlockLocked` later overwrites the same region again with the full block. A power cut while that overwrite is only partly persisted leaves a block that is half old ciphertext and half new, and that block fails authentication. With plain pebble the same cut would only lose the tail.
3. **Unsynced tail lost on unclean stop.** encfs holds up to 4 KiB of WAL bytes in memory (`tail`) until Sync or Close, and the embedded node's KV Put returns before pebble syncs. A kill or power cut loses acknowledged writes. In the tests, 64 Puts all left the WAL at its 133-byte header until Close; no `write_mode` (`sync`, `wal_durable`) changes that. `TestWALReboot_UnsyncedAcknowledgedWritesSurviveUncleanStop` reproduces it.

Synced records survive an unclean stop: qrdb exposes no WAL sync on the node, so the tests make the boundary a clean Close (verified by the store's bytes on disk), reboot and unseal, then copy the running node's directory. `TestWALReboot_UncleanStopReopensIntact` and `...EpochRotationAcrossUncleanRestarts` pass.

Epoch rotation is not the cause: `TestWALReboot_CleanRestartsThenUncleanStop` rotates the epoch on every unseal (4 times) and replays fine. The DEK is barrier-wrapped in the file header, and a wrong key would fail the header unwrap, not a block. The board's WAL size, 69,632 bytes, is an exact multiple of 4096, which no encfs layout normally produces (133 + 4124·k + partial). That points to a zero-extended or page-torn tail (point 1). The preserved board WAL would show which: compare its trailing block against the 4124-byte framing.

## Fix needed in go-qrdb (out of this lane: no replace, no module-cache patch)

- pkg/seal/encfs `encryptedFile.ReadAt` / `newReadFile`, when opened for WAL replay: treat an unauthenticated **trailing** block (and a short trailing block) as end of file (`io.ErrUnexpectedEOF`), so pebble's torn-tail handling applies. Interior blocks still return `ErrAuthFailed`. This drops the whole trailing block (up to 4096 plaintext bytes, several records), so it promises the synced prefix, not every record before the damage.
- Durability: KV writes the node acknowledges must reach a synced WAL (pebble.Sync, or a Sync before the ack), or the qrdb API must document that it does not.
- Optional and design-level (ruling 947: owner decides): stop the in-place partial-block rewrite, for example by appending sync-sized blocks.

## go-xkms side

- `serveSealedWindow` (pkg/server/sealed_window.go:96) already wraps the failure as `QRDBNodeError{Stage: "complete boot after sealed window"}` with the encfs cause reachable. `TestWALReboot_BootCompletionFailureIsPrecise` waits for the window to open before unsealing and injects a corrupt interior WAL block, so it always reaches boot completion (passes).
- Restart loop reproduced at daemon level: `TestDaemon_WALRebootBootFailureKeepsDaemonUp` (cmd/xkmsd/wal_reboot_daemon_test.go) runs run() on a passphrase-sealed pebble node with one corrupt interior WAL byte and unseals over the sealed window (`POST /v1/barrier/unseal`). It fails: run() returns 1 with "Failed to create server ... sealed window: ... complete boot after sealed window: ... encfs: block authentication failed". The exit path: `QRDBNodeError{Stage: "sealed window"}` (pkg/server/qrdb_node.go:294-296) leaves server.New, and cmd/xkmsd/main.go:210-213 logs "Failed to create server" and returns 1. The supervisor restarts xkmsd sealed, so every boot needs another unseal. The sealed-window listener is also torn down at unseal, before boot completion.
- Failed-boot state (slice 1c, done): when `server.New` fails at the "complete boot after sealed window" stage (`server.BootCompletionFailure`), xkmsd stays up and `server.ServeBootFailure` serves HTTPS on Server.Host:RESTPort (sealed-window bind rule, unified TLS cert or `tls.cert_file`). `GET /v1/barrier/status` and every other path answer 503 with `{"sealed":false,"boot_failed":true,"stage":...,"error":...}`. It returns 0 on SIGTERM/SIGINT and 1 only if the listener cannot be set up. Every other `server.New` failure still returns 1.
- Codex round 3, TLS: the failed-boot listener serves the unified TLS policy (`buildUnifiedTLSConfig`: TLS 1.3, `tls.client_auth`, configured client CAs); `TestServeBootFailure_KeepsUnifiedTLSPolicy`.
- Codex round 3, re-seal: `QRDBNodeError.Resealed` carries `node.IsSealed()` out of a failed boot completion; a re-sealed node (go-qrdb's clustered boot calls SealWholeNode) is not held behind the 503 listener: xkmsd logs it and exits, so the restart reopens the sealed window. The body reports `sealed` from it. The clustered re-seal itself is not driven in a test here.
