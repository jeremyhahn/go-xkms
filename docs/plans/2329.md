# Plan #2329: CORS on the daemon's unified API surface

## Objective

The Integration browser test `rp-ceremony.spec.ts` (cross-origin ceremony)
fails with `TypeError: Failed to fetch`. `pkg/apimodule` `RegisterHTTP`
registers each REST route by itself on the go-qrdb `ModuleHTTPRegistrar`, so
the chi CORS middleware in `pkg/api/rest/server.go` never runs on the unified
surface. No OPTIONS route exists either, so the preflight gets the auth
chain's 401. The fix applies the configured `cors` policy to the module's
routes.

## Slices

1. test(apimodule): a failing test builds the module's routes on a registrar
   the way the unified server does: `Handle` routes sit behind an auth gate
   that answers 401, and `HandlePublic` routes have no gate. CORS is enabled
   for one origin. The test checks four cases:
   - a preflight from the allowed origin for a webauthn route that requests
     `X-Session-Id` gets 2xx, with Allow-Origin, Allow-Credentials and the
     requested header;
   - a preflight from another origin gets no Allow-Origin;
   - a cross-origin POST carries Allow-Origin and Expose-Headers;
   - with CORS disabled, no CORS headers are added.
2. fix(apimodule, server): add a `WithCORS(*rest.CORSOptions)` module option.
   `RegisterHTTP` wraps each route handler in `rest.NewCORSMiddleware`, and
   for each route pattern it registers a public OPTIONS route that answers
   the preflight before auth. `pkg/server` passes the configured policy to
   the module. Add a changelog entry.

## Out of scope

- The Makefile, workflows, scripts and test/integration (the browser test is
  the acceptance check).
- CORS headers on 401 responses from the go-qrdb auth chain on authenticated
  routes. The go-qrdb registrar has no pre-auth middleware hook for module
  routes.
