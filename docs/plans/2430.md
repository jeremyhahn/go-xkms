# Plan: #2430 `ca crl` over QUIC returns internal server error

## Objective

Main is red on `TestProtocolParity_CA_CRL/quic`: the fourth forced CRL
generation in a row fails with a bare internal server error.

## Cause

The QUIC client posts to the same REST `GenerateCRL` handler as the other
transports, so the fault is server side, in `pkg/ca` `generateAndPersistCRL`.
That method does an unserialized read-modify-write: it reads the previous
CRL number (`nextCRLNumber`), signs, audits and writes the artifact
(`putCRLBlob`), with no lock. Overlapping generations (a forced refresh, a
refresh-on-revoke, a lazy regenerate) read the same previous number, issue
duplicate CRL numbers and race on the artifact write. On the replicated
store the losing write fails as a storage error, which the handler maps to
500.

## Slices

1. Test: concurrent `GenerateCRL` calls on one CA return no error, issue
   the distinct numbers 1..N, and leave N persisted
   (`TestGenerateCRL_ConcurrentCallsYieldDistinctIncreasingNumbers`).
2. Fix: serialize `generateAndPersistCRL` on a per-CA mutex so the
   number read, signing, audit and artifact write happen as one step.
   Changelog entry under `.changelog/unreleased/`.

## Out of scope

- Cross-instance serialization in a cluster (needs a store-level
  compare-and-set; the CA layer has none today).
- Retries, sleeps or test changes in the integration suite.
