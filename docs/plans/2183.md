# #2183 plan: Codex round-5 P1, harness trust bundle (ruling 968)

## Objective

The API integration harness and its REST/QUIC availability probes keep
verifying the server after unsealing switches it from the bootstrap
certificate (KEYSTORE_TLS_CA, /etc/xkms/certs/ca.crt in Compose) to the
certificate the serving CA issued, whose CA the server persists under the
unified-TLS data dir (XKMS_UNIFIED_CA, /xkms-data/xkms/unified-tls/ca-bundle.pem).

## Design

- One trust source in apiharness: the bootstrap CA (required), the ceremony
  root and the unified-TLS bundle (each when present), re-read from disk on
  every TLS dial, so a bundle the server writes at unseal is trusted at the
  next handshake. Verification stays on.
- Open and AwaitReady dial through that source instead of
  xkmsdtest.SealedWindowClient, which looks for ca-bundle.pem beside
  KEYSTORE_TLS_CA only.
- TrustBundleFile, the --tls-ca the CLI probes (QUIC) pass, is rewritten on
  each call instead of once per process.
- The REST probe (checkHTTPEndpoint) and loadCACertPool in test/integration/api
  use the same source instead of KEYSTORE_TLS_CA alone.

## Slices

1. test: trust_test.go with httptest TLS servers: a server on bootstrap CA A
   switches at unseal to a certificate from a distinct serving CA B written
   to the data-dir bundle path; Open returns, and TrustBundleFile written
   before the unseal trusts B afterwards and still trusts A.
2. fix: apiharness refreshing trust source, used by Open, TrustBundleFile,
   ClientTLSConfig callers and the REST/QUIC probes.

## Out of scope

Server-side TLS (pkg/server), the cluster harness, xkmsdtest.SealedWindowClient
and its callers, compose files and workflows.
