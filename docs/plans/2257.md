# Plan: key-get-algorithm (#2257)

## Objective

`xkmsctl key get` printed `Algorithm: 0` for a P-256 key (found on the
i.MX 95 deploy, ruling 814). The get path built the printed attributes
from the key ID and type only, dropping the response's algorithm and
curve.

## Slices

1. test(xkmsctl): `TestGetKey_P256NamesAlgorithm` drives `getKey` with a
   P-256 `KeyInfo` (algorithm `ECDSA`, curve `P-256`) in text, json and
   table formats and asserts the output names ECDSA and P-256 and never
   prints algorithm 0. Fails before the fix.
2. fix(xkmsctl): `keyAttributesFromInfo` (cmd/xkmsctl/key_info.go) maps
   the response's algorithm, curve and RSA size onto the attributes;
   `PrintKeyInfo` prints the algorithm by name in JSON and the curve by
   its name (`P-256`) in every format.
3. docs(plan): this file.
4. fix(transport): Codex P1 on the PR. The Unix and gRPC clients' GetKey
   conversion now copies `key_size`, `curve` and `partition` from the
   protobuf `KeyInfo`; the REST `KeyInfo` DTO and `keyInfoFromTransport`
   now carry them, so the REST and QUIC clients (which decode into
   `transport.KeyInfo`) receive them. Tests:
   `TestGetKey_CarriesCurveAndKeySize` (unix and grpc bufconn, P-256 and
   RSA-3072) and `TestKeyInfoFromTransport_CarriesCurveAndKeySize` (rest).

## Out of scope

- The server side of the gRPC/Unix response (`pb.KeyInfo` already carries
  `key_size` and `curve`).
- Store type and partition on the get output.
