# #2287 — login 500: the refresh-token store writes under the anonymous request context

## Objective

PIV/mTLS and WebAuthn login on a qrdb-backed xkmsd return 500 with
`auth/token: refresh store put failed: qrdb/auth: unauthenticated`. Login
routes are public, so the request context carries no identity, and
`QRDBRefreshStore` writes the go-qrdb KV with it. The refresh store's own
bookkeeping must run as the node's service principal
(`pkg/embeddednode/serviceprincipal`, via `Node.ServiceContext`).

## Slices (in order, one commit each)

1. test(auth): regression tests against an embedded, authenticating go-qrdb
   node configured with `serviceprincipal.Option()`:
   - `pkg/auth/token/store_servicectx_test.go`: `QRDBRefreshStore` with the
     binder saves, reads, rotates and revokes (family, subject) under a
     context with no identity; without the binder the put is refused as
     unauthenticated.
   - `pkg/server/login_wiring_test.go` (ruling 946, the xkmsd wiring:
     `server.New` over the embedded node, barrier enabled and unsealed with
     strategy `none`, piv_login with allow_unattested, enable_rbac off and
     on, the first-boot admin certificate): PIV login returns 200 with a
     token pair, the access token authenticates `GET /api/v1/auth/me`, and
     `POST /api/v1/auth/refresh` rotates the refresh token.
   Both fail at 9a4449afb with the unauthenticated refresh-store error.
2. fix(auth): `token.CallContext` binder (`token.WithCallContext` option on
   `NewQRDBRefreshStore`, nil = caller context) applied in Save, Get,
   MarkRotated, RevokeFamily and RevokeBySubject; `rest.TokenIssuerParams`
   and `rest.HostConfig` gain `ServiceContext`; pkg/server passes
   `s.qrdbNode.ServiceContext`, apimodule passes its `WithServiceContext`
   binder.
3. fix(rest): debug log of the Mint error on the 500 path of the PIV and
   WebAuthn login handlers (error string, user and tenant only; no token
   material).
4. changelog: `.changelog/unreleased/fixed-2287-login-refresh-store.md`.

## Finding (ruling 946)

The hand-built client wiring of session 1 refused the certificate lookup
before Mint; xkmsd does not use it. `Server.QRDBUserStore` resolves
certificates through `auth.NewQRDBServiceUserStore(nodeCertUsers{...})`,
i.e. `Node.UserService().UserByCertThumbprint`, which runs with no
principal below the node's client auth chain and RBAC (a certificate is
resolved before its holder is authenticated). On the production wiring
the login fails only at the refresh store put, in both RBAC modes, so
slices 2-4 apply unchanged and the grant stays as it is.

## Out of scope

- The service principal's grant (unchanged).
- Any other public-route qrdb call; if the refresh path's user re-check
  needs a permission the grant lacks, the lane stops and reports it.

## Stop after fix(auth): the refresh user re-check (architecture choice)

With the binder in place, PIV login answers 200, the WebAuthn mint succeeds
and `/auth/me` accepts the minted access token. (The earlier `/auth/me` 401
was the test config: `createMinimalConfig` sets an RS256
`auth.jwt.public_key_file`, which replaced the built-in ES256 issuer key as
verifier. The wiring test now uses `auth.type: composite` with no key
file, as an xkmsd that only verifies its own tokens runs.)

`POST /api/v1/auth/refresh` is refused 401 in both RBAC modes:
`auth/token: refresh refused: user re-check failed: auth: refresh user
lookup failed: qrdb/auth: unauthenticated`.

- Code path: `handlers_auth.go` refresh handler -> `token.Issuer.Refresh`
  (`pkg/auth/token/issuer.go:223`) -> `auth.QRDBUserResolver.ResolveUser`
  -> `lookup` (`pkg/auth/refresh_resolver.go:120`):
  `Users().GetUserByUsername(ctx, tenant, subject)` (:125) or
  `Users().GetUser(ctx, uid)` (:139), on the client built at
  `pkg/api/rest/host.go` BuildTokenIssuer
  (`auth.NewQRDBUserResolver(p.QRDBClient.Users())`), under the public
  route's identity-less context.
- Binding it to `Node.ServiceContext` would need the service principal
  to hold `read` on `users` (session 1: "qrdb-service:xkms cannot read on
  users"). The grant holds no users permission, and ruling 946 allows
  widening it only with the owner's say. A path that skips the access
  check (for example `Node.UserService`) is rejected by ruling 946.
- Permission list for option 1: `users: read` (GetUserByUsername, GetUser).
