# Plan 2376: xkms-server starts in the bootstrap integration stack (main fix)

## Objective

`make integration-test-bootstrap` brings up xkms-server and runs the
bootstrap suite. Main e0d8ce46 is red because the container exits 1.

## Slices

1. ComplianceGaps (done: 181d4110a test, 6ccbcc857 fix). The test runs
   generate-test-certs.sh and requires config.ComplianceGaps to return no
   gaps. The fix enables a composite authenticator and a CA section, and
   the Makefile prints the xkms-server log when the stack fails.
2. Sealed barrier (this slice). With those gaps fixed, the daemon still
   exits 1: the default "passphrase" barrier boots sealed and its
   sealed-window listener refuses server.host 0.0.0.0. Even when that bind
   is allowed, /health answers 503 until an unseal, so the compose
   healthcheck fails. The test requires the generated config's barrier
   seal strategy to be "none". The fix sets barrier.strategy "none"
   (auto-unseal), as test/integration/acmeadmin does.
3. Codex round 1 (this slice). The config tests move to
   internal/buildgates (make test-buildgates; no normal gate selected
   test/integration/bootstrap/setup), and a new test requires the compose
   test service to mount xkms-data and name the first-boot admin mTLS pair
   under datastore.path. The fix mounts the volume read-only, sets
   BOOTSTRAP_ADMIN_CERT/KEY, and newSDKTransport authenticates with them.
4. Codex round 2 (this slice). TestGeneratedConfigRequestsTheAdminClientCert:
   the generated config sets tls.client_auth: verify, so the server requests
   the admin certificate while certless clients (health check) still connect.
   The xkey-truststrap-test service gets the same mount and env, and its
   `bootstrap show-keys` call passes --tls-cert/--tls-key.

## Out of scope

- An unseal-ceremony step in the bootstrap harness.
- Any change to ComplianceGaps or to the sealed-window guard.
