# Plan: shipped-client-auth (issue #2254)

SPEC row xkmsd-configuration (Tenant Agent ruling 1073); merged main 852146763.

## Objective

`xkmsd init` provisions an mTLS administrator, but the shipped
`configs/xkmsd.yaml` left `tls.client_auth` unset (none), so the handshake
never asked for that administrator's certificate and the admin surface
refused it (found on the i.MX 95 deploy, ruling 814).

## Slices

1. test(config): `pkg/config/client_auth_mtls_admin_test.go` loads the
   shipped config and asserts `client_auth: verify`; asserts Validate
   rejects TLS on with client_auth none/unset while auth accepts mTLS
   (type mtls, the mtls flag, composite with mtls or default methods), and
   accepts a JWT-only chain. Fails before slice 2.
2. fix(config): `configs/xkmsd.yaml` sets `client_auth: verify`
   (VerifyClientCertIfGiven: browsers and ACME clients without a
   certificate still connect). `Config.Validate` refuses the unsafe
   combination with an error naming `tls.client_auth`
   (`AuthConfig.usesMTLS`). Configs with the same gap get `verify` too:
   xkmsd-dev, xkmsd-local, xkmsd.yaml.example,
   examples/config/config-default, and the api, web, acme-tpm and
   webauthn-browser integration configs; the cmd/xkmsd and pkg/server test
   fixtures that build TLS plus mTLS auth set it as well.
3. docs(plan): this file.
4. docs: engineering.md TLS section cites the Validate refusal and
   `usesMTLS`; `.changelog/unreleased/changed-2254-tls-client-auth-mtls-admin.md`.

## Out of scope

- Changing the code default of `tls.client_auth` or its TLS mapping.
- `require_and_verify` as the shipped default (would lock out browsers).
- Any workflow, go.mod/go.sum, scripts, SPEC or Makefile change.
