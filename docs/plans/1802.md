# 1802: cross-domain ELE key lock (seam row ele-cross-domain-lock, trusted-firmware#50)

**Answer: yes, go-xkms will offer it, as an A55-side lock.** xkmsd, on an M7 request it
can authenticate, refuses every key operation on the ELE key store, closes the store's
sessions and zeroizes its in-memory handles. It cannot be enforced against a compromised
A55, so it complements power-off ("A3 is A2"); it does not replace it. go-xkms has **no
ELE (EdgeLock Enclave) key store backend today**: `pkg/backend/` holds avr, awskms,
azurekv, gcpkms, importtoken, phone, pkcs11, software, tpm2 and vault, and no ele, imx
or edgelock package. ETA: after an ELE key store backend row and hsm-device-protocol exist.

## Grounding in go-xkms today
- Nearest lifecycle model: `pkg/backend/pkcs11/session_pool.go`, `NewSessionPool` (:137),
  `WithSession` (:224) and `Close` (:566). The lock reuses this shape: a locked state that
  `WithSession` refuses, then the drain-and-close of every session.
- Enclave keys: `pkg/enclaveprovider/provider.go`, `NewKeyProtector` (:49), `Unprotect`
  (:82), `NewRootUnsealer` (:109), `UnsealRoot` (:124), `ProvisionRoot` (:136); the
  package is the hardware bridge for go-enclave's provider (`pkg/enclaveprovider/doc.go:13`).
  A lock must also refuse `Unprotect` and `UnsealRoot` for an ELE-backed sealer.
- Seal strategies: `pkg/seal/strategy.go` (`StrategyTPM2` :109, `StrategyPKCS11` :112);
  there is no ELE strategy.
- SPEC rows `hsm-device-protocol` and `hsm-self-defence` (docs/SPEC.md:97-98, future);
  the latter's lockdown is already "driven by the M7 through System Manager/EdgeLock".

## Options
1. **A55-side lock on an authenticated M7 request (chosen).** Lives entirely in
   go-xkms; works with any ELE firmware. It is only as good as the A55 Linux: a
   compromised or stalled xkmsd ignores it.
2. **Enclave-native cross-domain lock.** Only if NXP ELE firmware lets another
   domain/MU lock a key store it did not open. That would be enforced by the
   enclave, but it is unknown whether the firmware offers it. go-xkms would only
   record the lock state. Preferred if it exists.
3. **"A3 is A2" (power off the A55).** trusted-firmware's default today. Strongest
   (no key use is possible while the A55 is off) and needs nothing from go-xkms, but
   it costs availability and cannot be undone remotely.
4. **Fold into hsm-self-defence lockdown.** The M7 lock request becomes one signal of
   the lockdown response (refuse key ops and unseal until a tenant quorum-signed
   unlock). Chosen as the unlock path for option 1, so there is one lock state, not two.

## Threat model
- Compromised or stalled A55 Linux: it ignores the request, so option 1 gives no
  guarantee. The M7 must watch for an authenticated acknowledgement within a deadline
  and fall back to A2 power-off when none arrives. Only options 2 and 3 hold here.
- Replay or forgery: the request is signed or MACed with a key only the M7 holds and
  xkmsd verifies; it carries a monotonic counter or nonce and the device identity.
  Unauthenticated, replayed or stale requests are refused and logged.
- Spurious lock (DoS): a lock never wipes keys. Unlock follows the hsm-self-defence
  quorum-signed unlock, and every lock and unlock is audit-logged.
- Guarantees: after an acknowledged lock, xkmsd performs no key operation and holds no
  session or handle. It cannot erase what an attacker already copied from A55 memory,
  and it cannot stop a rooted kernel from reopening the store. Power-off can.

## Needs from trusted-firmware and the enclave
- The M7-to-A55 channel (MU or RPMsg) and how xkmsd reaches it from Linux.
- The request's authentication key: where it lives on the M7, how go-xkms gets its
  public half or trust anchor (provisioned or attested), and how it rotates.
- The message format: lock request, acknowledgement and unlock, versioned.
- Whether ELE firmware offers a cross-domain lock or close (option 2).
- The hsm-device-protocol and hsm-self-defence rows that carry the signal.

## Open questions
- Does ELE firmware let a domain other than the one that opened a key store lock it?
- Does the M7 sign the request, or is a shared MAC key in the ELE enough?
- What acknowledgement deadline should trigger the A2 fallback?
- Is a lock per key store, per tenant or device-wide?
