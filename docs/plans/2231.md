# Plan #2231: PKCS8 DeleteKey leaves no orphan metadata

Defect on SPEC row key-version-cas (#2218).

## Objective

`(*PKCS8Backend).DeleteKey` removed the key blob and then the metadata record
in two storage calls. A failure or stop between them left the metadata record;
a retry returned ErrKeyNotFound at the blob step and never reached the record,
so a later key of the same identifier inherited the orphan's tenant and
Exportable flag.

## Slices

1. Test commit: a storage stub that fails the first metadata delete.
   - A retried DeleteKey removes both the blob and the metadata record.
   - A key placed afterwards under the same identifier (blob only, as an
     import without attributes does) lists with no inherited Exportable flag.
   - A GenerateKey whose metadata write fails rolls back without leaving a
     stale record of a missing blob for the next key to inherit.
2. Fix commit: DeleteKey tolerates a missing blob and still removes the
   metadata record, so a retry clears what an interrupted delete left.
   GenerateKey's rollback also removes the metadata record.
3. Codex round 1 (test commit, then fix commit): a failed blob delete must
   keep the tenant ownership record, so DeleteKey deletes the blob first and
   the record second; a rollback whose metadata cleanup fails keeps the blob
   and returns a joined error.
   Changelog entry `.changelog/unreleased/fixed-2231-pkcs8-delete-orphan.md`.

The storage Backend interface offers no batch or transaction, so ordering is
the mechanism.

## Out of scope

- The software backend's own import path (pkg/backend/software).
- Storage-level transactions.
