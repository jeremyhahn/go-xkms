# Plan: #2283 xkmsctl key copy sends no wrapping algorithm unless given

## Objective

`xkmsctl key copy` without `--algorithm` sends no wrapping algorithm, and the
server picks the destination backend's default: `TPM2_DUPLICATE` for a TPM 2.0
destination (its import surface accepts nothing else), `RSAES_OAEP_SHA_256`
for every other backend. An algorithm the caller names is passed through.

## Slices

1. CLI (done, earlier lane): the `--algorithm` flag has no default; the
   transport `CopyKeyRequest.Algorithm` is `omitempty`.
   Tests: `cmd/xkmsctl` key copy sends no algorithm unless given; the
   integration CLI copy without `--algorithm` on every transport.
2. Server (Codex round 1, both P1s):
   - REST `CopyKeyHandler`, gRPC `Service.CopyKey` and MCP `handleCopyKey`
     accept an omitted algorithm and delegate the default to the service.
     Tests: each handler forwards an empty algorithm to the service instead
     of rejecting it.
   - `XKMSService.CopyKey` resolves the default from the destination store
     type (`defaultCopyWrappingAlgorithm`); `backend.WrappingAlgorithmTPM2Duplicate`
     is exported and the TPM 2.0 backend uses it.
     Tests: `TestCopyKeyDefaultsWrappingAlgorithmFromDestination` checks the
     algorithm the destination's import parameters are requested with, for a
     TPM 2.0 destination, a software one, and a caller-named algorithm.

## Out of scope

- Per-backend default discovery beyond TPM 2.0 (a backend interface method).
- Other import/export endpoints that still require an algorithm.
