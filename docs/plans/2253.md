# #2253: the shipped config serves TLS (tls.server_cn)

## Cause

configs/xkmsd.yaml enabled TLS with a `ca:` section but no `tls.server_cn`
and no cert_file/key_file. Boot-time TLS issuance (pkg/server/server.go,
`TLS.Enabled && TLS.ServerCN != ""`) was skipped, and buildTLSConfig asked
the CA for an empty CN. The node kept its bootstrap certificate and never
installed a CA-issued one (the unix socket included, unified_tls.go).

## Fix

- test(config) b56d0fb05: TestShippedConfigTLSServerCN loads the shipped
  file, requires a non-empty server_cn, and requires Validate to reject
  an empty server_cn with no cert files.
- fix(config) f206f8d58: Validate rejects tls.enabled + CA + empty
  server_cn + no cert_file/key_file (the error names tls.server_cn).
  xkmsd.yaml and xkmsd-dev.yaml set `server_cn: localhost`.
  The rule is limited to configs with a CA. Without a CA, cert files were
  already required, and about 60 config fixtures that rely on the
  bootstrap certificate stay valid.
- Fixtures outside the original file map that the rule required:
  pkg/config/load_test.go (writeCAPasswordConfig), pkg/server/server_test.go
  (createMinimalConfig x3), server_ca_reload_793_test.go; the unix gRPC
  test dialer also trusts the installed CA-issued certificate.

## Out of scope

The acme: section and other blocks; server-side defaulting of the CN.

- docs(plan) 5a5a65685: this file.
