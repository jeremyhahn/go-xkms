# PKCS#11 Backend — User Guide

> **Status: NORMATIVE** · Feature: `pkcs11-backend` · Repo: `go-xkms` · Last verified: 2026-09-24

## What this is for

Use the PKCS#11 backend when your signing/encryption keys must live inside
a hardware security module or smart card — a SoftHSM2 token for
development, a YubiKey for PIV-style deployment, or a production HSM
(nCipher/nShield, CloudHSM, etc.) — instead of on disk. Once configured,
every `xkmsctl`/SDK/REST/gRPC/MCP key operation works against it exactly
like the `software` backend; the difference is where the private key
actually lives, and that it never leaves the device.

## 1. Build with the tag

```bash
go build -tags pkcs11 ./cmd/xkmsd
```

cgo is required. Without the tag, `xkmsd` starts, logs `PKCS#11 backend
enabled in config but not compiled in (use -tags pkcs11)`, and simply has no
`pkcs11` backend — every request naming it fails the same way requesting
any other unregistered backend would.

## 2. Prepare the token (you do this once, with vendor tooling)

`xkmsd` never initializes a token itself. For SoftHSM2 (what CI uses):

```bash
softhsm2-util --init-token --slot 0 --label 'xkms' --so-pin 12345678 --pin 87654321
softhsm2-util --show-slots
```

For any device, the generic Cryptoki tool works too:

```bash
pkcs11-tool --module /path/to/vendor.so --list-slots
```

## 3. Point `xkmsd` at it

```yaml
backends:
  pkcs11:
    enabled: true
    library: "/usr/lib/softhsm/libsofthsm2.so"
    token: "xkms"
    pin: "87654321"
```

Known library paths:

| Device | Library |
|---|---|
| SoftHSM2 | `/usr/lib/softhsm/libsofthsm2.so` |
| YubiKey PIV | `libykcs11.so` (`/usr/lib/x86_64-linux-gnu/libykcs11.so`) |
| nCipher / nShield | `/opt/nfast/toolkits/pkcs11/libcknfast.so` |
| Nitrokey HSM / SmartCard-HSM | `/usr/lib/opensc-pkcs11.so` |

Prefer `token:` (a label) over a slot number — slot numbers are not stable
across reboots or re-enumeration, and on a multi-token host the wrong slot
means the PIN gets presented to the wrong token, burning a retry attempt.

Treat the config file as a secret once `backends.pkcs11.pin` is populated
(`0600`, root-owned): the value can be a `credential://` reference resolved
at load time rather than a literal PIN — see
[`engineering.md`](engineering.md) §"PIN resolution" for the exact
mechanism, and prefer a token whose PIN policy tolerates being supplied
once at daemon boot, rotating it through vendor tooling rather than through
xkms.

## 4. Generate and use a key

```bash
xkmsctl --backend pkcs11 key generate demo-key \
  --key-type signing --key-algorithm ecdsa --curve P-256
xkmsctl --backend pkcs11 key sign demo-key --data-file payload.bin
```

Confirm on the device side that the private half is genuinely not readable:

```bash
pkcs11-tool --module /path/to/vendor.so --login --pin <PIN> --list-objects --type privkey
```

## Things that will surprise you

- **Ed25519 doesn't work on every token.** It needs PKCS#11 v3.0 Edwards
  support (SoftHSM2 ≥ 2.6) and is rejected outright on YubiKey PIV — use
  `ecdsa-p256` or `rsa` there.
- **A generated key is not automatically exportable.** Whether a key
  generated by this backend can later be wrapped out depends on the
  token's `CKA_EXTRACTABLE` default, which this backend does not force for
  generated RSA/ECDSA keys (unlike imported keys, where it is always set
  explicitly from your `exportable` request). Verify on the device with
  `pkcs11-tool --list-objects` before relying on export working. See
  [`architecture.md`](architecture.md) §"CKA_SENSITIVE vs CKA_EXTRACTABLE"
  — a broader, corrected treatment lives in the superseded
  `docs/pkcs11/backend/security.md`, which is otherwise still an accurate
  read on this topic.
- **Multi-token hosts need `token:` set explicitly.** Every backend
  operation resolves the slot by label for exactly this reason — grabbing
  "the first slot" would authenticate your PIN against somebody else's
  token and burn their retry counter.
- **Key rotation isn't supported by this backend.**
  `Capabilities().KeyRotation` is `false`; `RotateKey` returns
  `backend.ErrOperationNotSupported`.
- **Attestation needs a device attestation key the token may not have.**
  `key attest` (or the SDK's `AttestKey`) works only if the token publishes
  a certificate + signing key under the fixed
  `DeviceAttestationKeyLabel` — SoftHSM has none by default. See
  [`architecture.md`](architecture.md) §"Attestation."

## Common failure modes

| Symptom | Cause | Fix |
|---|---|---|
| `pkcs11: library not found` | `Config.Validate()` could not stat `library` | Fix the path; check `ldd` for missing vendor dependencies. |
| `failed to load PKCS#11 library: <path>` | `C_GetFunctionList` unavailable / not a Cryptoki module | Wrong `.so`; check architecture and `LD_LIBRARY_PATH`. |
| `pkcs11: token not found: token label "x" not found` | Label mismatch (labels are space-padded to 32 bytes) | `--show-slots`/`--list-slots` and copy the label exactly. |
| `pkcs11: token not initialized` on every call | `Login()` never called, or it failed | Check startup logs; the token must already be SO-initialized. |
| `failed to create session pool: ... login failed` | Wrong user PIN (`CKR_PIN_INCORRECT`) or locked token | Verify the PIN; check the device's retry counter before retrying. |
| `CKR_USER_ALREADY_LOGGED_IN` | Another pool/manager already logged in on the token | Benign; tolerated by the pool and import/export paths. |
| `CKR_OPERATION_ACTIVE` | A search or crypto operation left open on a session | A session handle escaped its `WithSession` callback — file a bug. |
| `pkcs11: invalid pin length` / `invalid SO pin length` | PIN shorter than 4 characters | Supply a real PIN. |
| `pkcs11: SO PIN required ... (provide management key)` | YubiKey PIV key generation without `so-pin` | Set the management key as `SOPIN` (library embedding only — no daemon YAML field). |
| `CKR_ATTRIBUTE_VALUE_INVALID` on YubiKey keygen | Full attribute template sent to `libykcs11` | Ensure the library path is detected as PIV (`IsYubiKeyPIV`). |
| `pkcs11: unsupported key algorithm: ... Ed25519` | Ed25519 requested on PIV | Use ECDSA P-256 or RSA. |
| `backend.ErrKeyNotExportable` | `exportable=false` on the request, or `CKA_EXTRACTABLE=false` on the object | Non-recoverable for that key — see [`architecture.md`](architecture.md). |
| `failed to unwrap key with RSA-OAEP` / `CKR_ARGUMENTS_BAD` | Token does not support OAEP unwrap for secret keys (SoftHSM2) | Use an `RSA_AES_KEY_WRAP_*` import algorithm (hybrid path). |
| `CKR_KEY_FUNCTION_NOT_PERMITTED` from ECDH derive | Base key lacks `CKA_DERIVE` | See [`engineering.md`](engineering.md) §"Signing, decryption, symmetric, ECDH." |
| ML-DSA / ML-KEM refused | `probeQuantumMechanisms` did not see the mechanism | Token lacks PKCS#11 v3.2 PQC support. |
| Fewer keys than expected from a key list | One `C_FindObjects` call caps at 256 handles | Filter on the device, or reduce objects per token. |
