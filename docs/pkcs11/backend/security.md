# Security

## What never leaves the HSM

Private and secret key material generated by this backend is created by
`C_GenerateKeyPair` / `C_GenerateKey` inside the token and is never held by the
xkms process. Every private-key operation — sign, decrypt, unwrap, ECDH derive —
is a Cryptoki call against an object handle.

There is consequently no plaintext node-local private key for the barrier to
seal. `Get()` refuses to return key material at all:

```go
	// For PKCS#11, we can only return public key
	// Private key material never leaves the HSM
	return nil, &errs.Detail{Err: backend.ErrNotSupported, Detail: "PKCS#11 private keys cannot be exported"}
```

`Save()` likewise refuses to accept key material: keys must be generated on the
device.

## CKA_SENSITIVE vs CKA_EXTRACTABLE

These two attributes are routinely conflated, and conflating them previously
broke `C_WrapKey` in this codebase. Per PKCS#11 §4.9 Table 30:

| Attribute | Meaning | Consequence |
|---|---|---|
| `CKA_SENSITIVE = CK_TRUE` | the value is never revealed **in plaintext** | `C_GetAttributeValue(CKA_VALUE)` fails; the key can still be wrapped |
| `CKA_EXTRACTABLE = CK_TRUE` | the key **may be wrapped** | `C_WrapKey` is permitted; this is *not* plaintext export |
| `CKA_EXTRACTABLE = CK_FALSE` | the key can never leave the token in any form | wrapping and plaintext read both fail |

**Wrapping does not require plaintext export.** A key can be, and normally is,
both sensitive and extractable: it leaves only as ciphertext under another key.

The import template writes both flags explicitly rather than trusting token
defaults:

```go
	template := []*pkcs11.Attribute{
		pkcs11.NewAttribute(pkcs11.CKA_CLASS, class),
		pkcs11.NewAttribute(pkcs11.CKA_TOKEN, true),
		pkcs11.NewAttribute(pkcs11.CKA_SENSITIVE, true),
		pkcs11.NewAttribute(pkcs11.CKA_EXTRACTABLE, attrs.Exportable),
		pkcs11.NewAttribute(pkcs11.CKA_LABEL, keyLabel),
		pkcs11.NewAttribute(pkcs11.CKA_ID, keyID),
	}
```

The reason is portability of the security level: §5.18.4 gives a key produced by
`C_UnwrapKey` a default `CKA_EXTRACTABLE` of `CK_TRUE`, and the §4.9 secret-key
table gives `CKA_SENSITIVE` a default of `CK_FALSE`. SoftHSM2 is stricter than
the specification requires, so a template that relied on defaults would pass in
CI and silently import a plaintext-readable key on a conforming HSM.

Two consequences worth stating plainly:

- `attrs.Exportable = false` at import time is **permanent**. The key can never
  be recovered from the token afterwards, by any route.
- `attrs.Exportable = true` still yields `CKA_SENSITIVE = CK_TRUE`, so the key
  leaves only through `C_WrapKey` — never as plaintext.

Generated keys are handled differently and less strictly:

- `GenerateSecretKey` sets `CKA_SENSITIVE=true` **and**
  `CKA_EXTRACTABLE=false`, so generated AES keys are sealed into the token.
- `generateRSAKeyPair` and `generateECDSAKeyPair` set `CKA_SENSITIVE=true` but
  say nothing about `CKA_EXTRACTABLE`, leaving the token's default in force. If
  your device defaults it to `CK_TRUE`, generated private keys are wrappable.
  Verify with `pkcs11-tool --list-objects` on the device you actually deploy.

`ExportKey` defends in depth: it checks `attrs.Exportable` (xkms policy) and
then reads `CKA_EXTRACTABLE` back off the object (device truth), failing with
`backend.ErrKeyNotExportable` if either says no.

## What the wrap/unwrap ceremony exposes

| Stage | Where the plaintext key is |
|---|---|
| `GetImportParameters` | nothing sensitive leaves; only the wrapping **public** key is returned |
| `WrapKey` | **on the host.** Import is by definition of externally generated material, so that material is in process memory here |
| `ImportKey`, direct OAEP | plaintext exists only inside the token |
| `ImportKey`, hybrid RSA+AES | the **ephemeral AES KEK** is decrypted to host memory (`aesKeyBytes`, `pkcs11_importexport.go:460`) before being re-imported as a session object; the target key itself is only ever unwrapped inside the token |
| `ExportKey` | output is ciphertext under the token's RSA-4096 wrapping key |
| `ExportKeyMaterial` | **plaintext bytes to the caller** — symmetric keys only, and only when `CKA_EXTRACTABLE=true` |

The hybrid path exists because SoftHSM2 rejects `C_UnwrapKey` with
`CKM_RSA_PKCS_OAEP` for secret keys. It is a compatibility workaround, not the
preferred route: on a production HSM with complete PKCS#11 2.40 support, prefer
the direct-OAEP algorithms so no key-encryption key is ever materialised on the
host. The temporary AES object is `CKA_TOKEN=false` and destroyed by a `defer`;
the decrypted `aesKeyBytes` buffer is left to the garbage collector.

The wrapping key pair itself is generated in the token with the private half
non-extractable and sensitive, and persists across restarts under the label
`go-xkms-wrapping-key`.

## Derived material

`DeriveKeyECDH` intentionally creates the derived object with
`CKA_SENSITIVE=false` and `CKA_EXTRACTABLE=true` so the raw ECDH shared secret
can be read out and run through the requested KDF in software. The private key
never leaves the token, but **the shared secret does**. If your threat model
does not permit that, use a token-side KDF instead of `CKD_NULL`.

## Authentication

- **User PIN (`CKU_USER`)** — supplied once at pool construction; Cryptoki login
  state is per token, so one login covers every session. The backend never calls
  `C_Logout` from the symmetric paths, because logout would drop every session on
  the token, including other callers'.
- **SO PIN (`CKU_SO`)** — used for `C_InitPIN` during first-time token setup and,
  on YubiKey PIV, as the management key for key generation and object
  destruction. `WithSOSession` restores the user login afterwards, including on
  the error path. Callers must serialise around it: the intermediate state is
  visible to every session on the token.
- PIN length is validated (minimum 4 characters) but strength is not; the device
  owns retry counters and lockout.
- `Config.String()` masks both PINs. The PIN is not written to logs by the
  daemon's initialisation message, which logs only library and token label.

See [configuration.md](configuration.md) for where the PIN comes from and why it
is not currently resolved through the `credential://` chain.

## AEAD safety

Symmetric encryption enforces a per-key byte budget and nonce uniqueness through
`types.AEADSafetyTracker` **before** the operation reaches the token. The
default tracker is in-memory, which means the guarantees reset on restart:
production deployments should inject a persistent `Tracker` via
`pkcs11.Config`.

Nonce and tag lengths are pinned (96-bit / 128-bit) and validated on input.
Rejecting a short tag prevents a caller from downgrading forgery resistance by
asking the token to verify fewer bits.

## Operational notes

- Multi-token hosts: always set `TokenLabel`. Every code path resolves the slot
  through `resolveSlot()` for this reason — an operation that grabbed `slots[0]`
  would authenticate the configured PIN against somebody else's token and burn a
  retry counter.
- `C_FindObjects` searches are always finalised, including on the error path;
  a leaked search leaves the session unusable (`CKR_OPERATION_ACTIVE`).
- An imported key that the backend cannot address afterwards is destroyed rather
  than left behind: PKCS#11 §5.1 requires a call to accomplish "either its
  entire goal, or nothing at all", and an orphaned object is unreachable key
  material.
