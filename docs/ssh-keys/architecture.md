# SSH Keys, Known Hosts & Authorized Keys — Architecture

> **Status: NORMATIVE** · Feature: `ssh-keys` · Repo: `go-xkms` · Last verified: 2026-09-24

## Scope of this folder

This folder covers the three SSH data models go-xkms manages directly: SSH
**keys** (`pkg/ssh/keys`), **host-key pins** (`pkg/ssh/known_hosts`, the
`known_hosts`-equivalent), and **authorized-key entries**
(`pkg/ssh/authorized`), plus the backend bridge that lets a key be generated
on any crypto backend (`pkg/ssh/backend`) and the network/CLI surfaces built
on top. It does not cover interactive console sessions or hostless
agent-signing sessions — those are
[`../ssh-agent-sessions/`](../ssh-agent-sessions/), which is NORMATIVE for
that capability — nor the xkey desktop application's connection-profile
manager (`pkg/ssh/connect`, `pkg/ssh/profile`, `pkg/ssh/sessions`,
`pkg/ssh/local`), which is a consumer of this feature and of
`ssh-agent-sessions`, not part of either: that manager, plus interactive
console sessions, is now [`../ssh-sessions/`](../ssh-sessions/)
(go-xkms#707), which is NORMATIVE for it. The legacy
[`../ssh/README.md`](../ssh/README.md) covered all of the above in one
file; with `ssh-keys`, `ssh-agent-sessions`, and `ssh-sessions` together,
every subpackage of `pkg/ssh` now has a NORMATIVE home and that legacy
file is fully superseded, though not yet deleted (no single folder
absorbs it end to end — see `docs/README.md`'s migration record).

## No build tag — always compiled, always mounted

Unlike FROST (`-tags frost`) and the PKCS#11 backend (`-tags pkcs11`), no
file under `pkg/ssh/keys`, `pkg/ssh/known_hosts`, `pkg/ssh/authorized`, or
`pkg/ssh/backend` carries a `go:build` constraint, and neither do the REST
(`pkg/api/rest/handlers_ssh.go`), gRPC (`pkg/api/grpc/service_ssh.go`), or
MCP (`pkg/api/mcp/handlers_ssh.go`) handlers. Every `xkmsd` binary has this
feature; there is no `backends.ssh` config section to enable it because it
is not a `types.KeyProvider` backend — it is a service layered over whatever
backends already exist.

## Where a key's private half actually lives

An SSH key is one of two shapes (`pkg/ssh/keys/key.go`):

- **Software** — an ed25519/RSA/ECDSA private key generated by
  `keys.Generate` (`pkg/ssh/keys/generate.go:63`), sealed into a
  `*secure.Secret` in OpenSSH PEM form, and stored directly in the SSH key
  store.
- **Backend-backed** — `Key.BackendID`/`Key.BackendKeyID` are set and
  `Key.Material` is nil. The private key was generated by (and stays inside)
  a configured crypto backend (`software`, `tpm2`, `pkcs11`, a cloud KMS, or
  a remote xkms reached as a backend); the SSH key record holds only the
  derived public key and a pointer to the backend key. `Key.BackendSigner`
  (`pkg/ssh/keys/signer.go:120`) resolves a `crypto.Signer` from the backend
  at use time and wraps it with `ssh.NewSignerFromSigner` — for a hardware
  backend, the private key never leaves the device to produce an SSH
  signature.

`pkg/ssh/backend.Provider` (`pkg/ssh/backend/provider.go:51`) is the bridge:
it takes a `Resolver` (a `backendID -> types.KeyProvider` lookup) and
implements `GenerateKey`/`Signer`/`DeleteKey` in terms of the resolved
backend's own `types.KeyProvider` methods. `SupportedAlgorithms(storeType)`
(`pkg/ssh/backend/algorithms.go:61`) is the single source of truth for which
SSH algorithms a given backend can generate: TPM 2.0 is restricted to RSA
and ECDSA P-256/P-384/P-521 (no native Ed25519 key object type in TPM 2.0);
every other recognized store type gets the full set
(Ed25519/RSA/ECDSA-P256/P384/P521); an unrecognized store type (including a
remote-xkms backend category this package does not resolve) fails open to
the full set and lets the backend's own `GenerateKey` reject an unsupported
algorithm with its own typed error.

## One key store behind every transport

```
xkmsctl ssh <verb> / xkey ssh <verb>
        |  (--server URL, or embedded)
        v
sdk/go/client/ssh.Client   (embedded | REST | gRPC | unix | QUIC | MCP — dispatch by URL scheme)
        |
        v
xkmsd: s.ensureSSHClient() builds ONE embedded sdkssh.Client, shared by every transport
        |                          (pkg/server/server.go:417-452)
        +-- storage "ssh" view --> pkg/ssh/keys.BackendStore   (SSH key envelopes)
        +-- pkg/ssh/known_hosts.Store                          (host-key pins)
        +-- pkg/ssh/authorized.Store                           (authorized_keys entries)
        +-- pkg/ssh/backend.Provider --> s.xkmsService.LookupBackend(backendID)
                                          --> any configured crypto backend
```

`ensureSSHClient` (`pkg/server/server.go:417`) builds this lazily, once, the
first time any transport needs it, and only if `s.xkmsService != nil` — REST,
gRPC, and MCP all call through the *same* embedded client object, so a key
generated over gRPC is immediately visible over REST. There is no
separate "REST implementation" of key generation; the REST/gRPC/MCP handlers
are thin encode/decode layers over `sdkssh.Client` method calls
(`pkg/api/rest/handlers_ssh.go:102`: `h.client.Keys().Generate(r.Context(), req)`).

## Transport selection (SDK)

`sdkssh.NewClientForServer(server, tlsCA, token)` dispatches on URL scheme:

| Scheme | Transport |
|---|---|
| `http(s)://` | REST |
| `grpc(s)://` | gRPC (`grpcs` = TLS) |
| `unix://<path>` | gRPC over a Unix domain socket |
| `quic://` | HTTP/3 (dials the REST port — no separate QUIC listener) |
| `mcp(s)://` | MCP JSON-RPC |

`xkmsctl ssh` honors the CLI's global `--server`/`--transport`/`--tls-ca`
flags for every subcommand in this folder's scope — unlike `xkmsctl frost`,
which never dials out (see `../frost-threshold-signing/architecture.md`).

## Identity coordinates: Scope / Owner / Name

Every key, host pin, and authorized-key entry is filed under
`(Scope, Owner, Name)`. `scope.Scope` (`pkg/ssh/scope/scope.go:31`) is one of
three string constants: `Tenant`, `User`, `Service`. Owner is a
scope-relative identifier (a tenant ID, user ID, or service ID); Name is the
caller-assigned label within that (Scope, Owner) pair. `xkmsctl ssh`'s
`--scope`/`--owner` flags default to `user`/`default`
(`cmd/xkmsctl/ssh.go:219-220`).

## Known-hosts: full public key, not just a fingerprint

`known_hosts.Pin` (`pkg/ssh/known_hosts/pin.go:54`) stores the full SSH
wire-format public key (`PublicKey []byte`), not only its SHA-256
fingerprint — required since a pin created before this field existed decodes
as `*LegacyPinError` rather than silently as an empty-key `Pin`
(`pkg/ssh/known_hosts/errors.go:45`). This is what lets a pin be re-emitted
as an OpenSSH `known_hosts` line and matched byte-for-byte, not just by
fingerprint collision odds. `Verify` compares the full key.

## Authorized keys: Entry (parsed line) vs. Record (store metadata)

`authorized.Entry` (`pkg/ssh/authorized/entry.go:34`) models exactly one
`authorized_keys` line — a `*keys.Key` (public-only for parsed lines),
`Options` (OpenSSH restriction tokens, preserved verbatim — this package
does not interpret `no-port-forwarding`, `command="..."`, `from="..."`,
etc., sshd does), and a free-text `Comment`. `authorized.Record`
(`pkg/ssh/authorized/record.go:38`) wraps an `Entry` with the store
coordinates (`Scope`, `Owner`, `Name`, `AddedAt`) a `List` call returns, so a
caller can feed `Record.Name` straight back into `Get`/`Remove`.

## Backend-selection surface gap: gRPC has no `verify`/`emit` RPC

REST and MCP both expose dedicated `known-hosts verify` and
`authorized-keys emit`/`verify` operations as server-side calls. gRPC does
not — `proto/xkmsv1/xkms.proto` defines `SSHAddKnownHost`,
`SSHListKnownHosts`, `SSHRemoveKnownHost`, `SSHAddAuthorizedKey`,
`SSHListAuthorizedKeys`, `SSHRemoveAuthorizedKey`, but no
`SSHVerifyKnownHost`/`SSHEmitAuthorizedKey`/`SSHVerifyAuthorizedKey`. The
gRPC SDK client (`sdk/go/client/ssh/grpc.go`) fills the gap **client-side**:
`grpcKnownHostsClient.Verify` (`grpc.go:280`) calls `List` and compares
fingerprints locally; `grpcAuthorizedKeysClient.Emit` (`grpc.go:366`) is
"a pure local normalization" that never calls the server at all (it just
parses and re-renders the line); `grpcAuthorizedKeysClient.Verify`
(`grpc.go:378`) calls `List` and compares locally, the same pattern as
known-hosts. Functionally equivalent to the caller, but it is worth knowing
that a `verify` over gRPC costs a full `List` round trip rather than a
single targeted lookup, and that `Callback` (`grpc.go:301`, the
`ssh.HostKeyCallback` adapter used for real SSH dials) inherits the same
`List`-then-compare cost on every host-key check.

## Rejected alternative: a dedicated `ssh` resource per verb

REST/gRPC/MCP authorization uses one blanket permission,
`auth.ResourceSSH`/`auth.ActionUse`, on every route in this feature
(`pkg/api/rest/routes.go:394-397`: "Every route carries the blanket ssh:use
gate; key generation and signing must never be reachable anonymously"). This
is coarser than the generic key-management routes, which vary
`auth.ActionCreate`/`List`/`Get`/`Delete`/`Sign` per verb. The RBAC
vocabulary for a finer split is go-qrdb's, not xkms's local decision; a
local view of it is the still-owed `architecture/rbac.md` item tracked in
[`../README.md`](../README.md) — this note records the fact for this
feature rather than resolving it.
