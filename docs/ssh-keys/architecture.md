# SSH Keys, Known Hosts & Authorized Keys — Architecture

> **Status: NORMATIVE** · Feature: `ssh-keys` · Repo: `go-xkms` · Last verified: 2026-10-12

## Scope of this folder

This folder covers the three SSH data models go-xkms manages directly: SSH
**keys** (`pkg/ssh/keys`), **host-key pins** (`pkg/ssh/known_hosts`, the
`known_hosts`-equivalent), and **authorized-key entries**
(`pkg/ssh/authorized`), plus the backend bridge that lets a key be generated
on any crypto backend (`pkg/ssh/backend`) and the network/CLI surfaces built
on top. It does not cover interactive console sessions or hostless
agent-signing sessions — those are
[`../ssh-agent-sessions/`](../ssh-agent-sessions/), which is NORMATIVE for
that capability — nor the xkey desktop application's connection-profile
manager (`pkg/ssh/connect`, `pkg/ssh/profile`, `pkg/ssh/sessions`,
`pkg/ssh/local`), which is a consumer of this feature and of
`ssh-agent-sessions`, not part of either: that manager, plus interactive
console sessions, is now [`../ssh-sessions/`](../ssh-sessions/)
(go-xkms#707), which is NORMATIVE for it. The legacy `ssh/README.md`
covered all of the above in one file; with `ssh-keys`,
`ssh-agent-sessions`, and `ssh-sessions` together, every subpackage of
`pkg/ssh` has a NORMATIVE home, so that file was absorbed into the three
and deleted (go-xkms#1433).

## No build tag — always compiled, always mounted

Unlike FROST (`-tags frost`) and the PKCS#11 backend (`-tags pkcs11`), no
file under `pkg/ssh/keys`, `pkg/ssh/known_hosts`, `pkg/ssh/authorized`, or
`pkg/ssh/backend` carries a `go:build` constraint, and neither do the REST
(`pkg/api/rest/handlers_ssh.go`), gRPC (`pkg/api/grpc/service_ssh.go`), or
MCP (`pkg/api/mcp/handlers_ssh.go`) handlers. Every `xkmsd` binary has this
feature; there is no `backends.ssh` config section to enable it because it
is not a `types.KeyProvider` backend — it is a service layered over whatever
backends already exist.

## Where a key's private half actually lives

An SSH key is one of two shapes (`pkg/ssh/keys/key.go`):

- **Software** — an ed25519/RSA/ECDSA private key generated by
  `keys.Generate` (`pkg/ssh/keys/generate.go:63`), sealed into a
  `*secure.Secret` in OpenSSH PEM form, and stored directly in the SSH key
  store.
- **Backend-backed** — `Key.BackendID`/`Key.BackendKeyID` are set and
  `Key.Material` is nil. The private key was generated by (and stays inside)
  a configured crypto backend (`software`, `tpm2`, `pkcs11`, a cloud KMS, or
  a remote xkms reached as a backend); the SSH key record holds only the
  derived public key and a pointer to the backend key. `Key.BackendSigner`
  (`pkg/ssh/keys/signer.go:120`) resolves a `crypto.Signer` from the backend
  at use time and wraps it with `ssh.NewSignerFromSigner` — for a hardware
  backend, the private key never leaves the device to produce an SSH
  signature.

`pkg/ssh/backend.Provider` (`pkg/ssh/backend/provider.go:51`) is the bridge:
it takes a `Resolver` (a `backendID -> types.KeyProvider` lookup) and
implements `GenerateKey`/`Signer`/`DeleteKey` in terms of the resolved
backend's own `types.KeyProvider` methods. `SupportedAlgorithms(storeType)`
(`pkg/ssh/backend/algorithms.go:61`) is the single source of truth for which
SSH algorithms a given backend can generate: TPM 2.0 is restricted to RSA
and ECDSA P-256/P-384/P-521 (no native Ed25519 key object type in TPM 2.0);
every other recognized store type gets the full set
(Ed25519/RSA/ECDSA-P256/P384/P521); an unrecognized store type (including a
remote-xkms backend category this package does not resolve) fails open to
the full set and lets the backend's own `GenerateKey` reject an unsupported
algorithm with its own typed error.

## One key store behind every transport

```
xkmsctl ssh <verb> / xkey ssh <verb>
        |  (--server URL, or embedded)
        v
sdk/go/client/ssh.Client   (embedded | REST | gRPC | unix | QUIC | MCP — dispatch by URL scheme)
        |
        v
xkmsd: s.ensureSSHClient() builds ONE tenancy client, shared by every transport
        |                          (pkg/server/server.go:508-527)
        v
pkg/ssh/tenancy: bind (scope, owner) to the caller, pick the partition
        |
        v  per request: an embedded sdkssh.Client over one partition
        +-- go-qrdb "ssh" database, "{tenant}/" partition:
        |     pkg/ssh/keys.DAOStore                                   (SSH key envelopes)
        |     pkg/ssh/known_hosts.DAOStore                            (host-key pins)
        |     pkg/ssh/authorized.DAOStore                             (authorized_keys entries)
        +-- pkg/ssh/backend.Provider --> tenant KeyProvider view
                                          --> s.xkmsService.LookupBackend(backendID)
                                          --> any configured crypto backend
```

`ensureSSHClient` (`pkg/server/server.go:508`) builds this lazily, once, the
first time any transport needs it, and only if `s.xkmsService != nil` — REST,
gRPC, and MCP all call through the *same* client object, so a key generated
over gRPC is immediately visible over REST to the same caller. There is no
separate "REST implementation" of key generation; the REST/gRPC/MCP handlers
are thin encode/decode layers over `sdkssh.Client` method calls
(`pkg/api/rest/handlers_ssh.go:102`: `h.client.Keys().Generate(r.Context(), req)`).

## Transport selection (SDK)

`sdkssh.NewClientForServer(server, tlsCA, token)` dispatches on URL scheme:

| Scheme | Transport |
|---|---|
| `http(s)://` | REST |
| `grpc(s)://` | gRPC (`grpcs` = TLS) |
| `unix://<path>` | gRPC over a Unix domain socket |
| `quic://` | HTTP/3 (dials the REST port — no separate QUIC listener) |
| `mcp(s)://` | MCP JSON-RPC |

`xkmsctl ssh` honors the CLI's global `--server`/`--transport`/`--tls-ca`
flags for every subcommand in this folder's scope — unlike `xkmsctl frost`,
which never dials out (see `../frost-threshold-signing/architecture.md`).

## Identity coordinates: Scope / Owner / Name

Every key, host pin, and authorized-key entry is filed under
`(Scope, Owner, Name)`. `scope.Scope` (`pkg/ssh/scope/scope.go:31`) is one of
three string constants: `Tenant`, `User`, `Service`. Owner is a
scope-relative identifier (a tenant ID, user ID, or service ID); Name is the
caller-assigned label within that (Scope, Owner) pair. `xkmsctl ssh`'s
`--scope`/`--owner` flags default to `user`/`default`
(`cmd/xkmsctl/ssh.go:219-220`). Against `xkmsd` a tenant-scoped caller must
name an owner it owns (next section), so it passes `--owner <its subject>`
for `user`/`service` scope and `--owner <its tenant ID>` for `tenant` scope.

The `"<scope>/<owner>/<name>"` identifier (`scope.BuildKeyID`) names an asset
in APIs, backend key IDs and CNs; it is not where the asset is stored. Storage
follows the xkms-wide scope layout (`pkg/scope`,
[`../multi-tenancy/architecture.md`](../multi-tenancy/architecture.md#ownership-scopes)),
built in one place, `pkg/ssh/scope/layout.go` (`Kind.RecordPath`,
`ListPrefix`, `Kind.Match`), so the three stores never re-derive it:

```
{tenant}/ssh/shared/<kind>/<name>             scope=tenant
{tenant}/ssh/users/{subject}/<kind>/<name>    scope=user
{tenant}/ssh/services/{owner}/<kind>/<name>   scope=service

<kind> = keys | known_hosts | authorized_keys
```

Each store writes the part from `ssh/` on; the `{tenant}/` root is the
partition the store's backend already is (next section). Other SSH features
sharing the view (`ssh/sessions/`, `ssh/profiles/`) never match a record path,
so a listing that scans the whole `ssh/` view keeps only its own kind.

A tenant-scoped path carries no owner — the owner is the tenant, which the
partition already is — so each store keeps the owner in the record and treats
it as authoritative: a `Get`, `Delete`/`Remove` or `Verify` naming another
owner answers exactly as a missing asset (and deletes nothing), a listing
filtered by owner filters on the record, and a write over another owner's
record is refused — `*keys.OwnerConflictError` for a key `Put` (a 409 on
every transport), `*DuplicateError` for a pin or `authorized_keys` `Add`. The
server never reaches this (tenancy binds a tenant-scoped owner to its
partition's tenant); it keeps an embedded or local store, such as xkey's, from
ever aliasing two owners. There is no data migration and no compatibility
reader for the previous `ssh/<kind>/<scope>/<owner>/<name>` layout.

## Owner binding and tenant partitions (go-xkms#1230)

`xkmsd` wires every transport — REST, gRPC, MCP, QUIC and the Unix socket —
with one SSH client, the tenant-binding service `pkg/ssh/tenancy`
(`pkg/server/server.go:486-512`). The transports stay thin: they decode a
request and call it. The RBAC gate in front of them cannot protect an SSH
asset, because `auth.Authorizer` always binds the caller's own tenant as the
target, and a tenant Admin holds every `ssh:*` permission. Before this
service existed the transports called the embedded client directly, so a
tenant-A Admin could list, sign with, delete, and plant `authorized_keys`
entries for tenant B's and every user's keys.

**Binding.** For each request the service reads the caller from the context
and applies the xkms scope rule, `scope.Principal.Authorize`
([`../multi-tenancy/architecture.md`](../multi-tenancy/architecture.md#ownership-scopes)):

- `scope=tenant` belongs to the tenant whose ID is the owner; every user of
  that tenant may address it, and nobody outside it — a system-tenant caller
  included (go-xkms#1406).
- `scope=user` belongs to the principal whose subject is the owner, in the
  caller's own tenant. Only that principal may address it — **a system-tenant
  caller included**: it reaches its own personal keys, never another user's.
- `scope=service` belongs to a workload in the caller's own tenant. The owner
  is the workload's ID and is not bound to the caller's subject; instead the
  caller must hold the explicit `ssh:service` permission, checked below the
  transport gate through `XKMSService.AuthorizeCaller`
  (`tenancy.Options.Permissions`). With no checker wired the scope is closed.

There is no platform caller. A request with no identity is refused
(`*scope.UnauthenticatedError`), and a listing without one reads the empty
partition. Every network transport attaches an identity first; on the unix
socket it is `uid:<peer uid>` in the system tenant
([`../multi-tenancy/api.md`](../multi-tenancy/api.md#identity-on-the-unix-socket)).
The refusal carries the scope rule's reason in `OwnerBindingError.Cause`
(`*scope.UnauthenticatedError`, `*scope.CrossTenantError`,
`*scope.CrossUserError`, `*scope.ServiceScopeError`) for server-side
diagnostics only. A refused request is served from the *empty partition*, a
store nothing is ever written to (`pkg/ssh/tenancy/client.go:130`), so its
answer is by construction the genuine-miss answer; the service wraps it in
`*OwnerBindingError`, which renders that answer verbatim
(`pkg/ssh/tenancy/errors.go:44-71`). A refused write never reaches a store or
a backend: it is answered with the not-found for the address it names
(`pkg/ssh/tenancy/ops.go:135-138`). A listing reads the caller's partition and
keeps only what the caller owns (`pkg/ssh/tenancy/ops.go:76-92`).

**Partitions.** A subject is unique only within its tenant — the mTLS
authenticator uses the username (`pkg/auth/mtls.go:252`) — so the owner
binding alone would still let `alice` of tenant A reach the `user/alice`
keys of `alice` in tenant B in one flat store. Each tenant therefore gets its
own storage partition, rooted at its tenant root `{tenant}/`
(`scope.TenantRoot`) in the shared `ssh` storage view
(`pkg/ssh/tenancy/client.go:352-372`), and its own
backend-key namespace: backend-backed keys are generated and resolved
through a `KeyProvider` view that sets `types.KeyAttributes.TenantID`
(`pkg/ssh/tenancy/keyprovider.go:24-105`), exactly as
`xkms.TenantScopedBackend` scopes the key-management surface. A backend key's
common name (`ssh-<scope>-<owner>-<name>`, `pkg/ssh/keys/generate.go:238-244`)
is unique only within a tenant; the namespace keeps two tenants' equal names
apart.

The platform is the ordinary tenant `system` (`scope.TenantRoot("")` is
`system/`), so its assets land under `system/ssh/...` exactly as tenant A's
land under `tenant-a/ssh/...`. Which partition serves a request
(`pkg/ssh/tenancy/client.go:275-320`):

| Caller | Partition |
|---|---|
| tenant-scoped | its own tenant's |
| system-tenant | the platform partition, `system/` |
| no identity | none — refused; a listing reads the empty partition |

The partition follows the caller, never the address: a system-tenant
identity manages the `system` tenant's `scope=tenant` assets, its own
`scope=user` assets, and the platform partition's service assets with
`ssh:service` — and no other tenant's. A session (`Session().Dial`) must take its key and its
host-key pins from one partition the caller owns
(`pkg/ssh/tenancy/ops.go:327-352`).

Rejected: enforcing the binding in each transport handler. Three transports
(and the Unix socket, which reuses the gRPC service) would each need the same
check, and the next transport would need it again; the service is the one
place every transport already goes through, the pattern go-xkms#1112 set for
tenant targets. Rejected: a tenant-qualified owner string (`<tenant>:<user>`)
in one flat store. It changes the wire value every client sends and still
shares one backend-key namespace.

## Known-hosts: full public key, not just a fingerprint

`known_hosts.Pin` (`pkg/ssh/known_hosts/pin.go:54`) stores the full SSH
wire-format public key (`PublicKey []byte`), not only its SHA-256
fingerprint; `Add` refuses a pin without it (`*PublicKeyRequiredError`). This is what lets a pin be re-emitted
as an OpenSSH `known_hosts` line and matched byte-for-byte, not just by
fingerprint collision odds. `Verify` compares the full key.

## Authorized keys: Entry (parsed line) vs. Record (store metadata)

`authorized.Entry` (`pkg/ssh/authorized/entry.go:34`) models exactly one
`authorized_keys` line — a `*keys.Key` (public-only for parsed lines),
`Options` (OpenSSH restriction tokens, preserved verbatim — this package
does not interpret `no-port-forwarding`, `command="..."`, `from="..."`,
etc., sshd does), and a free-text `Comment`. `authorized.Record`
(`pkg/ssh/authorized/record.go:38`) wraps an `Entry` with the store
coordinates (`Scope`, `Owner`, `Name`, `AddedAt`) a `List` call returns, so a
caller can feed `Record.Name` straight back into `Get`/`Remove`.

## Backend-selection surface gap: gRPC has no `verify`/`emit` RPC

REST and MCP both expose dedicated `known-hosts verify` and
`authorized-keys emit`/`verify` operations as server-side calls. gRPC does
not — `proto/xkmsv1/xkms.proto` defines `SSHAddKnownHost`,
`SSHListKnownHosts`, `SSHRemoveKnownHost`, `SSHAddAuthorizedKey`,
`SSHListAuthorizedKeys`, `SSHRemoveAuthorizedKey`, but no
`SSHVerifyKnownHost`/`SSHEmitAuthorizedKey`/`SSHVerifyAuthorizedKey`. The
gRPC SDK client (`sdk/go/client/ssh/grpc.go`) fills the gap **client-side**:
`grpcKnownHostsClient.Verify` (`grpc.go:280`) calls `List` and compares
fingerprints locally; `grpcAuthorizedKeysClient.Emit` (`grpc.go:366`) is
"a pure local normalization" that never calls the server at all (it just
parses and re-renders the line); `grpcAuthorizedKeysClient.Verify`
(`grpc.go:378`) calls `List` and compares locally, the same pattern as
known-hosts. Functionally equivalent to the caller, but it is worth knowing
that a `verify` over gRPC costs a full `List` round trip rather than a
single targeted lookup, and that `Callback` (`grpc.go:301`, the
`ssh.HostKeyCallback` adapter used for real SSH dials) inherits the same
`List`-then-compare cost on every host-key check.

## Permissions per verb

Each REST route gates on its own `ssh:*` action
(`pkg/api/rest/routes.go:476-503`): `ssh:read`, `ssh:write`, `ssh:delete`,
matching the MCP `ssh.*` methods (`pkg/api/mcp/server.go:499-517`) and the
gRPC `qrdb.v1.permission` options. Signing is `ssh:write` on every
transport (`pkg/api/rest/routes.go:493`). Until go-xkms#1230 every REST route
carried the blanket `ssh:use`, so a grant meant for signing also deleted keys
and added `authorized_keys` entries. The blanket `ssh:use` is retired. See [`api.md`](api.md) for
the per-route table.

`ssh:service` is the one SSH permission no route names: only the request's
scope reveals it is needed, so `pkg/ssh/tenancy` checks it, in addition to
the verb's own permission, for every `scope=service` address. xkms owns and
declares it (`ScopeSelf`, like its siblings) and contributes it through
`belowGatePermissions`, so the built-in Admin and Owner roles hold it.
