## Supported algorithms

| `types.SymmetricAlgorithm` constant | Wire string | Key size |
|---|---|---|
| `SymmetricAES128GCM` | `"aes128-gcm"` | 128 bits |
| `SymmetricAES192GCM` | `"aes192-gcm"` | 192 bits |
| `SymmetricAES256GCM` | `"aes256-gcm"` | 256 bits |
| `SymmetricChaCha20Poly1305` | `"chacha20-poly1305"` | 256 bits |
| `SymmetricXChaCha20Poly1305` | `"xchacha20-poly1305"` | 256 bits |

(`pkg/types/types.go:475-479`.) AES-CBC (`types.CipherModeCBC`/`CBCPad`) and
AES-ECB (`types.CipherModeECB`) are cipher **modes** selected via
`EncryptOptions.Mode`/`DecryptOptions.Mode`, not separate
`SymmetricAlgorithm` values — they require an AES-family key
(`isAESCipherAlgorithm`, `backend.go:909-919`) and are rejected for
ChaCha20/XChaCha20 keys with `ErrCBCRequiresAES`/`ErrECBRequiresAES`.

## Invariants

- **AEAD safety checks run in a fixed order and abort encryption on
  failure**: bytes-limit check, nonce resolution, an atomic (key, nonce)
  claim against the shared guard, encrypt (`backend.go:551-736`, and the
  equivalent sequence in `pkg/backend/azurekv/azurekv_symmetric.go`,
  `pkg/backend/pkcs11/pkcs11_symmetric.go`, `pkg/tpm2/symmetric.go`,
  `pkg/keyprovider/quantum/signer.go`). For the random-nonce FIPS path the
  nonce is only observable *after* `Seal`, so the claim runs on the produced
  ciphertext's nonce and a collision discards that ciphertext rather than
  ever returning it (`backend.go:672-686`).
- **Every AEAD nonce, on every backend's `Encrypt`, is claimed in the
  process-wide guard -- reached through `XKMSService` or directly.**
  go-xkms#1201's second half moved this claim out of
  `XKMSService.Encrypt`/`wrapAESGCM` (which claimed nothing themselves
  before this change and claim nothing themselves now) and into each
  backend's own `Encrypt`, immediately before `Seal`, through
  `backend.ClaimAEADNonce` (caller-supplied nonce) or
  `backend.ClaimGeneratedAEADNonce` (backend-generated nonce, tolerates a
  full guard) — `pkg/backend/aead_nonce.go:75`, `:112`. This is the lowest
  layer common to a request that arrives through `XKMSService` and one that
  holds a `Backend` directly (`sdk/go`, `xkey`), so a caller bypassing the
  service is now protected too, and it is the *only* claim made for a
  service-routed request: claiming again at the service layer would claim
  the same pair twice and refuse the first, legitimate call as a false
  reuse, which is why `pkg/xkms/aead_nonce_guard.go` was deleted rather than
  kept alongside it. A reuse is `aead.ErrNonceReuse` (wrapped as
  `*ErrKeyOperation` by callers with that error type, such as
  `pkg/xkms/servicer_wrapkey.go`'s `wrapAESGCM`), and no ciphertext is
  returned. Tests: `pkg/backend/aead_nonce_test.go` (the claim functions in
  isolation: reuse, sealed-vs-material identity, unresolved/propagated
  errors, full-guard tolerance policy, concurrent-callers race under
  `-race`); `pkg/xkms/servicer_crypto_nonce_test.go` and
  `servicer_wrapkey_nonce_test.go` (the same guarantees reached through
  `XKMSService`: reuse, ChaCha20-Poly1305, concurrency, a key generated by
  one backend instance and encrypted through a second — both directly
  against that second instance's own encrypter and through the service --
  aliasing across two backend instances and two names, generated-nonce
  replay, wrap/encrypt sharing one guard, PKCS#11 end to end);
  `pkg/backend/pkcs11/pkcs11_symmetric_test.go`'s
  `TestSymmetricEncrypter_RejectsNonceReuse`, `pkg/tpm2/symmetric_test.go`'s
  `TestNonceReuse`, and `pkg/backend/azurekv/azurekv_symmetric_test.go`'s
  `TestAzureKVBackend_NonceReuse` (each backend's own `Encrypt` path,
  against that backend's own mocks, with no `XKMSService` involved).
- **`aead.ErrNonceReuse` and `aead.ErrNonceTrackerFull` classify to
  `ClassAlreadyExists` / `ClassResourceExhausted` on every transport**,
  through `apierrors.AEADSentinelClasses` (`pkg/api/apierrors/tables.go`),
  consulted from `pkg/api/grpc/errors_keyops.go`'s and `pkg/api/mcp`'s
  `mapKeyOpError`, and mirrored by REST's `keyOpSentinelStatus`
  (`pkg/api/rest/errors_keyops.go`) — `409`/`AlreadyExists`/the MCP
  duplicate code for a reuse, `503`/`ResourceExhausted`/the MCP internal
  floor (with `Classified` set so the text is not withheld) for a full
  guard (go-xkms#1223). Both `Encrypt` and `WrapKeyByID` (the AES-GCM wrap)
  go through the same table. Tests: `TestMapKeyOpError_AEADNonceSentinels`
  in each of `pkg/api/grpc`, `pkg/api/mcp` and `pkg/api/rest`, plus the
  `"aead"` sub-test in each package's `TestClassification_MatchesSharedTables`.
- **A caller-supplied nonce against a backend whose encryption always
  happens remotely is refused, not silently dropped.** AWS KMS, GCP KMS,
  Vault Transit and the paired phone's symmetric `Encrypt` all manage nonce
  generation themselves and expose no parameter to override it; a non-nil
  `EncryptOptions.Nonce` is refused with `backend.ErrCallerNonceNotSupported`
  before the remote call is ever made (`pkg/backend/awskms/awskms_symmetric.go`,
  `pkg/backend/gcpkms/gcpkms.go`, `pkg/backend/vault/vault_symmetric.go`,
  `pkg/backend/phone/symmetric.go`), classified as `ClassInvalidArgument` via
  `apierrors.ImportExportSentinelClasses` — `400`/`InvalidArgument`/MCP
  Invalid params (go-xkms#1223).
- **CBC/ECB carry no AEAD safety tracking at all** — they are not AEAD
  modes, so `IncrementBytes`/`CheckNonce`/`RecordNonce` are never called on
  that path (`backend.go:556-569`, `:750-759`).
- **`Exportable` and `Sensitive` are set-once, at creation.** The persisted
  `keyMetadata` record (`metadata.go:47-68`, schema version 3) documents
  this explicitly: "Only `newKeyMetadata` may set this field to true;
  nothing downstream of key creation is permitted to widen a key from
  non-exportable to exportable." `saveKeyMetadataOrRollback`
  (`metadata.go:114-...`) deletes the just-written key blob if the metadata
  write fails, so a key is never left with material on disk and no metadata
  record.
- **CBC padding-oracle resistance is unconditional.** `unpadPKCS7`
  (`backend.go:1162-1203`) runs the same number of comparisons regardless of
  where or whether padding is invalid, and returns the single
  `ErrInvalidPadding` for every failure mode — no branch may be added whose
  timing or error value depends on *how* padding failed (Vaudenay 2002).
- **A stored, password-protected symmetric key's own wrapping is subject to
  the identical FIPS-mode GCM-construction rules** as an ordinary AEAD
  `Encrypt` call — see [`architecture.md`](architecture.md) §"GCM nonce
  modes and FIPS".

All declared as typed sentinels in `errors.go`, never inline `fmt.Errorf`:
`ErrStorageClosed`, `ErrInvalidPassword`, `ErrUnsupportedCipherMode`,
`ErrCBCRequiresAES`, `ErrECBRequiresAES`, `ErrIVNotSupported`,

`ErrArbitraryIVGCMUnavailable`, `ErrAdditionalDataNotSupported`,

not by this package; `ErrNonceReused`, an alias for `aead.ErrNonceReuse`

nonce those backends' remote encryption service cannot honor.

## AEAD safety tracker — `types.AEADSafetyTracker`

Interface (`pkg/types/types.go:2886-2906`): `IncrementBytes(keyID, numBytes
int64) error`, `GetBytesEncrypted(keyID) (int64, error)`,
`GetAEADOptions(keyID) (*AEADOptions, error)`, `SetAEADOptions(keyID,
*AEADOptions) error`, `ResetTracking(keyID) error`. Covers only the bytes
budget; `CheckNonce`/`RecordNonce` were removed by go-xkms#1201 -- see "One
process-wide claim, made inside `Encrypt` itself" in
[`architecture.md`](architecture.md) for where nonce-reuse checking lives
now, and `pkg/backend/errors.go`'s `ErrNonceReused` doc comment for why that
sentinel is kept as an alias of `aead.ErrNonceReuse` rather than deleted: a
caller checking `errors.Is(err, backend.ErrNonceReused)` must keep matching
what the guard actually returns.

`types.AEADOptions{NonceTracking, BytesTracking, BytesTrackingLimit,
NonceSize bool/bool/int64/int}`; `DefaultAEADOptions()` sets both tracking
flags true, a 350GB byte limit, and `NonceSize: 12`
(`pkg/types/types.go:527-547`, defaults at `:570-577`). `NonceTracking` is retained on the struct for
the `GetAEADOptions`/`SetAEADOptions` configuration surface but no longer
gates anything: nonce-reuse protection is unconditional, on every backend,
regardless of this setting (`TestBackend_NonceReuseRefusedEvenWithTrackingOptedOut`
in `pkg/keyprovider/symmetric/backend_tracking_test.go` pins this).

**The only implementation in this repository** is
`backend.NewMemoryAEADTracker` (`pkg/backend/aead_tracker.go:51`): a
per-keyID byte counter, guarded by a `sync.RWMutex` with `sync/atomic`
counters. `RotateKey` calls `tracker.ResetTracking(keyID)` before generating
the replacement key (`backend.go:328-355`), zeroing the byte counter for
that key ID. This reset is deliberately scoped to the bytes budget only: the
nonce guard is not reset on rotation, and must not be — resetting it would
let the old key version's nonces be reused if the rotated key ever produced
the same material again (see `pkg/backend/awskms/awskms_backend_gaps_test.go`'s
`TestRotateKey_SymmetricResetsAEADTracking`).

### Per-key options and the bytes budget

- `KeyAttributes.AEADOptions` (`pkg/types/types.go:1224-1226`) sets the
  budget per key; nil means `DefaultAEADOptions()`. `GenerateSymmetricKey`
  takes `attrs.AEADOptions` or the defaults, runs `Validate`, and stores the
  result with `tracker.SetAEADOptions` (`backend.go:431-442`).
- `AEADOptions.Validate` (`pkg/types/types.go:550-561`): `NonceSize` 0
  becomes 12, below 12 is an error; with `BytesTracking` set, a
  `BytesTrackingLimit` of 0 or less becomes the 350GB default. Setting
  `BytesTracking: false` is the only way to turn the budget off.
- `memoryAEADTracker.IncrementBytes` (`pkg/backend/aead_tracker.go:59-86`)
  tracks nothing for a key with no stored options or with `BytesTracking`
  false. Otherwise, if the running total plus the request would pass the
  limit, it returns `ErrBytesLimitExceeded` (`pkg/backend/errors.go:72`)
  without counting the request. The symmetric `Encrypt` wraps that as
  "AEAD safety check failed: … (consider rotating this key)"
  (`backend.go:606-610`). `GetAEADOptions` returns a copy, or `nil, nil`
  when none is set (`aead_tracker.go:102-118`).
- The tracker never warns ahead of the limit; the first sign is the refusal.

### `pkg/crypto/aead.BytesTracker`

A standalone, exported byte counter (`pkg/crypto/aead/bytes_tracker.go`)
that no production code calls; the backends use the `AEADSafetyTracker`
above. `NewBytesTracker(enabled, limit)` (`:71`) treats a limit of 0 as
`DefaultBytesTrackingLimit` (350GB, `:33`); `Conservative68GB` (`:37`) is
offered as a tighter limit. `CheckAndIncrementBytes` (`:98-114`) adds
atomically and rolls the add back when it passes the limit;
`ShouldWarnUser` (`:185-190`) reports usage at or above 90%.

## Algorithm auto-selection — `pkg/crypto/aead/auto.go`

- `SelectOptimal(hardwareBacked bool)` (`:193-202`) returns the JWE name
  `"A256GCM"` or `"ChaCha20-Poly1305"`; `SelectOptimalBackend` (`:221-228`)
  returns `"aes256-gcm"` or `"chacha20-poly1305"`. Both pick AES when the
  key is hardware-backed, when FIPS mode is on, or when the CPU has AES
  instructions (`selectAESGCM`, `:103-119`).
- FIPS is a runtime check, `fips140.Enabled()` (`fipsRequiresAES`,
  `:138-140`), not a build tag, so one binary follows the process's
  `GODEBUG=fips140` setting.
- `HasAESNI` (`:155-164`) reads `cpu.X86.HasAES` on amd64 and
  `cpu.ARM64.HasAES` on arm64; every other architecture reports false and
  gets ChaCha20-Poly1305.
- `IsAESGCM`/`IsChaCha` (`:231-252`) accept either naming; `ToJWE`/`ToBackend`
  (`:260-300`) convert between them and return an unknown name unchanged.
- The only production caller is JWE: `parseContentEncryption`
  (`pkg/encoding/jwe/jwe.go:504-534`) uses `SelectOptimal(false)` when `enc`
  is empty, and maps the ChaCha20/XChaCha20 names to `A256GCM` because
  ChaCha20-Poly1305 is not an RFC 7516 content-encryption algorithm. Symmetric key generation
  does not auto-select (see below).

## Password-wrapped key storage

`encryptWithPassword` (`backend.go:1282`) derives the wrapping key with
Argon2id, t=1, 64 MiB, p=4, from a fresh 32-byte `crypto/rand` salt
(`backend.go:1291`), and stores `[salt][nonce][ciphertext+tag]`.
`decryptWithPassword` (`backend.go:1324`) refuses a blob shorter than 60
bytes before deriving.

## `EncryptedData` wire format

`symmetric.Marshal`/`Unmarshal` (`pkg/keyprovider/symmetric/encrypted_data.go:99`,
`:174`; layout documented at `:71-98`): version byte `0x02`, nonce-mode byte
(`0x00` explicit, `0x01` random), then algorithm, nonce and tag each as a
u16 length plus bytes, then the ciphertext as a u32 length plus bytes.
Version 1 is refused; there is no older-format reader.

## Deriving from a stored key — `types.SymmetricKeyDeriver`

`SymmetricKeyDeriver` (`pkg/types/kdf.go:138-152`) is optional. The service
checks for it and returns `ErrBackendUnsupported` wrapping
`ErrOperationNotSupported` when the backend lacks it
(`pkg/xkms/servicer_kdf.go:95-99`). A backend that has it but whose key
cannot be read returns `ErrKeyDerivationNotSupported` (`pkg/types/kdf.go:71`).

| Backend | Implementation |
|---|---|
| symmetric | `pkg/keyprovider/symmetric/kdf.go:43` |

| PKCS#11 | `pkg/backend/pkcs11/pkcs11_kdf.go:49-78` — exports the key value, maps `ErrKeyNotExportable` to `ErrKeyDerivationNotSupported`, wipes the material |

## Configuration

No YAML/config-file surface of its own: `symmetric.Config` is a Go struct
passed to `NewBackend`, constructed by
`pkg/xkms/register_symmetric.go:init()`, which registers under
`xkms.BackendSymmetric = "symmetric"`
(`pkg/xkms/registry.go:74-76`, "Always compiled in" — and, unlike
`register_quantum.go`, this one's doc comment matches the code: there is no
build-tag claim to contradict). Its factory `newSymmetricKeyProvider`
recognizes exactly one configuration key, `"key_dir"` (string): empty or
`"memory"` selects `storage.New()` (in-memory); any other value opens
`file.New(keyDir)` (`register_symmetric.go:33-47`).

## What is absent, half-built, or misdescribed

- **Resolved (go-xkms#1201, first half): the nonce guard is now durable.**
  `aead.SharedAEADNonceGuard`'s own tracker is still per-process memory with a
  per-process salt, but `pkg/server`'s `initializeAEADNonceStore` attaches a
  `pkg/aeadnonce.Store` to it at startup, and `KeyNonceGuard.UseContext`
  claims through that store as well as the in-memory tracker. A claim now
  survives a restart and is visible to every node sharing the datastore. See [`architecture.md`](architecture.md)'s
  "Persistence: a durable claim, not process memory alone" for the spec
  citations behind the design and why a caller-supplied nonce is still
  admitted rather than refused outright.
- **Resolved (go-xkms#1201, second half): a caller holding a `Backend`
  directly is now guarded too, by the same shared instance.** Before this
  half, the durable claim above lived only in `XKMSService.Encrypt`/
  `wrapAESGCM`; a caller that constructed a `symmetric.Backend`,
  `azurekv.Backend`, `pkcs11.Backend`, `tpm2.TPM2` or `quantum.QuantumBackend`
  directly (`sdk/go`, `xkey`) reached none of it, and fell back to the old,
  in-memory, non-atomic, per-instance `types.AEADSafetyTracker`
  (`CheckNonce`/`RecordNonce`) — or, for PKCS#11/TPM2/cloud-KMS backends,
  nothing at all, since those never implemented tracker-based nonce checking
  in the first place. The claim now lives inside each backend's own
  `Encrypt`, through `backend.ClaimAEADNonce`/`ClaimGeneratedAEADNonce`,
  which is the lowest layer both a service-routed and a direct caller pass
  through, so both are covered by one guard and one claim per operation. See
  "One process-wide claim, made inside `Encrypt` itself" in
  [`architecture.md`](architecture.md). `types.AEADSafetyTracker` lost its
  `CheckNonce`/`RecordNonce` methods entirely as part of this change — it now
  covers only the bytes-encrypted budget, which remains genuinely per-backend
  and process-local (see "AEAD safety tracker" above) — and no in-memory
  tracker for nonces remains anywhere in the repository to eventually make
  persistent, since none is needed: the guard it used to imitate is now the
  only guard, and it is already durable.
- **`pkg/crypto/aead`'s CPU/hardware-aware `SelectOptimal` is not called by
  `GenerateSymmetricKey`.** The auto-selection logic exists and is exported,
  but key generation takes the algorithm directly from
  `attrs.SymmetricAlgorithm` — nothing in `pkg/keyprovider/symmetric` invokes
  `aead.SelectOptimal`/`SelectOptimalBackend`. A caller that wants
  CPU-optimal cipher selection must call that function itself before setting
  `attrs.SymmetricAlgorithm`.
- **CLI and generic REST key-generation only reach AES-GCM by name**; see
  [`cli.md`](cli.md) and [`api.md`](api.md) for the exact gap between what
  the backend supports (all five algorithms, four modes) and what each
  transport's help text advertises.
- **Key-derivation (`DeriveFromSymmetricKey`) is documented in full in this
  package**, but the underlying `pkg/crypto/kdf` package (HKDF, PBKDF2,
  Argon2/Argon2i/Argon2id, SP800-108 counter/feedback/double-pipeline, X9.63,
  SP800-56A) is shared, general-purpose infrastructure imported well beyond
  this feature (`pkg/encoding/pkcs8.go`, `pkg/staticpw/`, the PKCS#11,
  software and TPM2 backends, `pkg/xkms/servicer_kdf.go`), so it is
  documented once in [`../crypto/kdf.md`](../crypto/kdf.md); this folder
  does not duplicate that coverage.
