# Symmetric Encryption & AEAD — User Guide

> **Status: NORMATIVE** · Feature: `symmetric-aead` · Repo: `go-xkms` · Last verified: 2026-09-28

## Generate a symmetric key

```
xkmsctl key generate my-secret --key-type symmetric --algorithm aes256-gcm
```

AES-128/192/256-GCM, ChaCha20-Poly1305, and XChaCha20-Poly1305 are all
supported; only the AES-GCM sizes appear in `--algorithm`'s own help text —
see [`cli.md`](cli.md) for the exact wire strings the other two need.

## Encrypt and decrypt

```
xkmsctl key encrypt my-secret "hello world" --aad "context-string"
```

Save the printed ciphertext, nonce, and tag — all three are required to
decrypt:

```
xkmsctl key decrypt my-secret <base64-ciphertext> --aad "context-string" --nonce <base64-nonce> --tag <base64-tag>
```

`--aad` (additional authenticated data) must match between encrypt and
decrypt, or decryption fails authentication.

## AES-CBC, AES-ECB, and a non-default tag size

These are not reachable from `xkmsctl` today — only the default AEAD mode
has a CLI verb. If your workload genuinely needs CBC (e.g. interop with a
PKCS#11 client that only speaks `CKM_AES_CBC`), you have two options:

- Call the REST/gRPC/QUIC/MCP encrypt/decrypt endpoint directly, setting
  `mode` to `"cbc"` or `"cbc-pad"` and supplying `iv` — see
  [`api.md`](api.md).
- Use the embedded Go SDK and call `SymmetricEncrypter.Encrypt` with
  `types.EncryptOptions{Mode: types.CipherModeCBC, IV: ...}` directly.

**AES-ECB is implemented for PKCS#11 v3.2 conformance
(`CKM_AES_ECB`) and is deterministic** — identical plaintext blocks produce
identical ciphertext blocks under the same key. Do not select it for
anything where that structure leak matters; it exists to answer an explicit
protocol requirement, not as a general-purpose cipher mode.

## Key rotation

```
xkmsctl key rotate my-secret
```

Rotation generates a fresh key under the same key ID and resets that key's
nonce-reuse history and byte counter. The AEAD safety tracker's state is
**in-memory only** (see below) — after a server restart, tracking for every
key (rotated or not) starts over regardless of rotation.

## Supplying your own nonce

Leave the nonce empty and let the server generate it. If a protocol requires
you to choose it, use each nonce once per key: the server refuses a second
encryption under the same key and nonce, including a nonce it generated for
someone else's ciphertext. That record is kept in the server's memory. It is
lost when `xkmsd` restarts and is not shared between cluster nodes, so the
guarantee does not span restarts yet.

## Operational note: AEAD safety tracking does not survive a restart

go-xkms's only AEAD-safety tracker implementation keeps nonce-reuse history
and byte counters in memory. A restarted `xkmsd` process has forgotten every
nonce it has ever used and every byte it has ever encrypted with every key.
This does not make a re-used nonce safe — the underlying cryptography is
unaffected — but it does mean the *detection* mechanism that would catch a
reused nonce, or warn before a key exceeds its NIST SP 800-38D byte budget,
resets on every restart. If your deployment encrypts high volumes with a
long-lived symmetric key across process restarts, rotate keys on a schedule
well inside the 350GB default limit rather than relying on the tracker to
warn you close to it.

## FIPS-mode deployments

Under `GODEBUG=fips140=only`:

- AES-GCM keeps working for every key size, but the server can no longer
  honor a caller-supplied nonce: `EncryptRequest.nonce` must be left empty,
  and the response's nonce is generated by the module itself. A request
  that supplies its own nonce under `fips140=only` fails with
  `ErrArbitraryIVGCMUnavailable`.
- A non-default (truncated) `tag_size` also fails under `fips140=only`
  encryption, for the same reason: the substitute FIPS-only construction
  only produces the full 128-bit tag.
- ChaCha20-Poly1305 / XChaCha20-Poly1305 remain usable for
  `symmetric.Backend`'s own AEAD path (this backend does not force AES the
  way `pkg/crypto/aead.SelectOptimal` does elsewhere in the project) — but
  confirm against your own FIPS validation scope before relying on that in
  a certified deployment.
