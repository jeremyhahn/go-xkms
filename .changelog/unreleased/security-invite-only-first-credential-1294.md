- **A provisioned account's first passkey could be enrolled by anyone who knew its email, with no proof of possession; account creation now issues a single-use activation invitation instead, and enrollment of the first credential is authorized by redeeming it** (#1294 part B).
  - `pkg/webauthn.Service.BeginRegistration` — the public, unauthenticated WebAuthn registration entry point — previously enrolled the first passkey of ANY existing account that held zero credentials, including one an administrator had just provisioned through `CreateUser`. It now refuses every account that existed before the call, whatever its credential count; the only account it may still enroll a passkey for is one it creates itself in the same call, under open self-registration (`AllowPublicRegistration`).
  - `XKMSService.CreateUser` (`pkg/xkms/servicer_user.go`) now creates an email-login-key account `LifecyclePending`, not active, and mints a single-use activation invitation through go-qrdb's canonical `invite.TenantStore` in the same call — the plaintext token is returned exactly once (`transport.GetUserResponse.Invite`), never recoverable afterward. A mint failure rolls the account back. The certificate-only/bootstrap path (`WithoutEmailLoginKey`) is unchanged: created active, no invitation.
  - New invite-redemption entry points: `pkg/webauthn.Service.BeginInviteRegistration`/`FinishInviteRegistration` (require `LifecyclePending`, zero credentials) and `pkg/xkms.XKMSService.{GetInvite,BeginInviteRegistration,FinishInviteRegistration,ActivateInvitePIV}`, which bind the credential to the still-pending account, activate it, and redeem the invitation — in that order, so a failure at any step never leaves a redeemed invite pointing at an unactivated account or a live token on an already-active one. Every unusable token (absent, expired, already redeemed, malformed) answers with the one opaque `invite_unusable`/`ErrInviteUnusable` response.
  - These four are composed surface (`transport.InviteServicer`/`InviteService`, embedded into `transport.XKMSServicer`/`transport.Client`), so they are public/unauthenticated on **every** transport, not REST alone: REST (`/api/v1/invites/{tenant_id}/{token}`, `.../fido2/begin`, `.../fido2/finish`, `.../piv/activate`), gRPC and Unix (`KeystoreService.{GetInvite,BeginInviteRegistration,FinishInviteRegistration,ActivateInvitePIV}`, new deliberately-unannotated RPCs in `pkg/api/grpc/proto/xkmsv1/xkms.proto`, regenerated), QUIC (reuses the REST handlers over HTTP/3), and the embedded transport. MCP exposes `invite.get`/`invite.pivActivate` as ordinary public methods but excludes the FIDO2 Begin/Finish pair (`ErrIdentityCeremonyExcluded`), the same go-xkms#193 ruling already applied to `BeginRegistration`/`FinishRegistration`: MCP holds no state to correlate a Begin call with its Finish, and an agent-facing tool surface must not mint sessions or enroll credentials. `pkg/api/grpc/authz_proto_option_test.go`'s ungated-RPC golden register was updated for the four new RPCs.
  - New `xkmsctl user invite redeem <invite-link-or-token>` (`cmd/xkmsctl/user_invite.go`) redeems an invitation over `xkmsctl`'s default transport: FIDO2 (default) drives the local CTAP2 security key through the registration ceremony; `--method piv` activates with a presented PIV certificate. Replaces the REST-curl workaround previously documented in `docs/user-onboarding/cli.md`.
  - `transport.CreateUserRequest` gains `InviteTTLSeconds`; `transport.GetUserResponse` gains `Invite *InviteInfo` — propagated on every transport's `CreateUser` (REST, gRPC, Unix, QUIC, MCP, embedded); the gRPC/Unix wire gained `CreateUserRequest.invite_ttl_seconds` and `UserResponse.invite` (`pkg/api/grpc/proto/xkmsv1/xkms.proto`, regenerated).
  - New operator config section `invite:` (`public_base_url`, `default_ttl`, `max_ttl`) controls the invitation link and TTL bounds. The invite store works in xkmsd's **default** configuration through exactly ONE storage path, with no fallback (per the owner's standing "never use fallbacks without approval" rule): `pkg/server/server.go` wires `pkg/server.tenantPrefixedInviteStore` (`invite_store.go`, new; renamed from an earlier `fileInviteStore` once the fallback it existed to feed was removed) unconditionally, built on the same `createStorage` seam every other xkmsd subsystem's persistent metadata uses (the `pkcs11state` precedent), namespaced per tenant with `storage.NewPrefixBackend` over the existing `pkg/storage/kvadapter` bridge, using the qrdb SDK's own `qrdbsdk.NewInviteStore`/`InviteDAOStore` for every single-use/redemption semantic. An earlier revision tried `qrdbsdk.TenantInviteStore` over the embedded qrdb node's `StoreResolver` (available only with a configured barrier registry) first and fell back to a `createStorage`-backed store otherwise; that two-path design was removed as an unapproved fallback. `createStorage` itself becomes a prefixed, barrier-protected, replicated view over one shared qrdb datastore under go-xkms#1363, and this store moves with that change automatically. `CreateUser` fails closed (`xkms.ErrNotConfigured`) only if this one store's construction fails; that failure is not fatal to server startup.
  - `xkmsctl user register` and `xkmsctl admin create --method fido2` no longer drive a local FIDO2 ceremony inline (an administrator cannot enroll a passkey on an invitee's behalf); they create the account and print the activation invitation, redeemable with the new `xkmsctl user invite redeem`. The `--device`/`--timeout`/`--user-verification`/`--pin*`/`--origin`/`--rp-id`/`--rp-name` flags were removed from both verbs. `xkmsctl admin create --method mtls` is unaffected.
