- **The Encrypt RPC's and the AES-GCM key wrap's caller-supplied-nonce reuse guard was in-memory only, so a restart forgot every claim it had made.** `pkg/xkms/servicer_crypto.go`'s `Encrypt` and `pkg/xkms/servicer_wrapkey.go`'s `wrapAESGCM` both already claimed a caller-supplied or provider-generated AES-GCM/ChaCha20-Poly1305 nonce through the shared, atomic `aead.SharedAEADNonceGuard` before sealing (closing the check-then-record race the per-key-provider `types.AEADSafetyTracker` cannot), but the guard's tracker was process memory: a restart, or a second `xkmsd` node in a cluster, had no way to see a claim another process had already made. PKCS#11 v3.2 §6.13.1–§6.13.2 (`CK_GCM_PARAMS` always takes a caller-supplied `pIv`; `CK_GCM_MESSAGE_PARAMS`'s `ivGenerator` makes the caller-supplied `CKG_NO_GENERATE` an explicitly supported alternative to the mandatory `CKG_GENERATE`) and KMIP v1.4 §3.6/§4.29 (`Random IV` is an opt-in server-generation request; the IV/Counter/Nonce otherwise travels in the client's request, and "the server does not store or otherwise manage" it) both permit a caller-supplied nonce as the default case, so the fix is a durable, atomic guard over that case, not removing caller-supplied nonces.
  - `aead.KeyNonceGuard` gained `PersistentNonceStore`, an optional durable backing consulted from a new `UseContext(ctx, keyMaterial, nonce)` method in addition to the existing in-memory tracker `Use` alone still checks. The persisted identity (`persistentEntry`) is deliberately NOT salted with the guard's own per-process random salt (used only for the in-memory tracker's `entry`): the same (key, nonce) pair has to derive the identical identity after a restart or on a different node, and a per-process salt would defeat that. `claimAEADNonceIn` (`pkg/xkms/aead_nonce_guard.go`, shared by `Encrypt` and the AES-GCM wrap) now calls `UseContext` instead of `Use`.
  - New package `pkg/aeadnonce` implements `aead.PersistentNonceStore` over a `storage.Backend`, mirroring `pkg/pkcs11state`'s and `pkg/staticpw`'s existing thin-namespacing-wrapper pattern rather than adding a new storage mechanism: the claim is `storage.Backend.PutIfAbsent`, so it inherits whatever durability and, with `Storage.Backend: qrdb`, cluster-wide replication the configured backend already provides. `pkg/crypto/aead` itself still takes no dependency on `pkg/storage` or qrdb, so the PKCS#11 module — a cgo-loaded client library with no reason to carry either — is unaffected; its own in-process claim (`guardGCMNonce`) still calls the unchanged `Use`.
  - `pkg/server`'s new `initializeAEADNonceStore` builds the store (via the same `createStorage` seam every other durable subsystem uses) and attaches it to the process-wide `aead.SharedAEADNonceGuard` at startup; the new `detachAEADNonceStore`, called from `shutdown()`, removes it again so the package-singleton guard is never left pointing at storage a stopped server has closed.
  - The previously-existing, per-key-provider `types.AEADSafetyTracker` (`CheckNonce`/`RecordNonce`) is unchanged: it remains the only guard for a caller that embeds a `symmetric.Backend`/`quantum.QuantumBackend` directly rather than through `XKMSService`, so it was not removed as dead code. See `docs/symmetric-aead/engineering.md`'s "What is absent" for why that remains a separate, tracked gap.
