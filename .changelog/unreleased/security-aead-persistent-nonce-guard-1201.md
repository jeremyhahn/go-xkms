- **The Encrypt RPC's and the AES-GCM key wrap's caller-supplied-nonce reuse guard was in-memory only, so a restart forgot every claim it had made.** `pkg/xkms/servicer_crypto.go`'s `Encrypt` and `pkg/xkms/servicer_wrapkey.go`'s `wrapAESGCM` both already claimed a caller-supplied or provider-generated AES-GCM/ChaCha20-Poly1305 nonce through the shared, atomic `aead.SharedAEADNonceGuard` before sealing (closing the check-then-record race the per-key-provider `types.AEADSafetyTracker` cannot), but the guard's tracker was process memory: a restart, or a second `xkmsd` node in a cluster, had no way to see a claim another process had already made. PKCS#11 v3.2 §6.13.1–§6.13.2 (`CK_GCM_PARAMS` always takes a caller-supplied `pIv`; `CK_GCM_MESSAGE_PARAMS`'s `ivGenerator` makes the caller-supplied `CKG_NO_GENERATE` an explicitly supported alternative to the mandatory `CKG_GENERATE`) and KMIP v1.4 §3.6/§4.29 (`Random IV` is an opt-in server-generation request; the IV/Counter/Nonce otherwise travels in the client's request, and "the server does not store or otherwise manage" it) both permit a caller-supplied nonce as the default case, so the fix is a durable, atomic guard over that case, not removing caller-supplied nonces.
  - `aead.KeyNonceGuard` gained `PersistentNonceStore`, an optional durable backing consulted from a new `UseContext(ctx, keyMaterial, nonce)` method in addition to the existing in-memory tracker `Use` alone still checks. The persisted identity (`persistentEntry`) is deliberately NOT salted with the guard's own per-process random salt (used only for the in-memory tracker's `entry`): the same (key, nonce) pair has to derive the identical identity after a restart or on a different node, and a per-process salt would defeat that. `claimAEADNonceIn` (`pkg/xkms/aead_nonce_guard.go`, shared by `Encrypt` and the AES-GCM wrap) now calls `UseContext` instead of `Use`.
  - New package `pkg/aeadnonce` implements `aead.PersistentNonceStore` over a `storage.Backend`, mirroring `pkg/pkcs11state`'s and `pkg/staticpw`'s existing thin-namespacing-wrapper pattern rather than adding a new storage mechanism: the claim is `storage.Backend.PutIfAbsent`, so it inherits whatever durability and, with `Storage.Backend: qrdb`, cluster-wide replication the configured backend already provides. `pkg/crypto/aead` itself still takes no dependency on `pkg/storage` or qrdb, so the PKCS#11 module — a cgo-loaded client library with no reason to carry either — is unaffected; its own in-process claim (`guardGCMNonce`) still calls the unchanged `Use`.
  - `pkg/server`'s new `initializeAEADNonceStore` builds the store (via the same `createStorage` seam every other durable subsystem uses) and attaches it to the process-wide `aead.SharedAEADNonceGuard` at startup; the new `detachAEADNonceStore`, called from `shutdown()`, removes it again so the package-singleton guard is never left pointing at storage a stopped server has closed.

- **A second, non-atomic nonce guard still existed alongside the one above, and it was the only one protecting a caller that never went through `XKMSService`.** The per-backend `types.AEADSafetyTracker` (`CheckNonce`/`RecordNonce`, one instance per `symmetric.Backend`/`azurekv.Backend`/`pkcs11.Backend`/`tpm2.TPM2`/`quantum.QuantumBackend`) checked and recorded in two separate steps under an `RWMutex` — a TOCTOU race two concurrent callers could both win — and knew nothing about a key generated by an earlier process or reachable under a second name, backend instance, or an `sdk/go`/`xkey` caller that constructs a backend directly rather than through the service: that caller never reached the durable guard above at all.
  - `types.AEADSafetyTracker` (`pkg/types/types.go`) lost `CheckNonce`/`RecordNonce` entirely; it now covers only the NIST SP 800-38D bytes-encrypted budget, which is a genuinely separate, per-backend-instance concern the durable guard does not and should not replace. `backend.NewMemoryAEADTracker` (`pkg/backend/aead_tracker.go`) lost its nonce map accordingly.
  - New `pkg/backend/aead_nonce.go` adds `ClaimAEADNonce`/`ClaimGeneratedAEADNonce` (plus `...In` variants taking an explicit guard, for tests): the single point every backend's `Encrypt` now calls, atomically, immediately before `Seal` — the software symmetric backend, Azure Key Vault, PKCS#11, TPM2, and the quantum KEM hybrid encrypter alike. This is the lowest layer common to a request reached through `XKMSService` and one reached by a caller holding a `Backend` directly, so both are now covered by the one shared, optionally-persistent `aead.SharedAEADNonceGuard`. The key identity (`aeadNonceIdentity`) prefers a key's own material wherever the backend already has it in hand for the encryption itself (software symmetric, Azure Key Vault, and TPM2's software AES-GCM path, which unseals the key into process memory for exactly this call) — so the same physical key reached under two names or two instances collides on one guard entry — and falls back to `sealedAEADKeyDomain + attrs.ID()` only for PKCS#11, whose key material never leaves the token at all. `ClaimGeneratedAEADNonce` preserves the one policy difference the old service-layer code had: it tolerates a full guard (a provider-generated nonce is fresh by construction and cannot itself be a repeat), while `ClaimAEADNonce` does not.
  - `pkg/xkms/servicer_crypto.go`'s `Encrypt` and `pkg/xkms/servicer_wrapkey.go`'s `wrapAESGCM` no longer claim anything themselves — `pkg/xkms/aead_nonce_guard.go` (`claimAEADNonce`, `claimGeneratedAEADNonce`, `aeadKeyIdentity`) is deleted. Keeping it alongside the new backend-layer claim would have claimed the same pair twice for every request reached through the service, refusing the first, legitimate call as a false reuse.
  - `backend.ErrNonceReused` is now an alias for `aead.ErrNonceReuse` (was a distinct `errors.New`), so `errors.Is(err, backend.ErrNonceReused)` keeps matching what the guard actually returns.
  - AWS KMS, GCP KMS and Vault Transit were investigated and found out of scope: none of the three ever called `CheckNonce`/`RecordNonce` — each refuses a caller-supplied nonce outright (`ErrCallerNonceNotSupported`) because their remote encryption service manages nonce generation itself, so there is no local (key, nonce) pair for this guard to claim.
