- **The Azure Key Vault backend now uses Azure's native BYOK (bring-your-own-key) flow instead of unwrapping key material locally** (#1342). `pkg/backend/azurekv.Backend.ImportKey` used to unwrap the caller's wrapped key material inside this process -- with a locally generated ephemeral RSA wrapping keypair -- and send the resulting plaintext private key to Azure Key Vault's `ImportKey` API as a standard JWK. That meant the target key's plaintext existed inside xkms, briefly, on every import.
  - `GetImportParameters` now provisions (once, and reuses on every later call) a vault-scoped RSA-HSM key-encryption key (KEK) with Azure Key Vault's `import` key operation, and returns its public half. `WrapKey` wraps the caller's key material client-side against that public key using `CKM_RSA_AES_KEY_WRAP` (RSA-OAEP-256 wraps an ephemeral AES-256 key, which wraps the target key material with AES-KWP) -- the wire format Azure Key Vault's `key_hsm` transfer field requires. `ImportKey` sends the wrapped blob to Azure Key Vault as the JWK `key_hsm` (`T`) field with `HSM: true`; Azure's own HSM performs the unwrap, using the KEK's private half, which never leaves the HSM boundary. `UnwrapKey` is now unconditionally `backend.ErrNotSupported` -- there is no local unwrap step left to perform.
  - The single-use import token from #1340/#1342's `pkg/backend/importtoken.Store` now binds each ceremony to the KEK's `kid` and the wrapping algorithm (a `kekBinding`, not a sealed local wrapping key): `ImportKey` refuses a token whose algorithm does not match `WrappedKeyMaterial.Algorithm`, and refuses one whose KEK has since been rotated or recreated, before ever presenting a doomed blob to Azure.
  - Plain RSA-OAEP wrapping (with no AES-KWP layer) is no longer accepted by `GetImportParameters`/`WrapKey`: it is not a valid Azure Key Vault `key_hsm` encoding on its own.
