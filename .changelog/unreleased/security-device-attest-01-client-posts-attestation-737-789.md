- **`device-attest-01` followed neither the draft nor a deployable design: the server dialed the device, and the shipped `xkmsd` could not start with the challenge enabled** (#737, #789, #1370 review). Four changes, made together because each was a blocker for enrolling an AVR/DICE device.
  - **The client POSTs the attestation; the server never contacts the device (draft-ietf-acme-device-attest).** The client answers the challenge with the payload `{"attObj": "<base64url, unpadded, of the CBOR attestation object>"}` and the server verifies it from the payload. The dial path is removed: `challengePath`, the `validation.Client` parameter of `deviceattest01.Verify`/`VerifyAttestation`, and `startAttestServer` in the Go client are gone, `AttestationChallenge.DialTarget` and `Port` are empty for this challenge, and the loopback-identifier substitution applies to `enroll-01` and `endorse-01` only (`dialsDevice`). A device needs no listener and no address, so one on a serial port enrolls through a gateway holding the ACME account. **Breaking for callers of the package:** `VerifyAttestation(verifier, payload, keyAuth)` replaces `VerifyAttestation(client, verifier, host, port, token, keyAuth)`, `Verify` likewise, and `AttestationRequest` is `{AttObj string}` (`json:"attObj"`) in place of `{AttStmt []byte}`. New `ParseAttestationRequest` and `EncodeAttestationRequest`, and `ErrAttestationPayloadInvalid` naming the layer that failed. `ChallengeHandler` reads the payload from the verified JWS and hands it to the verifier as `AttestationChallenge.Payload`. Freshness is unchanged: the attestation must cover the key authorization (`TPMExtraData`, `DICENonce`). `EnrollmentConfig.IPAddress`, `Port` and `ListenHost` are unused by `DeviceAttest`, and `IPAddress` is no longer required for it.
  - **A production verifier: `deviceattest01.TrustAnchorVerifier`.** `xkmsd` with `acme.challenges.device_attest01` enabled aborted at startup because the shipped CA cannot implement `AttestationVerifier` (it would be an import cycle). The verifier is now built from configured anchors and injected: `handlers.NewDeviceAttestVerifier(verifier)` and `ACMEAttestingVerifiers(client, enroll, endorse, deviceAttest)` take it as an argument. A `tpm` chain is anchored to `tpm_roots` with `evidence.VerifyAKCertificate`; a `dice` chain to `dice_roots` with `dice.Verify` (nonce, `Ueid`, and the `dice_require_device_signed_leaf`/`dice_require_measurement`/`dice_require_tcb_info` policy). The root sets are separate and a format with no root is refused (`ErrNoTrustAnchors`). New config `acme.challenges.device_attest` (`tpm_roots`, `dice_roots`, `dice_require_*`); `device_attest01` with no anchor fails validation (`ErrACMEDeviceAttestNoAnchors`) and `xkmsd` refuses to start (`ErrACMEDeviceAttestAnchors`). `ErrDeviceAttestCAUnsupported` and `requireDeviceAttestCA` are removed. SDK: `ACMETrustAnchors`, `ACMEDICEPolicy`, `ACMETrustAnchorVerifier`, `ACMENewTrustAnchorVerifier`, `ACMEDeviceAttestRequest`, `ACMEParseDeviceAttestRequest`, `ACMEEncodeDeviceAttestRequest`, `ACMEDeviceAttestStatement`, `ACMEDICENonce`, `ACMETPMExtraData` and the sentinels `ACMEErrNoTrustAnchors`, `ACMEErrNoAttestationVerifier`, `ACMEErrAttestationPayloadInvalid`. The EK-to-manufacturer chain is not re-proven for `tpm` (the statement carries no EK); it is proven by whoever issued the AIK certificate, for a go-xkms CA by `enroll-01`.
  - **A missing authorization refuses finalize.** `deviceAttestations` skipped an order's referenced authorization that storage did not hold, so after a partial restore `refuseForeignRequestForAttestedOrder` read zero records as "not a device-attest-01 order" and let a TCG-CSR or an `endorse-01` EK request through the key binding. `orderAuthorizations` now returns `ErrOrderAuthorizationMissing` (a `serverInternal` 500 problem) and the request is refused. SDK alias `ACMEErrOrderAuthorizationMissing`.
  - **The issued certificate asserts the attested identity.** The CA copies no otherName a CSR requests, so a device-attest-01 certificate carried no device identity. New `ca.SignOptions.OtherNames` (an issuer-asserted subjectAltName otherName, never copied from a CSR) lets finalize hand the CA the evidence-derived RFC 4043 `permanentIdentifier`. Available to SDK users through `TrustedCASignOptions`.
  - Verified by `TestChallengeHandler_DeviceAttest01_NeverDialsTheDevice`, `TestTrustAnchorVerifier*` (`anchors_test.go`), `TestStartACMEServer_DeviceAttestAnchors`, `TestOrderFinalize_MissingAuthorizationRefusesFinalize` (fails without the fix) and the client-to-server round trip `TestDeviceAttestRoundTripAgainstTheRealServer`, which no longer rewrites the dial target and runs against a server given no way to reach the device. Docs: `docs/acme/challenges.md`.
  - **Open:** the IAK certificates a go-xkms CA issues at `enroll-01` carry a subject, which WebAuthn section 8.3.1 (enforced by `checkAIKCertificate`) forbids in `x5c[0]`, so an `enroll-01` IAK certificate is not yet accepted by the `tpm` format. `dice` is unaffected. Reconciling the profiles is a decision for the owner.
  - Closes the device-attest-01 blockers of #737 and #789.
