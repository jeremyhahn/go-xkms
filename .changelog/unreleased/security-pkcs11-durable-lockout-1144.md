- **PKCS#11 PIN lockout is enforced against the token's shared counter, not each process's copy (#1144).** Before this change, `C_Login`, `C_LoginUser` and the old-PIN check in `C_SetPIN` checked the lockout against in-memory counters. The durable counter was read only after a failure. So N processes on one file or remote token each got the full `MaxPINAttempts` guesses. A process with a stale counter could also verify the correct PIN after the shared counter read LOCKED, and its success then reset the counter and cleared the lock. Now every verification spends its attempt first. It goes through a guarded spend on the durable counter (`ModuleStorage.SpendFailedAttempt`), which uses `PutIfAbsent` plus a `CompareAndSwap` retry loop, reaching `PKCS11StateCAS` for remote tokens. The spend refuses once the budget is exhausted, and nothing is derived after a refusal. A wrong PIN leaves its attempt spent. A correct PIN refunds it: the counter resets only if nothing else touched it since the spend. Otherwise only the caller's own charge is returned, so a success never erases another process's failure or lock. An error from the store now fails the login with `CKR_DEVICE_ERROR` and grants nothing. Before, the module fell back to the local counter. `C_InitToken`, `C_InitPIN` and `C_SetPIN` report `CKR_DEVICE_ERROR` when the counter reset does not reach the store. The in-memory counters are now only a cache for the `CKF_*_PIN_*` token flags. Remaining gap: on a file-backed token, the file engine's compare-and-swap is atomic only within one process.
