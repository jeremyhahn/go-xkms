- **`device-attest-01` never bound the attested key to the certificate request's key, and no attestation challenge bound the attested device's identity to the order's authorized identifier** (#789, #828). `deviceattest01.VerifiedAttestation.BindCSRKey` existed but nothing in the ACME server called it, so a permanent-identifier order's finalize request signed any CSR; and a client could complete an attestation challenge with device A while claiming device B's identifier.
  - **Owner ruling on #828, option B: an optional, additive attesting-verifier interface.** `common.ChallengeVerifierFunc`, `Params.ChallengeMap` and the existing SDK functions are unchanged, and `http-01`, `dns-01` and `tls-alpn-01` are untouched. New `common.AttestingVerifier` (`VerifyAttested(resolver, ca, AttestationChallenge) (*AttestedIdentity, error)`, plus the `AttestingVerifierFunc` adapter) returns the attested identity and the `*entities.DeviceAttestation` to persist. Attestation verifiers register in the new `Params.AttestingVerifiers`; `sdk/go/acme.ACMEAttestingVerifiers` builds the map and `cmd/xkmsd/acme.go` registers it.
  - **`ChallengeHandler` fails closed for `enroll-01`, `endorse-01` and `device-attest-01`.** A type with no attesting verifier is refused (`unauthorized`), even if a plain `ChallengeVerifierFunc` is registered for it, and is not offered to clients. An `ip` identifier is refused (`unsupportedIdentifier`, `ErrAttestationIdentifierType`) without running the verifier. A mismatch between the attested identity and the order's identifier (constant-time compare) is `unauthorized` (`ErrIdentityMismatch`, never shown to the client). There is no `device-attest-01` special case in the handler.
  - **Identity per type.** `device-attest-01`: the AIK certificate's RFC 4043 `permanentIdentifier` for `tpm` (an AIK without one is refused), the TCG `Ueid` for `dice`. `enroll-01` and `endorse-01` implement the interface but attest possession, not a name, and report the order's own identifier, so their identity comparison is a tautology today; see Open below.
  - **Persistence and finalize.** The verified evidence is persisted on the challenge (`entities.ACMEChallenge.DeviceAttestation`) through the existing DAOs. `OrderFinalizeHandler` refuses with `badCSR` a CSR whose key is not the attested key, and fails closed (`badCSR`) when no attestation record exists.
  - **Behavior change: `"ip"` has no default challenge candidates.** `enroll-01` and `endorse-01` are removed from the default `"ip"` list (`xkmsDefaultIdentifierChallengeTypes`) because attestation never authorizes an `ip` identifier. A new-order for an `ip` identifier is refused up front as `rejectedIdentifier` with a 400 (`ErrIPIdentifierNotValidatable`) when the policy offers no non-attestation challenge for `ip`; an operator who sets `IdentifierChallengeTypes` for `ip` to http-01 or similar keeps that path. Devices authorize with `permanent-identifier`, which is what `acme-client` and the cluster joiner send.
  - **Behavior change: attestation verifiers registered only through `ChallengeMap` are refused.** `sdk/go/acme.ACMEAttestationVerifiers` is kept for source compatibility and marked Deprecated; its output is refused for attestation types. Callers move to `ACMEAttestingVerifiers`. `pkg/acme/client` gains `WithAttestingVerifiers`.
  - `device-attest-01` also emits the `DEVICE_ATTESTATION` audit event on success, gated like the other attestation events. New config flag `acme.challenges.device_attest01`. Typed errors: `ErrAttestationIdentifierType`, `ErrAttestingVerifierRequired`, `ErrAttestationNoIdentity`, `ErrIdentityMismatch`, `ErrDeviceAttestationNotFound`, aliased in `sdk/go/acme`. `sdk/go/acme.ACMEAttestingVerifiers` takes the device-attest-01 trust policy as an `ACMEDeviceAttest01Verifier` (nil leaves the challenge unregistered) rather than asserting it from the CA handle.
  - **Open (go-xkms#828):** the cluster SPIFFE hook (`NewPermanentIdentifierURISANHook`) still stamps the order's client-declared `permanent-identifier`; and the `enroll-01`/`endorse-01` identity comparison does not yet bite. Both need `enroll-01`'s order identifier separated from the address the server dials, and a source of truth mapping an attested device to its Raft address.
  - #737 (wire device-attest-01) is deployable: the client POSTs its attestation and `xkmsd` builds a production verifier from configured trust anchors; see `security-device-attest-01-client-posts-attestation-737-789.md`.
