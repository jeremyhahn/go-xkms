- **With a user store configured, the mTLS authenticator now fails closed: a client certificate that does not resolve to a bound, enabled qrdb user never authenticates.** `pkg/auth/mtls.go` `buildIdentity` used to treat every `UserStore.GetByCertFingerprint` error the same way. Whether the certificate was unbound or the store could not answer (a sealed tenant barrier, a failed index read, an unreachable remote), it built an identity from the certificate's own fields: `Subject` from the CN, `TenantID` from the first OU, and no roles. While the store was unavailable, an account the store would have refused (disabled, or with its binding withdrawn) came through as a certificate identity. Even with the store healthy, any certificate from a trusted client CA authenticated under a Subject and tenant its holder chose. With RBAC enabled the gate still denied such a role-less identity. With RBAC disabled, nothing else checks it, and handlers that scope per-user state on `(TenantID, Subject)`, such as the REST and MCP password vault, would serve the store of the user whose name matched the CN. The authenticator now refuses an unbound certificate with `auth.ErrCertNotBound`, recognized by qrdb's typed `UserNotFoundError`, and returns every other store error as `*auth.UserLookupError`. The certificate-field identity remains only for an authenticator built without a store, which is used when no qrdb identity plane is hosted. Behaviour change: on a qrdb-backed daemon, a trusted client certificate must be bound to a user to authenticate, even with `auth.enable_rbac: false`. On the ACME admin plane an unbound certificate is now answered 401 at authentication instead of 403 at the gate (go-xkms#1096).
