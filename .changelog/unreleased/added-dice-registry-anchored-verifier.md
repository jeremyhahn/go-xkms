- **ACME `device-attest-01` anchors DICE devices in their provisioning record** -- a DICE alias certificate is signed by the key it carries, so on its own it vouches for nothing. `TrustAnchors.Devices` now takes a `DeviceResolver` that returns a device's provisioning record, keyed by the UEID as 34 lowercase hex digits. A record that holds a raw DeviceID key accepts an alias only if the alias carries that key and its signature verifies under it. A record that holds a DeviceID certificate accepts an alias only if the certificate names the same UEID and `[alias, DeviceID certificate]` anchors in `dice_roots`. The DICE claims are checked only after that. If there is no resolver or no record (`ErrDeviceNotProvisioned`), the lookup fails, or the record does not vouch for the key, the device is refused as `unauthorized` (`ErrDeviceNotAuthorized`). `dice_roots` alone no longer authorize any device, and a stock `xkmsd`, which injects no resolver, refuses every `dice` attestation. The key the record vouched for is persisted with the challenge as `AttestedSPKI`. At finalize, a request without it, or a CSR whose SPKI is not byte-equal to it, is `badCSR`. The registry is queried again at finalize, and a device withdrawn or re-keyed since its challenge is `unauthorized`. The resolver types and sentinels are re-exported in `sdk/go/acme` with the `ACME` prefix.
