CI: the PKCS#11 module integration suites reach the compose `xkms-server` the readiness step unsealed. `scripts/start-test-xkmsd.sh` used to unlink the socket in the shared volume whenever a single probe missed it, which left the running server listening on a deleted file, so every later dial reported the unix protocol unreachable. While the compose server runs, the script now waits for its socket, and if the socket never answers it fails with what the devcontainer sees. It no longer replaces that server's socket. When no compose server runs, the fallback starts xkmsd the supported way, with no secret in its config: `xkmsd init` with the SO PIN in the environment, then the daemon, then an unseal through `open-server-barrier.sh`. The web-console and ACME Playwright harnesses drop the removed `barrier.passphrase` key the same way, and the web tier waits for `/health` instead of the sealed window's port. A script test covers the fallback and the compose-server cases (DS-3769).

CI: the PKCS#11 module integration suite passes against the unsealed xkms-server. The harness kept its per-test token stores inside the base store directory, which the file engine then refused to open, so every C_Initialize on the base path failed with `CKR_DEVICE_ERROR`; the per-test stores now sit beside it. The suite's direct daemon client presents the module's TLS credential to the TLS-only socket. C_WrapKey with CKM_AES_GCM now returns the wrapped key followed by its tag, and C_UnwrapKey takes the IV from CK_GCM_PARAMS.pIv (PKCS#11 v3.2 §6.13.3). The module used to return the key service's `mode || nonce || ciphertext || tag` frame, which only this module could unwrap. A CKM_AES_GCM C_WrapKey without the 12-byte pIv fails with `CKR_MECHANISM_PARAM_INVALID`. The imported-KEK oracle and the conformance suite's in-memory key service unwrap with the wrap's IV, and the wrap tests read CKA_VALUE from the sealed `Attribute.Secret` the module returns it in (DS-3769).

CI: `ensure-server-ca.sh` no longer trusts the compose xkms-server's CA on first use. If no verified server serves one, the suite stops with a message instead of running on with no CA. Without the compose server it publishes the CA and admin credential of the server `scripts/start-test-xkmsd.sh` started, fetched the same verified way from its loopback REST port, so the module's `XKMS_PKCS11_TLS_CERT` and `XKMS_PKCS11_TLS_KEY` exist (DS-3769, DS-3754). CI: the Go integration harness (`test/integration/xkmsdtest`) opens an xkmsd node that is already unsealed. `OpenBarrier` read `/v1/barrier/status`, which the unsealed server refuses with 401, and `SealedWindowClient` trusted only the bootstrap certificate, which the CA-issued certificate the server swaps to does not chain to. The client now verifies the node against the bootstrap certificate and `unified-tls/ca-bundle.pem`, read afresh on each connection, and `OpenBarrier` treats an answering `/health` as an unsealed node, as `open-server-barrier.sh` does. PKCS#11: C_WrapKey, C_UnwrapKey, C_WrapKeyAuthenticated, C_UnwrapKeyAuthenticated, C_EncapsulateKey and C_DecapsulateKey refuse a key whose CKA_WRAP, CKA_UNWRAP, CKA_ENCAPSULATE or CKA_DECAPSULATE is false with `CKR_KEY_FUNCTION_NOT_PERMITTED` (PKCS#11 v3.2 §5.1.6, §5.1.7), as C_DeriveKey already did for CKA_DERIVE. They used to answer with a key-type code, which §5.1.6 reserves for a key of the wrong type for the mechanism. The conformance suite now expects `CKR_SESSION_READ_ONLY_EXISTS` for an SO login while a R/O session is open (§5.6.8) and `CKR_SESSION_READ_ONLY` for a token object created in a R/O session (§5.7.1). It also tests the unsupported-KDF refusal of CKM_ECDH1_DERIVE with a KDF the module does not implement, not with CKD_NULL, which §6.3 defines (DS-3769).

The process it left active made the next C_MessageVerifyInit fail with `CKR_OPERATION_ACTIVE`. The test now pins `CKR_OPERATION_NOT_INITIALIZED` for C_VerifyMessage without an init and `CKR_SIGNATURE_INVALID` or `CKR_SIGNATURE_LEN_RANGE` for a bad signature (§5.16.2) (DS-3769).
PKCS#11 conformance: the C_GetMechanismInfo test counts every operation flag PKCS#11 v3.2 §3.5 defines for CK_MECHANISM_INFO, including CKF_ENCAPSULATE and CKF_DECAPSULATE, so CKM_ML_KEM is no longer reported as advertising no operation. The protection-attributes test reads a generated key's CKA_VALUE through `Attribute.ValueLen`, because the module returns a backend-held key's value sealed in `Attribute.Secret` (DS-3769).

PKCS#11 C ABI suite: three tests now follow PKCS#11 v3.2, and the module already did. The message-signing test expects C_MessageSignInit to return `CKR_OPERATION_ACTIVE` after a refused C_SignMessage, because a failed C_SignMessage does not end the message-based signing process (§5.14.2). The new test asserts that change is refused with `CKR_ATTRIBUTE_READ_ONLY` (Table 105 gives CKA_VALUE no footnote 8; §5.7.6) and that the wrap fits its predicted length. The Security Officer now creates the CKA_TRUSTED wrapping key (Table 13 footnote 10). The error-name table names both return codes (DS-3769).
PKCS#11 pkcs11-tool suite: the wrap round trip generates its wrapping key with `--usage-wrap`. A bare `pkcs11-tool --keygen` puts only CKA_ENCRYPT and CKA_DECRYPT in the template. PKCS#11 v3.2 §4.11 gives CKA_WRAP no default, so the default is token-specific: SoftHSM2 sets it to CK_TRUE and the module sets it to CK_FALSE. C_WrapKey therefore refused the key with `CKR_KEY_FUNCTION_NOT_PERMITTED` (§5.18.3) (DS-3769).
PKCS#11 pkcs11-tool multiprotocol suite: the ECDSA sign steps choose their key by `--id`. For `--sign`, OpenSC 0.26.1 pkcs11-tool ignores `--label`. It sends C_FindObjectsInit with only `CKA_CLASS=CKO_PRIVATE_KEY` and signs with the first private key the token returns. On the shared token that key was RSA, so the module correctly refused CKM_ECDSA with `CKR_KEY_TYPE_INCONSISTENT` (PKCS#11 v3.2 §5.1.6, §6.3.12). Each key pair is now generated with a CKA_ID taken from its label, and signing selects it by that ID.
