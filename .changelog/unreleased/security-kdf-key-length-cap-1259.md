- **A caller-chosen KDF `key_length` had no upper bound, so a single `DeriveKey` or `DeriveKeyECDH` request could task the server with a multi-gigabyte allocation** (#1259). `types.KDFParams.Derive` checked only that `KeyLength` was positive, and `types.DeriveFromKeyMaterial` — the entry point `DeriveKey`'s raw-input-key-material path and every backend's stored-symmetric-key derivation actually call — checked nothing at all. Neither of the two KDF constructions this reaches bounds a caller-chosen length on its own: the ANSI X9.63 / NIST SP 800-56A concatenation KDFs accept requests up to 2^32 hash blocks and preallocate `reps*hash.Size()` before deriving a single byte, and NIST SP 800-108 accepts requests up to roughly 512 MiB. A request naming `key_length: 100000000000` reached one of those adapters and asked it to preallocate roughly 100 GB.
  - New exported `types.MaxDerivedKeyLength` (1024 bytes, covering the largest key or MAC this service ever derives) is the single ceiling, checked in `types.KDFParams.Derive` (both the bridge-dispatched algorithms and the raw/CKD_NULL pass-through) and `types.DeriveFromKeyMaterial`, so every derivation path — `DeriveKey`'s raw-material and stored-key forms, and every backend's `DeriveKeyECDH` — is capped at the same two choke points regardless of which algorithm or backend it reaches. A new sentinel, `types.ErrKeyLengthTooLarge`, reports the refusal; `KDFParams.Validate` was already checking the same bound for its bridge-dispatched algorithms (against an uninformative bare-`1024` literal) but not for the RAW algorithm, which is fixed too.
  - `pkg/crypto/kdf` itself keeps only the ceiling each construction's own wire format requires (2^32 blocks, ~512 MiB, HKDF's RFC 5869 255×HashLen bound via the standard library) rather than a caller-facing capacity policy of its own; `pkg/types` is documented as the gate anything taking a length from an untrusted request must go through.
  - The service layer (`XKMSService.DeriveKey`, `DeriveKeyECDH`) now refuses an oversized `key_length` as request validation, before any backend or key lookup, so it surfaces as `InvalidArgument`/400/Invalid-params on gRPC, REST and MCP alike, the same way every other malformed KDF field on these two operations already did.
  - The PKCS#11 module's `CKA_VALUE_LEN` (both the generic `C_DeriveKey` template and `CKM_ECDH1_DERIVE`'s template) and every other caller of `DeriveKey`/`DeriveKeyECDH` reach the same gate: they all route through the transport request these two service methods validate, so no separate cap was needed there.
