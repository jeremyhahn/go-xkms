- **The unauthenticated WebAuthn routes revealed which emails have accounts; login begin now answers unknown accounts with decoy options, registration refusals are uniform, and the status probe is gone** (#1296).
  - `POST /api/v1/webauthn/login/begin` answered an unknown email with 404 and a known one with 200, an `X-User-Id` header and the account's credential IDs. It now calls `Service.BeginLoginForEmail` / `BeginLoginForHandle`, which answer an unknown email or user ID, or an account without credentials, with a real go-webauthn ceremony against a decoy account whose `allowCredentials` (one or two descriptors, realistic ID lengths and transports) are derived with HKDF-SHA256 (HMAC-based, stdlib `crypto/hkdf`) from a per-process key and the requested email or handle, so repeated probes see the same descriptors. The decoy session is stored like any other; finishing against it fails as `verification_failed` (a session whose handle resolves to no account is now a verification failure, not a 500). The webauthn configuration carries no server secret, so the key is drawn with `crypto/rand` in `NewService` and held only in memory: decoys differ across restarts and cluster nodes. The SDK and gRPC `BeginAuthentication` use the same method; `FinishAuthentication` no longer re-resolves the email (the session decides the account), so an unknown email fails exactly like a wrong assertion.
  - `X-User-Id` is removed: login begin no longer sets it, login finish no longer reads it, and CORS no longer allows or exposes it. The user ID arrives only in a successful finish response. Clients updated: the Go `pkg/webauthn/client` (`BeginResult.UserID` removed; `Available` now probes `/health`), the TypeScript SDK (`HEADER_USER_ID` and `WebAuthnCeremonyStart.userId` removed, `webAuthnFinishLogin` takes no user ID), `svelte-auth`'s `LoginPanel`, the Playwright RP spec.
  - `GET /api/v1/webauthn/registration/status` is deleted (handler, types, route, mount helpers, TS SDK `webAuthnRegistrationStatus`): it answered for any email whether it had a passkey, and no UI or client used it.
  - With public registration off, an unknown email and an account that already has a passkey are refused with one error, `ErrRegistrationRefused` (403 `registration_refused`, identical message on REST, SDK REST and gRPC), replacing `ErrPublicRegistrationDisabled` / `registration_disabled`. Known limitation, noted in code: a provisioned account with no passkey still gets 200 until go-xkms#1294 part B is ruled.
