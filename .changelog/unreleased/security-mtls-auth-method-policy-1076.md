- **The mTLS authenticator now enforces a user's permitted-authentication-method policy, so an account restricted to, say, FIDO2 can no longer sign in to the xkms planes with a client certificate.** go-qrdb's own auth middleware refuses an account whose `User.AuthMethods` is non-empty and does not name the method that authenticated. `pkg/auth`'s `QRDBUserStore` and `MTLSAuthenticator` resolved the user and its role but never read that field, so withdrawing mTLS from an account took effect on qrdb and failed open on xkms. `QRDBUserStore.GetByCertFingerprint` now projects the policy onto the new `MTLSUser.AuthMethods`, and `MTLSAuthenticator.buildIdentity` checks it after the enabled check through `checkAuthMethod`, which applies qrdb's `checkAuthMethod` contract unchanged and uses only the SDK (`qrdbsdk.MethodMTLS`, `qrdbsdk.NormalizeAuthMethods`). An empty policy states no restriction, so existing accounts are unaffected. The method name is normalized the way the store normalized the policy, and a name that does not survive normalization is refused. A refused account returns the new typed `*auth.AuthMethodNotPermittedError{Username, TenantID, Method, Permitted}` and is never admitted through the certificate-field fallback. `MTLSAuthenticator.Name` now returns `qrdbsdk.MethodMTLS` instead of a local literal. Files: `pkg/auth/{authmethod.go,errors.go,mtls.go,qrdb_userstore.go}`. Docs: `docs/rbac/engineering.md`. Verified by `pkg/auth/authmethod_test.go` (a FIDO2-only or WebAuthn-only account is refused over HTTP and gRPC; an account naming `mtls` and an account with no policy are admitted; normalization and blank-name cases) and `pkg/auth/qrdb_userstore_test.go`. go-xkms#1076.
