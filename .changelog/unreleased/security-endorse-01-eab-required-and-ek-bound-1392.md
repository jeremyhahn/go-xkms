- **`endorse-01` proved nothing and was unauthenticated by default: any ACME account could obtain an EK certificate for any public key** (#1392, #1370 review). The verifier returned `nil` unconditionally, the only control was External Account Binding, and EAB was off by default (every account was then authorized).
  - **EAB is required by default, failing closed.** `Params.EndorseEABOptional` waives it and its zero value requires it, so a server built with no setting fails closed; `Params.EndorseEABRequired` is kept for source compatibility and is deprecated. `acme.endorse_eab_required` is now a `*bool` read through `ACMEConfig.EndorseEABIsRequired`: unset means required. To waive it (a closed lab server only) set `endorse_eab_required: false` or `XKMS_ACME_ENDORSE_EAB_REQUIRED=false`; the server then logs a warning for every endorse-01 challenge. **Behavior change** for deployments that relied on the old open default.
  - **The EAB must name the EK it authorizes, and that is the attested identity.** `EndorseEABValidator` binds the EK by `deviceInfo.ekPublicKeyHash` (SHA-256 of the EK's PKIX DER in hex, optionally `sha256:`-prefixed as the admin API reference shows; the field existed and was documented for this but never read) and/or `endorse_device_id_meta_key`. A binding naming neither is refused (`ErrEndorseEABKeyNotBound`) because it authorizes its account for any key; a different EK is refused (`ErrEndorseEABKeyMismatch`). `ChallengeHandler` hands the EAB-authorized identity to the verifier (`AttestationChallenge.AuthorizedIdentity`) and the new `handlers.NewEndorseVerifier` reports it, refusing without one (`ErrEndorseNoAuthorizedIdentity`); the endorse-01 verifier no longer echoes the order's identifier. **Behavior change:** a batch binding that names no EK, previously accepted when EAB was required, is refused; register each device's EK with it. `endorse01.Verify` is deprecated.
  - **What kind of order it is comes from the challenge that validated it, in one decision.** Finalize classified an order as endorse-01 from the bytes of its identifier in two places (the checks and issuance), so a device-attest-01 identity that decodes as a public key was checked as a device order and then issued an EK certificate for the identifier's key. Both now follow the same decision, derived from the validated challenge.
  - **An endorse-01 authorization may finalize only the EK-certificate path.** The EK-certificate request now requires endorse-01 to be the only attestation challenge that validated the order (the converse of the #789 check, which only excluded device-attest-01), and an endorse-01-validated order cannot finalize a TCG-CSR-IDEVID, IDevID, cluster node or device-attest-01 certificate request (`ErrFinalizeRequestNotPermitted`, `badCSR`). Commit 36c830bd began this.
  - **No MakeCredential proof of possession.** It needs the server to reach the device (the order's identifier is the EK, not an address, so there is nothing to dial; the separation of identifier and address is the open question on #828) or a second request on the challenge, and either changes the protocol. EAB bound to the key is the control; documented in `docs/acme/challenges.md`.
  - SDK: `ACMENewEndorseVerifier`, `ACMEErrEndorseEABKeyNotBound`, `ACMEErrEndorseEABKeyMismatch`, `ACMEErrEndorseNoAuthorizedIdentity`, `AttestationChallenge.AuthorizedIdentity`. #1393 (SPIFFE) is out of scope.
  - Verified by `TestChallengeHandler_Endorse01_RefusedWithoutEABByDefault`, `TestChallengeHandler_Endorse01_AnotherEKThanTheBoundOneIsRefused`, `TestEndorseEABValidator_RefusesABindingThatNamesNoKey`, `TestOrderFinalize_EKCertificate_OnlyForAnEndorse01Order` and `TestOrderFinalize_TCGCSR_EndorseValidatedOrderIsRefused`, each failing without the fix; `TestNewRestService_EndorseEABRequiredByDefault` and `TestLoad_ACMEEndorseEABRequired`. Docs: `docs/acme/challenges.md`, `docs/acme-issuance/api.md`.
  - Closes #1392.
