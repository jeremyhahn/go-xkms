- **Possession request for DICE device-attest-01 finalize** -- a template-minting DICE device cannot encode PKCS#10, and its alias key is its static DeviceID key. So at finalize it now proves possession by signing a fixed CertificationRequestInfo whose one host-supplied input is `b = SHA-256(keyAuthorization)`, and the host wraps the signature. The template has an empty subject, a P-256 key and one `extensionRequest` attribute. That attribute holds a critical `subjectAltName` with the RFC 4043 `permanentIdentifier` otherName `hex(DeviceID)`, and a non-critical `tcg-dice-UCCS-evidence` whose `eat_nonce` is `b`. The challenge stays standard `device-attest-01` with ACME identifier type `permanent-identifier`. Finalize of a `dice` order now refuses, as `badCSR`, any request that is not the template, plus four cases that each have their own error: the signature does not verify (`ErrPossessionSignatureInvalid`), the key is not the attested key (`ErrPossessionKeyMismatch`), the nonce belongs to another order (`ErrPossessionNonceMismatch`), or the identifiers are not exactly the order's (`ErrPossessionIdentifierMismatch`). A `dice` order therefore names one device and nothing else. No requested extension, the UCCS evidence included, is copied onto the certificate. `acmeclient.DeviceAttest` mints the request for an `AttestedKey` whose new `Format` field is `FormatDICE`.
