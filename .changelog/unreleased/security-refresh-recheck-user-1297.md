- **Refresh-token rotation never re-checked the user, and disabling or deleting an account did not end its already-issued sessions** (#1297). `pkg/auth/token.Issuer.Refresh` rebuilt the identity solely from the refresh token's own claims (`identityFromClaims`) and minted a new access token from that snapshot; a user disabled or deleted after login kept refreshing indefinitely, on the stale roles it logged in with, until the refresh token's own long TTL expired. `handleAuthRefresh` (`pkg/api/rest/handlers_auth.go`) did no user lookup of its own, so this was the only enforcement point on the wire. `Issuer.Refresh` now re-checks the token's subject through an optional `token.UserResolver` before any rotation is attempted: refusal (account not `qrdbsdk.LifecycleActive`, deleted, or unresolvable) is `*UserRecheckFailedError`, mapped by the REST handler to the same generic 401 as every other refresh refusal, so a presented token never reveals *why* it was refused. On success the rotated access token carries the account's CURRENT roles, not the login-time snapshot — a role change now reaches the very next refresh. `pkg/auth.QRDBUserResolver` is the production resolver, resolving the qrdb-backed identity plane the same way `MTLSAuthenticator.userIdentity` does for an mTLS login.
  - **The subject's encoding is declared, never inferred.** mTLS and PIV logins mint a username subject; a WebAuthn passkey login mints the base64url 8-byte qrdb user handle instead (`pkg/webauthn.HandleFromUserID`). The first version of this fix had `QRDBUserResolver` try `GetUserByUsername` and, on not-found, fall back to decoding the subject as a handle — review caught that this lets a **deleted** mTLS/PIV account whose username happens to also be a valid base64url encoding of a *different, live* user's numeric id resolve the refresh to that other account: identity confusion and a privilege escalation, on the exact refresh path this issue exists to close. Every identity now carries a new `sub_kind` claim/metadata key (`auth.SubjectKindMetadataKey`, values `auth.SubjectKindUsername` / `auth.SubjectKindUserHandle`), stamped by every login path that mints a pair — `MTLSAuthenticator`/PIV's `handlePIVLogin` (serves both mTLS and PIV certificate logins) sets `"username"`; `WebAuthnTokenAdapter.identityFor` sets `"user_handle"` — carried through `addIdentityClaims`/`identityFromClaims` onto both token halves. `QRDBUserResolver.lookup` now switches on the declared kind and uses **only** the matching lookup; a not-found under that kind refuses outright, with no fallback to the other encoding. A missing, empty, or unrecognized `sub_kind` refuses with `*RefreshSubjectKindError` — pre-release, so a token minted before this field existed simply fails refresh (the user logs in again); there is no compatibility shim.
  - `token.RefreshStore` gained `RevokeBySubject(ctx, subject) error`, revoking every refresh-token family belonging to a subject exactly as `RevokeFamily` revokes one; implemented in both `MemoryRefreshStore` (in-process index scan under the existing lock) and `QRDBRefreshStore` (a `Scan` over the KV refresh prefix, since the store keeps no subject index, followed by `RevokeFamily` per distinct family found). `Issuer.RevokeBySubject` is the convenience wrapper. `pkg/xkms.XKMSService.DisableUser`/`DeleteUser` — the only places in xkms that change qrdb account lifecycle (`qrdbtransport.UserClient.DisableUser`/`DeleteUser`; `EnableUser` widens access and revokes nothing) — call it for both subject encodings a login could have minted (the username, and the base64url WebAuthn handle) once the qrdb lifecycle change has already succeeded, wired via a new optional `XKMSService.SetTokenIssuer`. This is unaffected by the `sub_kind` change: `RevokeBySubject` is still keyed by the raw subject string, matched against `Record.Subject`, not by decoding it. It is defense-in-depth, not the sole enforcement: it is best-effort (a revoke failure is logged, not returned, since the lifecycle change itself must not be rolled back) and only reachable when a session-token plane is wired (`SetTokenIssuer` called); the refresh-time re-check above is what still refuses an affected session either way, including for any lifecycle change that reaches qrdb through a path other than these two xkms methods.
  - gRPC and MCP carry no refresh verb of their own (grepped for one; none found), so REST's `/api/v1/auth/refresh` was and remains the only transport this reaches.
