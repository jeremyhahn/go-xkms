- **The public WebAuthn registration ceremony could add a passkey to any existing account; adding a passkey now requires a session authenticated as that account** (#1294, part A). `Service.BeginRegistration` looked the account up by the email in the request body and began a ceremony for it with no caller authentication, on `RouteAuthPublic` routes (`/api/v1/webauthn/registration/begin`, `/sdk/registration/begin`, gRPC `BeginRegistration`), so anyone who knew an email could enrol their own authenticator on that account and sign in as it. The public ceremony now enrols only an account's first passkey: an account holding one or more credentials is refused with the new `ErrRegistrationRefused` (403, code `registration_refused`; gRPC `PermissionDenied`). A further passkey is added through the new `POST /api/v1/webauthn/credentials/begin`, a `RouteAuthSession` route in `GroupWebAuthn`: `Handler.BeginAddCredential` reads the session identity (`auth.GetIdentity`), `webauthn.SessionAccountFromIdentity` maps it back to the account (base64url handle in the subject plus the `email` claim, the inverse of `WebAuthnTokenAdapter`), and `Service.BeginAddCredential` checks both name the same existing account (`ErrSessionAccountMismatch`, 403 `session_account_mismatch`) before beginning a ceremony that excludes the account's existing credentials. The account always comes from the session, never the request, so one user's session cannot reach another account. The ceremony finishes through the existing `registration/finish`. The legacy router now applies authentication to `RouteAuthSession` routes in `GroupWebAuthn` the same way it does in `GroupAuthSession` (one shared helper); the unified-server module needed no change.
  - Unchanged, pending go-xkms#1294 part B: an account with zero credentials (provisioned by an administrator) still enrols its first passkey through the public ceremony in both registration modes, and this is noted at the call site.
  - Client impact: `xkey auth register` (and any SDK/gRPC client) re-run against an account that already has a passkey is now refused with 403 `registration_refused`; there is no SDK-transport add-passkey verb yet — only REST. The TypeScript SDK gained `auth.webAuthnAddCredentialBegin()`; `svelte-auth`'s `RegisterPanel` shows one message for every 403 refusal. The Playwright RP ceremony spec adds its second passkey through the session route.
