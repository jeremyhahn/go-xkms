- **`xkmsctl frost keygen` in dealer mode wrote every participant's secret share to disk as plaintext hex** (#1337). Each exported package was a JSON file holding `secret_share` in the clear. The files were `0600` in a `0700` directory, but they exist to be carried to other machines, so the share was readable by anything that handled the file along the way. Each package is now encrypted to a recipient key that only its participant holds, and `frost import` decrypts it.
  - **Breaking**: dealer mode now needs `--recipient <participant-id>=<public-key-file>` for every participant, and writes a new file format: `key_id`, `participant_id` and `participant_name` as clear routing labels, plus `package`, a JWE compact serialization of the key package. Each participant first runs the new `xkmsctl frost recipient`. It creates an ECDSA P-256 recipient key in `<key-dir>/frost/secrets`, as encrypted PKCS#8 under the FROST passphrase, and prints the public key (optionally to `--public-key-file`) and its RFC 7638 thumbprint, `recipient_id`, for confirming with the dealer out of band. `frost import` refuses a package from an earlier build (`ErrFrostPackageNotEncrypted`), a package for another participant (`ErrFrostPackageRecipientMismatch`), a modified package (`ErrFrostPackageDecryptFailed`), and a `--key-dir` with no recipient key (`ErrFrostRecipientKeyMissing`). It stores nothing until the package has decrypted. Dealer keygen refuses a missing, duplicate, malformed or non-P-256 recipient, the same key given for two participants (one holder would get two shares), and `--recipient` in participant mode. Every recipient is checked before any share is generated. `ErrFrostPassphraseRejected` now names the local key store rather than the wrapping key, since it also covers the recipient key.
  - The encryption reuses the SDK's existing JWE helper (`pkg/encoding/jwe`): `ECDH-ES+A256KW` to the recipient key, with `A256GCM` content encryption, and the recipient thumbprint as the authenticated `kid`. All of it is FIPS 140-3 approved. Recipient keys were chosen over per-participant passphrases: the private key never leaves the participant, `import` needs no second secret beyond the FROST passphrase it already takes, and no new envelope format was needed. The CLI's store opener is split into `openFrostLocalStore` and `frostLocalStore.shareBackend`, so `import` and `recipient` share one passphrase and one PKCS#8 backend with the share verbs. The SDK re-exports `JWKThumbprintSHA256`.
