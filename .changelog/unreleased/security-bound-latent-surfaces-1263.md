- **Four surfaces not reachable from `xkmsd` today were still unbounded, so a future wiring or a standalone consumer of the affected packages would have inherited the gap** (#1263).
  - xkey's agent gRPC server (`xkey/pkg/agent/server.go`, binds `:9443`) took no `MaxConcurrentStreams`, keepalive enforcement policy, message-size cap, or connection timeout. It now builds its `[]grpc.ServerOption` through a new `grpcServerOptions` method carrying all four, with `Config` gaining `MaxRecvMsgSize`/`MaxSendMsgSize`/`ConnectionTimeout`/`MaxConcurrentStreams` (defaulted in `Validate`, mirroring `pkg/api/unix/grpc_server.go`'s option set) and a `KeepaliveEnforcementPolicy` (30s `MinTime`, `PermitWithoutStream: true` for the agent table's long-lived, bursty connections). The option-building code itself is not shared with `pkg/api/unix`: xkey's own `CLAUDE.md` requires it integrate only through `go-xkms/sdk/go`, never `pkg/*`, directly.
  - `pkg/acme/client/enrollment.go`'s enroll-01 and endorse-01 challenge-activation handlers (`startEnrollServer`, `startEndorseServer`) read `r.Body` with no size cap. Both now wrap the body in `http.MaxBytesReader` at `acmeserver.MaxRequestBodySize` (`pkg/acme/server`'s existing 256 KiB ACME request-body cap, already imported into this package by `trustedca.go`) before reading it, and answer 413 on an oversized body — the same pattern `pkg/acme/challenges/enroll-01/enroll01.go`'s `activateCredentialHandlerWithShutdown` already used.
  - `pkg/ca/ocsp.go`'s in-memory OCSP response cache was keyed on any requested serial number and never evicted, so a client probing distinct serials grew it without bound. `OCSPResponderConfig` gains `MaxCacheEntries` (default 10000, matching `pkg/acme/server/degradation`'s cache default); `cacheResponse` evicts expired entries first and then arbitrary ones (Go's randomized map iteration order) until back under the cap before inserting. Each entry's expiry is now `min(CacheTTL, the response's own NextUpdate)`, so a `CacheTTL` configured longer than `NextUpdate` can no longer keep serving a response RFC 6960 already tells relying parties to treat as stale.
  - `pkg/acme/api/server.MultiProtocolServer` was investigated, not changed, per instruction: nothing in the tree imports `go-xkms/pkg/acme/api/server` outside its own package. It is a `go-trusted-ca` migration artifact (`DefaultGRPCUnixPath`/`DefaultHTTPUnixPath` still name `trusted-ca` sockets) but is not abandoned — its constructor and `buildRouter` are wired against the *current* `pkg/acme/admin` interfaces (`admin.Service`, `admin.TenantService`, `admin.AuthHandler`, `admin.NewPermissionGate`, `admin.TenantAwareService.BarrierSvc()`), the same ones `cmd/xkmsd/admin.go`'s `finalizeAdminModule` already constructs for REST, and its gRPC authorization interceptor received a real fix under #743's own number. It is very likely the intended host for #743 (ACME admin over gRPC, QUIC and MCP); wiring it in still needs the `trusted-ca` socket-path defaults renamed and a decision on whether it gets its own dedicated listeners (as built) or mounts onto `xkmsd`'s existing unified mTLS listener the way REST does today.
