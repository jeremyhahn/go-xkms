- **The ACME admin API now confines a tenant administrator to its own tenant (#1225).** The permission gate binds the caller's own tenant as the request's target, so a tenant Admin's self-scoped grants passed it whichever tenant the request named, and the admin service did no binding of its own. A tenant-A administrator could therefore suspend or delete tenant B (`PUT /api/v1/tenants/B/status`, `DELETE /api/v1/tenants/B`), create tenants, list every tenant, create, change and delete tenant B's roles and users (directly, or under its own `/tenants/A/...` path by ID), revoke tenant B's ACME certificates, disable its accounts, and read every tenant's accounts, orders, certificates, statistics and the whole audit trail. The admin plane also gave qrdb no tenant context, so qrdb's own tenant enforcement treated every call as the system tenant's. The admin service now binds every tenant a request names (`bindTenantTarget`) on every `{id}`-scoped operation — lifecycle, CA hierarchy, EAB, roles, users — for every transport, and the REST handlers repeat the check before reading the body. A refusal reads exactly like a missing tenant (`404 Tenant not found`, gRPC `NotFound`), the #1112 convention. A role or user is checked against the tenant the path names before it is returned, changed or deleted; a foreign one is `404`, like a missing one, for every caller. `GET /api/v1/tenants` lists only the caller's tenant. `/admin` certificates, accounts, orders and stats are limited to the caller's tenant: its accounts (by the account's EAB-assigned tenant) and the certificates their orders were issued. Anything else is `404` on get, revoke and disable. Creating a tenant and reading the audit trail, which records no tenant, are platform-only and answered with the gate's own `403`. The authentication boundary now binds the caller's tenant as the qrdb context tenant. The system (platform) identity keeps its cross-tenant reach. `RequireTenant`/`RequireTenantScope` now refuse with the same not-found answer. A missing account or order is now `404` rather than `500`, and `GET`/`DELETE /api/v1/tenants/{id}/users/{userID}` answer `400` for a non-numeric user ID. Files: `pkg/acme/admin/tenant_binding.go`, `tenant_service.go`, `service.go`, `tenant_handlers.go`, `handlers.go`, `auth.go`, `authz.go`, `types.go`; the in-memory qrdb double (`pkg/acme/qrdb/memory_auth.go`) now returns qrdb's typed role/user not-found errors; `admin-api.yaml` documents the new `404`/`400` answers. Tests: `pkg/acme/admin/tenant_binding_test.go`, `cmd/xkmsd/admin_tenant_binding_test.go` (a real embedded qrdb node). **Remaining gap:** a tenant user's certificate does not yet authenticate on xkmsd's admin plane, because its thumbprint is looked up in the system tenant.
