- **Password vault key factors on every client: xkmsctl, the xkey CLI and GUI, and the web console through the xKey extension.** `pkg/vaulttoken` (`sdk/go/vaulttoken`) is the one client implementation: it finds a key factor's token in an xkms key backend (a PIV backend's slot 9d key, a PKCS#11 token, a TPM 2.0 key, a software key), self-tests it before enrollment (`SelfTest`: a token that cannot open a secret sealed to its own key is refused), builds the enrollment, and recovers a vault factor's secret (`Find`, `UnlockCredential`). xkmsctl: `password vault enroll|recover --key-factor piv|certificate|tpm` and `password unlock --key`, with a PEM key (`--key-file`, `--cert-file`), a PKCS#11 token (`--key-pkcs11-module`, `--key-pkcs11-token`, `--key-pin`; needs a `-tags pkcs11` build, the CGO-free release answers `ErrVaultPKCS11Unavailable`) or a TPM (`--tpm-keystore`, `--tpm-create` under the built-in platform policy). xkey CLI: the same `--key-factor` / `--key` over xKey's local key store (barrier password flags); xkey GUI: *Add key*, *Unlock with key*, recovery with a key. **Browser bridge:** the console's *Unlock with xKey* asks the xKey extension (window.postMessage), whose worker forwards the browser-attributed origin of the top frame over encrypted native messaging to xKey (new IPC `vault` message); xKey refuses any origin that is not the connected server's console (https on its WebAuthn relying party domain), refuses factors that are not in the vault it reads itself, asks the user to approve (`vault:browser_unlock_request`, two-minute timeout), and unlocks the vault itself over its own connection -- the page receives only `{unlocked: true}`, never a key or secret. Without the extension the console says the factor needs it (`XkeyExtensionUnavailableError`). xKey's local key-store backend configuration is shared between the GUI and the CLI (`config.KeyBackendConfigs`).
