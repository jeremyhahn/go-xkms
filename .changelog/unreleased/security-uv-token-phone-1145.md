- **The xkey FIDO2 authenticator no longer mints a `pinUvAuthToken` without user verification** (#1145). `authenticatorClientPIN` subcommand `0x06` (`getPinUvAuthTokenUsingUvWithPermissions`) treated a key backend's `HandlesUserVerification` capability as an implicit successful verification. The phone backend reports that capability, so with `xkey fido2 --backend phone` any local HID client could get a token carrying `cm`, `acfg` or `lbw` permissions and then enumerate or delete resident credentials or change authenticator configuration, without anyone being verified. The capability only means the phone's biometric gates its own `Sign` and `GenerateCredentialKey`. It is not a verification the authenticator can run on demand, and the pairing protocol has no verifiable "verify user" call. Subcommand `0x06` now returns `CTAP2_ERR_INVALID_SUBCOMMAND` for every backend, and the PIN path (`0x09`) is the only way to get a token. `getInfo` gates `FIDO_2_1`, `credMgmt` and `pinUvAuthToken` on the PIN alone, and advertises `uv=true` for a verifying backend only when no `pinUvAuthToken` surface is advertised. Under `xkey fido2` (credential management on, so PIN forced on) the phone backend now reports `uv=false`: the browser collects the PIN, and the phone still asks for the biometric on every signature. The backend's in-operation UV still sets the UV flag on the `makeCredential`/`getAssertion` it signed.
  - Files: `xkey/pkg/authenticator/{cmd_clientpin,cmd_getinfo,cmd_makecredential,cmd_getassertion}.go`, `xkey/pkg/authenticator/keybackend/keybackend.go`, `xkey/pkg/phone/phone.go`.
  - Verified by `TestGetPinUvAuthTokenUsingUvWithPermissions_RefusedWithUVBackend` (a well-formed `cm|acfg|lbw` request under both PIN/UV protocols is refused, mints no token and leaves UV retries alone), `..._RefusalKeepsPINToken`, `TestSupportsPinUvAuthToken` and `TestGetInfo_BackendUVNeverPromisesUvToken` (`uv=true` never appears next to `pinUvAuthToken=true`).
