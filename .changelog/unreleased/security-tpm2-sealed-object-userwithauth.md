- **A TPM2 object or NV index bound to the platform policy could be used without satisfying it.** Every keyed-hash object `pkg/tpm2` sealed, and every RSA, ECDSA and AES key it created, kept `userWithAuth` SET. Under TPM 2.0 the object's USER role then also answered its `authValue`. That value was empty when the object had no password, so a plain empty-password `TPM2_Unseal`, `TPM2_Sign`, `TPM2_RSA_Decrypt` or `TPM2_EncryptDecrypt2` worked on any platform state, never evaluating the PCR policy. An object with a password answered that password alone, outside the policy. Platform-policy NV indices had the same flaw through `TPMA_NV_AUTHREAD`/`AUTHWRITE` and their always-empty auth value. Passwordless objects and indices had a second open path: the platform policy was `PolicyOR(PolicyPCR, PolicyAuthValue)`, and its `PolicyAuthValue` branch is satisfied by an empty `authValue`.
  - **Affected:** the platform store's sealed PKCS#11 PIN (`credential://`), `tpmpolicy` scope secrets, `xkmsctl seal --tpm-policy platform` without `--password`, every platform-policy TPM2 key, and every platform-policy NV index. The barrier's `TPM2Strategy` root key sealed without credentials, and FROST TPM2 shares, were sealed with neither a policy nor a password; their only protection was the Platform SRK's authorization at `TPM2_Load`. Objects bound to a named policy already had `userWithAuth` cleared and were not affected.
  - **Proof:** every path was proven on the simulator, before and after the fix (`pkg/tpm2/seal_policy_bypass_simulator_test.go`, `pkg/tpm2/object_policy_simulator_test.go`).
  - **One shared fix (`pkg/tpm2/object_policy.go`).**
    - `bindObjectPolicy` binds every child object at creation: `sealKeyInternal`, `CreateRSA`, `CreateECDSA` and `CreateSecretKey`. An object with an `authPolicy` gets `userWithAuth` CLEAR, so its password counts only through `PolicyAuthValue` inside the policy. A passwordless platform-policy object gets the `PolicyPCR` branch alone (`platformPCRPolicyDigestFromPin`). An object with a password keeps the `PolicyOR`, so the recovery PIN still works after a platform change.
    - `objectSession` answers the USER role at every use: unseal, `Sign`, `ECDHZGen` and `RSADecrypt`. It reads the policy from the object: the named-policy binding record, else the loaded object's `authPolicy` read back with `TPM2_ReadPublic`. A passwordless platform object gets a `PolicyPCR` session (`platformPCRSession`), so it is used correctly even when the caller's attributes name no policy, as xkey's `LocalTPMPolicies.UnsealObject` does.
    - Platform-policy NV indices (`NVWrite`, `NVDefineCounter`, `NVDefineExtend`) are defined with the `PolicyPCR` branch alone and without `TPMA_NV_AUTHREAD`/`AUTHWRITE`. Reads go through `TPMA_NV_POLICYREAD`, chosen from the index's own attributes, or through the owner.
  - **`RSADecrypt` signature change.** `TPM2.RSADecrypt` now takes `(keyAttrs, backend, ciphertext)`; it was `(handle, name, ciphertext)`. It loads the key and authorizes it through `objectSession`. Before, it presented no authorization at all, so a key with a password or a policy could not decrypt through `pkg/backend/tpm2`.
  - **`SealKey` refuses unprotected seals.** `SealKey`, and therefore `Seal` and every sealing caller, refuses a seal with neither a policy nor a non-empty password. It returns the new typed `tpm2.ErrSealUnprotected` (`sdk/go`: `ErrTPMSealUnprotected`); previously that seal created an object anyone able to load it could unseal.
    - `Seal` with no `KeyAttributes` and no password now binds the object to the Platform SRK's own policy, and FROST's `TPM2SecretSealKeyAttributes` does the same for its shares.
    - Keys and symmetric key objects are not refused: their use stays gated by the Platform SRK at `TPM2_Load`.
    - `xkmsctl seal --backend tpm2` now needs `--tpm-policy`, `--password` or both. The `tpm_policy` and `password` fields of `SealRequest` are described the same way on the REST, MCP, gRPC, transport, `sdk/ts` and `xkmsctl` surfaces.
  - **Removed: `types.SealOptions.TPMPolicy` and `types.TPMSealPolicy`** (`sdk/go`: `TPMSealPolicy`). No production caller set them. `PCRSelection` and `HashAlg` were copied onto the key attributes and never enforced, and a caller-supplied `AuthPolicy` produced an object `Unseal` could not open.
  - **Existing objects keep their old attributes.** Objects and NV indices created before this change keep `userWithAuth` (or `TPMA_NV_AUTHREAD`) SET and, when passwordless and platform-bound, their open `PolicyAuthValue` branch, so they can still be opened the old way. Nothing is migrated (pre-release, no migration path). Re-create them to protect them: re-enroll the platform-store credential, the `tpmpolicy` secrets and the barrier's TPM2 root key, and regenerate platform-policy keys and NV indices.
  - Docs: `docs/tpm2/engineering.md` ("Object authorization").
