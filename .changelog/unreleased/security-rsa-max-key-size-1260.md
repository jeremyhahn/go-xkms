- **`types.ValidateRSAKeySize` now enforces a maximum, not just the RSAKeySize2048 minimum, closing a DoS where an authenticated caller could name an unbounded RSA modulus** (#1260). `rsa.GenerateKey` cannot be cancelled and its cost grows with the cube of the modulus size, so a request naming `key_size: 65536` pinned a CPU core for minutes to hours; nothing between the RPC surface and the crypto library refused it. The ceiling is `RSAKeySize4096`, not an arbitrary larger "safe-looking" number: it is the largest modulus every backend this project ships actually generates — AWS KMS, Azure Key Vault and GCP Cloud KMS all cap asymmetric RSA CMKs at 4096 bits, a TPM 2.0 device generates at most 2048 or 3072 bits in practice, and the PKCS#11 module's own `CKM_RSA_PKCS_KEY_PAIR_GEN` already advertises 4096 as `ulMaxKeySize` after a prior 16384 advertisement let one `C_GenerateKeyPair` call exhaust the daemon's memory. `*types.RSAKeySizeError` is reused for the new refusal (message becomes "at most 4096" above the ceiling, unchanged "at least 2048" below the floor), so every call site that already type-asserts on it needs no change.
  - Two production paths generated RSA keys from a caller-controlled size without ever calling `ValidateRSAKeySize`: `pkg/keyprovider/pkcs8.PKCS8Backend.generateRSAKey` duplicated only the floor check inline (no ceiling at all), and `pkg/ssh/keys.Generate`/`GenerateOnBackend` (the SSH factor's key generation, which runs entirely client-side with no backend in the loop for `Generate`) checked only `RSABits < minRSABits`. Both now call `types.ValidateRSAKeySize`. `pkg/acme/client/service`'s account/certificate-key `signerGenerators["RSA"]` had no bound at all on a config-supplied `KeyConfig.RSA.KeySize` and now validates before generating. `cmd/xkmsctl`'s local `generateKeyPair` (used by offline cert/CA issuance) and `buildKeyAttributesFromFlags` (the `xkmsctl key create`/`rotate` local pre-check ahead of the server round trip) gained the matching ceiling refusal, `ErrRSAKeySizeTooLarge`, alongside the existing `ErrRSAKeySizeTooSmall`.
  - Every other RSA-keygen path already funnelled through `types.ValidateRSAKeySize` before this change — `KeyAttributes.Validate`, the PKCS#11 and TPM backends' own `GenerateRSA`/`CreateRSA`, and `compositeBackend.GenerateRSA` (the one `Backend` implementation every `GenerateKey`/`RotateKey`/import-ceremony request reaches before any concrete backend, per its own doc comment) — so those needed no code change, only the raised ceiling from the shared validator; the PKCS#11 module's `C_GenerateKeyPair` (`pkg/pkcs11/module/mechanism.go`'s `rsaModulusBitsMax`) already enforced the identical 4096-bit ceiling for the same reason and was already consistent with the new bound.
  - Files: `pkg/types/algorithms.go`, `pkg/keyprovider/pkcs8/pkcs8.go`, `pkg/ssh/keys/generate.go`, `pkg/ssh/keys/errors.go`, `pkg/acme/client/service/account_manager.go`, `cmd/xkmsctl/cert.go`, `cmd/xkmsctl/key.go`, `cmd/xkmsctl/errors.go`, `sdk/go/types.go` (re-exports `RSAKeySize3072`/`RSAKeySize4096` alongside the existing `RSAKeySize2048`).
  - Verified by: `pkg/types.TestValidateRSAKeySize_RefusesAboveMaximum`/`_Table` (2047/8192/8193/16384/65536 refused, 2048/3072/4096 accepted); `pkg/xkms.TestGenerateKey_RSA_RefusesOversizedModulus` (the RPC surface refuses `key_size: 65536` in validation, before any backend runs — the test would hang rather than fail fast if that regressed); matching refusal tests in `pkg/ssh/keys`, `pkg/acme/client/service`, and `cmd/xkmsctl`. `go vet -tags "codec_cbor codec_json codec_msgpack tpm_simulator frost"` clean repo-wide, plus `-tags pkcs11` on `pkg/backend/pkcs11`; `gofmt` clean.
