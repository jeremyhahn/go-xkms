- **`Decrypt`'s RSA fallback ran PKCS#1 v1.5 unconditionally, with no `allow_legacy_key_wrap` gate and no uniform ciphertext-rejected error — the one PKCS#1 v1.5 construction in the service not covered by either protection.** `pkg/xkms/servicer_crypto.go`'s `asymDecrypterOpts` mapped both an unnamed padding and `"pkcs1v15"` straight to `nil` (PKCS#1 v1.5, RFC 8017 section 7.2.2's Bleichenbacher/Marvin decryption-oracle construction) with no policy check, while the identical construction on `Encrypt`'s asymmetric fallback (`servicer_crypto.go`, wrapping under an RSA KEK) and on `WrapKeyByID`/`UnwrapKeyByID` (`servicer_wrapkey.go`'s `resolveWrapMechanism`) already refused it unless the operator set `crypto.allow_legacy_key_wrap`. `Decrypt` is reachable over every transport (gRPC, REST, MCP, QUIC, the unix socket, and the PKCS#11 module's `C_Decrypt` under `CKM_RSA_PKCS`, all of which route through this one RPC) with a caller-designated key and a caller-supplied ciphertext, so the missing gate left the oracle fully exposed by default.
  - `asymDecrypterOpts` now refuses PKCS#1 v1.5 — named explicitly or left unnamed, since an unnamed padding still means PKCS#1 v1.5 — unless `crypto.allow_legacy_key_wrap` is set, via a new shared helper (`legacyRSAPKCS1v15Refusal`) that `Encrypt`'s asymmetric fallback now also calls, so the two halves of the operation cannot drift onto different wording or a different sentinel again. RSA-OAEP is unaffected and requires no configuration change. The unnamed-padding default itself is unchanged (still PKCS#1 v1.5): `Encrypt`'s asymmetric fallback has exactly one construction, so defaulting `Decrypt`'s unnamed padding to OAEP would have made a service-produced ciphertext unreadable by the service's own default decrypt call.
  - A ciphertext that fails decryption once the flag is set — bad padding, a wrong key, or any other cause — now reports one uniform, undifferentiated `ErrDecryptionFailed` (`wrapAsymDecryptError`), discarding whatever diagnostic text the backend's own `crypto.Decrypter` attached, mirroring `ErrUnwrapCiphertextRejected`'s existing discipline for `UnwrapKeyByID`'s identical RSA constructions. Previously the raw backend error text was wrapped verbatim into the response, which is a second, independent oracle channel beyond the accept/reject bit itself (RFC 8017 sections 7.1.2 and 7.2.2 both require withholding which check failed) — confirmed reachable on gRPC, whose `codes.Internal` mapping puts an unclassified error's `.Error()` text on the wire verbatim with no scrubbing (REST and MCP already scrub an internal-status error to a fixed message). A backend capability refusal (a TPM2 raw-decrypt refusal on a sign-only key, for instance) is unaffected and still reports its own text under `ErrOperationNotSupported`, since that names a static capability boundary rather than a property of the ciphertext.
  - The PKCS#11 module's `CKM_RSA_PKCS` `C_Encrypt`/`C_Decrypt` (as opposed to `C_WrapKey`/`C_UnwrapKey`, already gated) is a real, client-legitimate PKCS#11 mechanism reached only through this same `Decrypt`/`Encrypt` RPC pair (`CryptoManager.Decrypt`/`Encrypt` call the transport client, which calls `XKMSService.Decrypt`/`Encrypt` directly), so it is covered by the identical gate with no separate change; `CKM_RSA_PKCS_OAEP` is unaffected.
