- **Phone attestation never checked the Android `attestationApplicationId`, so any app on any locked Android handset passed first pairing and every re-attestation; the attested package and signing-certificate digest must now match an allow-list** (#1305). `attestation.VerifyDeviceAttestation` (`xkey/pkg/attestation/device.go`) verified the chain, boot state, key origin, genesis challenge and live signature, all of which say the key lives in a genuine handset's secure hardware and none of which says which application generated it. It now also calls the new `RequireAttestedApplication`, which matches the Keystore-written `attestationApplicationId` against `attestation.Trust.Applications` and refuses with `pairing.ErrApplicationDenied` (wrong package, wrong signer, or no application named) under `ErrDeviceAttestVerifyFailed`. Because every path that judges a device goes through that function — `xkey device pair`, `device attest-device`, the reconnect proof in `device_session.go`, the phone backend's `NewLiveAttestor`, and the GUI's Pair, Connect and Attest — the check applies on first pairing and on every re-attestation.
  - **BREAKING — pairing and re-attestation refuse until an allow-list is configured.** No official xkey-android package name and release signing digest are defined in this repository, so there is no built-in default: `attestation.LoadTrust(store, apps)` refuses with the new `pairing.ErrApplicationPolicyUnconfigured` before any phone is asked for evidence. Configure it in `devices.yaml` under `attestation_policy`: `allowed_applications` (a list of `package_name` plus `signing_digests`, hex SHA-256) and `allow_unpinned_signatures` (development builds only). The CLI's `AttestationPolicy` and the GUI's `devices.yaml` mirror both inline the one `pairing.ApplicationPolicy` type, so the GUI round-trips the keys unchanged. An unreadable `devices.yaml` refuses rather than reading as "no policy".
  - One matcher: the enroll-phone allow-list code (`EnrollmentPolicy.matchApplication`) moved to `pairing.ApplicationPolicy.Match` in the new `xkey/pkg/pairing/application_policy.go`, and `EnrollmentPolicy` now embeds `ApplicationPolicy` (same `allowed_applications` / `allow_unpinned_signatures` keys). `ErrEnrollmentApplicationDenied` is replaced by `pairing.ErrApplicationDenied`, and an empty enrollment allow-list now returns `pairing.ErrApplicationPolicyUnconfigured`. The match now compares package names exactly (Android package names are case-sensitive) and considers every allow-list entry for a package instead of stopping at the first.
  - The SDK's `android.BuildAttestationExtensionWithOptions` gained `AttestationExtensionOptions.ApplicationID`, encoded as `softwareEnforced` tag 709 where the Keystore daemon writes it, and `sdk/go` exports `AndroidAttestationPackageInfo`, so consumers can build synthetic evidence for the check. The shared `attesttest` fixtures now carry an application identity by default and expose `Applications()` / `AttestedApplication()`.
  - **The enterprise/SO plane can lock the allow-list, the same way it already locks `allow_unattestable_devices`** (owner ruling 2026-09-29). `PolicySection` gains `pairing_allowed_applications`, `pairing_allow_unpinned_signatures` and `lock_pairing_application_policy`; the new `attestation.ResolveApplicationPolicy` returns the enterprise allow-list outright (never merged with `devices.yaml`'s own entries) once given an already-verified section, and the user's plane otherwise. **A sealed section that has not verified refuses outright with the new `attestation.ErrApplicationPolicyUnverifiable`, and NEVER falls back to `devices.yaml`** — this is deliberately stricter than `AllowUnattestablePairing`'s own "unverified means refuse the escape hatch, pairing still runs" resolution, because there is no safe default here to degrade to: falling back to a file anyone with a shell can edit, without ever producing the SO PIN, would be exactly the bypass the lock exists to prevent. The CLI's `resolveEnterpriseApplicationPolicy` (`cmd/xkey/cmd/device_pair.go`) checks `config.IsEnterpriseMode` first — unsealed, `devices.yaml` governs with no PIN needed; sealed, it verifies via `config.LoadVerifiedPolicy` using `XKEY_SO_PIN` alone (never `--so-pin-stdin`, unusable by an unattended reconnect) and refuses on any verification failure, including no config loaded at all. There is no PIN-free verification mechanism anywhere in the codebase to use instead: the HMAC key is derived from the SO PIN via Argon2id every time (`pkg/config/policy_integrity.go`), and the on-disk record's `TPMNVIndex` field is unused reserved space. The GUI's `PhoneService` tracks `SetEnterpriseSealed` (set once at startup from `config.IsEnterpriseMode`) alongside `SetPolicy` (called ONLY by `applyVerifiedEnterprisePolicy` with a genuinely SO-verified section, never with the `config.DefaultPolicy()` placeholder the GUI installs for `AppService`/`PINService`/`TrustService`/`AuditService`/`SealService`/`APIExplorerService`'s own lower-stakes gates); `ResolvedApplicationPolicy` refuses whenever sealed and unverified, falls through to `devices.yaml` only in personal mode. The official xkey-android package name, `com.automatethethings.xkey`, is documented on `AllowedApplication.PackageName` and pinned as `attesttest.AppPackage`; no release signing digest ships in this repository, so pairing stays refused until one is configured, and `ErrApplicationPolicyUnconfigured`'s text names exactly what to set.
