- **Secrets no longer cross the TPM bus in plaintext: the SO PIN, the USER PIN, sealed data such as the auto-unsealed PKCS#11 PIN, and every other TPM secret now travel only inside salted, encrypted sessions, and the `EncryptSession` switch is removed.** Before this change, anyone probing the LPC/SPI/I²C bus could read the owner and endorsement hierarchy authorization (the SO PIN) from the cleartext password sessions of `TPM2_CreatePrimary`, `TPM2_EvictControl`, `TPM2_HierarchyChangeAuth`, `TPM2_NV_DefineSpace` and `TPM2_Clear`. `TPM2_HierarchyChangeAuth` also sent the new value in clear. The same observer could read the Platform SRK's USER PIN from the `TPM2_CreatePrimary` sensitive area. The encrypted-session branch of `CreateSRK` required a parent that a primary key never has. The observer could brute force the USER PIN offline from any command authorized through the unsalted `PolicyAuthValue` branch of the platform policy, whose HMAC key was the PIN alone. They could read every value sealed or unsealed through `TPM2_Create`/`TPM2_Unseal` in both directions. `EncryptSession` defaulted to `false`, while the documentation said it defaulted to `true`. Now every secret-bearing session is salted (`saltKey`, `pkg/tpm2/session.go`). The salt key is the persistent EK, which is only read. Before an EK exists, an ephemeral NULL-hierarchy ECC P-256 key is used and flushed at once; the EK and SSRK are never modified. Every non-empty auth value is proven through a salted HMAC session, never `TPM_RS_PW`. Hierarchy sessions are bound, so the new-auth response HMAC of `TPM2_HierarchyChangeAuth`/`TPM2_Clear` verifies. The `PolicyAuthValue` session is salted. The secret parameter of each command is AES-128-CFB encrypted in the direction it travels. A separate salted encryption session carries it when the authorization is a policy session. The protected commands are `TPM2_Create`, `TPM2_CreateLoaded`, `TPM2_Unseal`, `TPM2_NV_Write`, `TPM2_NV_Read`, `TPM2_NV_DefineSpace`, `TPM2_RSA_Decrypt`, `TPM2_ECDH_ZGen`, `TPM2_ActivateCredential` and `TPM2_GetRandom`. `TPM2_NV_Extend` is now authorized through go-tpm sessions (`nv_extend.go`). `HashSequence` no longer uses the SO PIN as the auth value of its ephemeral sequence object. Removed, with no compatibility shim: `pkg/tpm2.Config.EncryptSession` (`encrypt-sessions`), `pkg/backend/tpm2.Config.EncryptSession` (`encrypt_session`, including the `pkg/xkms` registry key), `xkmsctl`'s `TPM2EncryptSession`, xkey's `tpm.encrypt_sessions`, and the one-shot unsalted `TrustedPlatformModule.HMAC`. `HMACSession` and `HMACSaltedSession` are now always salted. Verified by `pkg/tpm2/session_encryption_simulator_test.go`. It records the TPM traffic of provisioning with an SO PIN, Platform SRK creation, sealing and unsealing through both the PIN and the PCR branch, an NV secret under owner auth, and `TPM2_GetRandom`. It asserts that the plaintext PIN or secret appears in no command and no response, that each secret-bearing command carries the decrypt or encrypt attribute, and that the sessions authorizing it are salted. The tests fail when parameter encryption is disabled. The existing seal/unseal, provisioning, PSRK and key-creation simulator suites pass unchanged in behaviour. Documented in `docs/tpm2/engineering.md` §"Bus protection" (go-xkms#1147).
