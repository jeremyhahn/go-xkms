- **REST and gRPC `GenerateKey` no longer reimplement the service layer's key-generation logic, and REST/gRPC `ImportKey`/`GetImportParameters` now enforce the RSA-2048 floor they used to skip.** `pkg/api/rest/handlers.go`'s `GenerateKeyHandler` and `pkg/api/grpc/service.go`'s `GenerateKey` built their own `types.KeyAttributes` and called the backend directly, duplicating `pkg/xkms/servicer_key.go`'s `buildKeyAttributes` — the algorithm and key-purpose vocabularies, curve and RSA-size validation (including the 2048-bit floor, go-xkms#1204), and the exportability contract. Both now call `XKMSService.GenerateKey` directly and map its errors through each transport's existing `mapKeyOpError`/error-mapping convention, matching the pattern `Sign`/`Verify`/`Encrypt`/`Decrypt` already used. `ImportKeyHandler`/`GetImportParametersHandler` (REST) and `ImportKey`/`GetImportParameters` (gRPC) were evaluated for the same conversion and intentionally left as independent implementations: `pkg/xkms/backend_importexport.go`'s `importExportFor` resolves a backend's import/export capability through the full `backend.ImportExportBackend` union, while these four handlers correctly assert only `backend.ImportBackend` — the narrower capability an AWS-KMS-shaped import-only backend actually has (`pkg/api/rest/importexport_capability_split_test.go`'s `TestImportKeyHandler_ReachableWithoutExportSupport` is the regression test). Routing them through the service as written would silently refuse that backend for import; the embedded transport and MCP already inherit this same regression, since both call the service's `ImportKey`/`GetImportParameters` directly. Fixing it requires `importExportFor` to expose an import-only and export-only resolution path, a ~20-call-site service-layer change filed as a follow-up rather than folded into this one. Each handler instead now calls `types.KeyAttributes.Validate()` directly on the attributes it builds before calling the backend, so an RSA-1024 `ImportKeyRequest`/`GetImportParametersRequest`/`CopyKeyRequest` is refused with 400/`InvalidArgument` on every transport, exactly as `GenerateKey` is. Fixing gRPC's `GetImportParameters` to pass that check also surfaced and fixed a real bug: it built its `types.KeyAttributes` without ever setting the purpose (`KeyType`) field, so `Validate()` would have refused every request, asymmetric and symmetric alike, with "key type is required" — it is now set in every branch, matching `ImportKey`'s own switch. `pkg/xkms/servicer_key.go`'s `buildKeyAttributes` also gained gRPC's former key-size-to-cipher selection for a bare `"symmetric"`/`"secret"` algorithm name (128/192/256, refusing anything else) instead of always defaulting to AES-256-GCM regardless of the requested size, so the one implementation now matches the more precise behaviour gRPC's duplicate used to have, rather than gRPC losing it on conversion.
  - Files: `pkg/api/rest/handlers.go`, `pkg/api/grpc/service.go`, `pkg/xkms/servicer_key.go`, `docs/key-management/{api,engineering}.md`.
  - Verified by `pkg/api/rest/rsa_floor_test.go` and `pkg/api/grpc/rsa_floor_test.go` (RSA-1024 refused with 400/`InvalidArgument` through `GenerateKey`, `ImportKey` and `GetImportParameters` on both transports; an unrecognised algorithm refused through `GenerateKey`; an unknown backend refused with the transport's existing status code), the full existing REST and gRPC `GenerateKey`/`ImportKey`/`GetImportParameters`/`CopyKey`/`WrapKey`/`UnwrapKey`/`ExportKey` suites (unchanged behaviour, including the AWS-KMS-shaped import-only capability split and the gRPC symmetric key-size branches), and `pkg/xkms`'s existing `GenerateKey`/symmetric-algorithm tests. Fixes #1214.
