- **The root module runs on go-qrdb v0.46.0-alpha, go-quicraft v0.19.0, go-enclave v0.7.0-alpha and go-luks2 v0.5.0-alpha** -- the bump includes the go-qrdb v0.40.1-alpha migration, which deletes go-xkms's re-exposure of go-qrdb services (Backup, Barrier, Custodian/Share, SealStore, Credentials, Init, Invite and Audit query) from REST, gRPC, MCP, unix, the SDKs, the CLIs and the web console. Single-admin `xkmsd init` now runs through go-qrdb's `node.FirstBoot`. go-qrdb's secret APIs are now context-aware (`secure.NewSecret`, `Secret.Open`, `SecretValue.WithBytes`, `seal.CredentialsFor`/`MustCredentials`, `enclave.WipeAll`), and every caller passes its request or command context. Certificate issuance goes through go-qrdb's CSR-based `IssueCert`/`EnrollCert`, because the server-side key generation in `GenerateCert`/`ExportCert` is gone upstream. go-qrdb dropped the per-database `engine` setting, its volume-pool subsystem and the tenant `DataRoot`, so xkmsd no longer provisions a volume pool and its barrier registry serves prefix and barrier tenant isolation only. go-qrdb no longer re-exports Shamir split/combine, so the TPM `ShareSecret`/`SecretFromShares` helpers and the matching SDK aliases are removed. go-luks2 no longer models the systemd TPM2 token members, so `pkg/luks` writes and reads `tpm2-blob`, `tpm2-pcr-bank`, `tpm2-pcrs`, `tpm2-key-handle` and `tpm2-policy-hash` itself, under the same names, so existing tokens and systemd-cryptsetup are unaffected. The `certs:generate` permission is gone upstream: certificate issuance now requires `certs:issue` (and `certs:enroll` for enrollment), so roles granting `certs:generate` must be updated. File storage uses go-qrdb's hashed shard layout and writes every record owner-only (0600); `certs/*` is no longer world-readable. Its cross-process write lock is now taken on the store directory itself, so the directory no longer holds a `.lock` file, and it also covers opening the store, so processes opening one directory at the same time no longer fail on each other's temporary files. Role-membership checks resolve the role through the node's role store as the caller, so a caller without `roles:read` fails closed with a role-resolution error instead of a plain denial. Barrier and volume tenants are refused unless the node seals through the node-seal path. go-qrdb now publishes each node's member record itself, so xkmsd's cluster advertiser and the `cluster.advertise_host` setting are removed. A first boot without a CA configured leaves the node serving only the ceremony endpoints until an administrator certificate is bound. go-qrdb resolves a user or role only within the request context's tenant, so the admin plane scopes each tenant user and role operation to the tenant it addresses once the tenant binding admits the caller; a platform administrator's cross-tenant user and role management works as before. go-qrdb authorizes every embedded-client call, so xkms's own calls on its embedded node run as its service principal (see the service-principal entry). go-truststrap stays at v0.4.0-alpha because go-qrdb v0.45.0-alpha did not compile against v0.5.0-alpha. The integration-test module follows in its own change. Refs #1413, #1355, #1358, #1399.
- **The `sdk/go`, `xkey` and web/desktop modules run on the same go-qrdb, go-quicraft, go-enclave and go-luks2 releases** -- web/desktop needs no source change. xkey seals barrier credentials, PINs, USB passphrases and imported passwords under the command or GUI context, so `pwimport`'s `Parser.Parse`, `Import`, `Preview` and `ToStaticPassword` and `usb.CreateImage` now take a `context.Context`. xkey's data directory is a go-qrdb file engine, which stores each key under a hashed path and refuses a non-empty directory without its format marker. Because of that, `xkey barrier` probes and reads the sealed root key through storage instead of a `barrier/root_key` file. An xkey data directory written by an earlier release must be re-initialized; there is no migration. `xkey barrier status` (and the GUI's seal info) report the data directory and the engine entry holding the sealed root key (`root_key_entry`) instead of a `root_key_path` file. An explicit `--token-store` or `--session-store` on `xkey oidc` now names the directory of an unencrypted store rather than a single JSON file, and their defaults are `~/.xkey/tokens` and `~/.xkey/aws-session`. Known break: `xkey barrier init` is refused when the data directory already holds TPM key-store state from an earlier `xkey tpm` or `xkey pin` command, because the engine only claims an empty directory; initialize the barrier first. Refs #1413.
