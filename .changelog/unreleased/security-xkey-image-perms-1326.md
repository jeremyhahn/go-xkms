- **LUKS/USB container files were created world-readable and could race a concurrent creator, an unlocked volume's mount point could be left world-listable, and the seal command's plaintext staging copy would follow a symlink** (#1326).
  - `xkey/pkg/luks/volume.go`'s `Volume.Create` and `xkey/pkg/usb/image.go`'s `createOnImageFile` created their container file with `os.Create`, which honors the process umask and typically yields `0644` — a LUKS or USB image file, not yet formatted or encrypted, was briefly (and on a permissive umask, persistently) readable by every local user. `image.go` also checked existence with a separate `os.Stat` before creating the file, a TOCTOU race: a file created between the check and the create was silently overwritten. Both now create with `os.OpenFile(path, os.O_CREATE|os.O_EXCL|os.O_WRONLY, 0600)`; `O_EXCL` makes the existence check atomic with creation, and an `os.ErrExist` from that call is mapped to the same typed "already exists" error (`luks.ErrVolumeAlreadyExists`, `usb.USBError{Operation: "check_existing", Err: usb.ErrImageExists}`) the earlier `Stat` check used to return.
  - `xkey/pkg/luks/volume.go`'s `Volume.Unlock` mounted the encrypted filesystem over a mount point directory it had just created with mode `0700`, but go-luks2's ext4 creation runs `mkfs.ext4` with no `root_perms` option, so a freshly formatted filesystem's root inode can be `0755` — mounting it replaced the `0700` mode with the filesystem's own, leaving the unlocked volume's contents listable by every local user for as long as it stayed mounted. `Unlock` now re-asserts `os.Chmod(mountPoint, 0700)` immediately after a successful mount, through a new `chmodFn` seam; a failed chmod unmounts, re-locks and detaches before returning a typed `*VolumeError{Operation: "chmod_mountpoint"}` rather than leaving a world-listable volume mounted and unlocked. go-luks2 v0.2.0-alpha's `Ext4Options` (`pkg/luks2/filesystem.go`) has no field for arbitrary `-E` mkfs tunables — only `StrideSize`/`StripeWidth` reach `-E`, and nothing reaches `-E root_perms=...` — so passing `root_perms=0700` at filesystem-creation time is not possible through the current public API; this is an upstream gap, not fixed here.
  - `xkey/cmd/xkey/cmd/seal.go`'s `copyFileSeal` (used by `migrateExistingData` to stage the plaintext `~/.xkey` data directory before it is copied into the new encrypted volume) followed symlinks via `os.Stat`/`os.ReadFile`. A symlink in the data directory pointing outside it would have been dereferenced into the (unencrypted) staging copy under a name the caller never intended to expose. `copyFileSeal` now `Lstat`s the source first and refuses with a typed `*SealError{Operation: "copy_file", Err: ErrSealSymlinkRefused}` if it is a symlink. The staging-copy-preserved-on-failure message in `migrateExistingData` is now explicit that the directory holds an unencrypted copy of the caller's plaintext secrets and must be securely deleted once recovered.

  - Verified by `TestVolume_Create_Success` (container file mode `0600`), `TestVolume_Create_AlreadyExists`, `TestCreateOnImageFile_Success` (image file mode `0600`), `TestCreateOnImageFile_FileExists`, `TestVolume_Unlock_ChmodsMountPointAfterMount` (mount point re-asserted to `0700` after a mount that leaves it `0755`), `TestVolume_Unlock_ChmodMountPointFails` (a failed chmod unmounts, re-locks and detaches), `TestCopyFileSeal_RefusesSymlink`, and `TestCopyDirContents_RefusesSymlink`. `go vet` and `gofmt` clean under `codec_json tpm_simulator ble` for `xkey/pkg/luks/...`, `xkey/pkg/usb/...`, and `xkey/cmd/xkey/cmd/...`.
