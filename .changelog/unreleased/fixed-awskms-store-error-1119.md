- **awskms `GetSymmetricKey` no longer treats a metadata-storage outage as "no seal key yet"** (#1119). It mapped every `storage.GetKey` failure to `backend.ErrKeyNotFound`, indistinguishable from a genuinely unprovisioned key. `seal.EnsureSealKey` (pkg/seal/cloud_provision.go) uses exactly that distinction to decide whether generating a replacement key is safe, so a storage outage during unseal could have driven it down the "provision a new key" path -- the mechanism #1098 found regenerating seal keys. Only `errors.Is(err, storage.ErrNotFound)` now maps to `ErrKeyNotFound`; every other error wraps `awskms.ErrMetadataStorage`, matching `getKeyID`'s existing classification (#839). The same collapse was also present in two other places, fixed the same way:
  - `awskms.Backend.ListKeys` silently dropped a key from its result on any per-key metadata read failure rather than just a genuine not-found race with `List`; it now surfaces the error instead of returning a misleadingly incomplete list.
  - `awskms.Backend.Get` (the FSEXT_PRIVATE_BLOB/FSEXT_PUBLIC_BLOB metadata path) reported every metadata-read failure as `backend.ErrFileNotFound`; only a genuine `storage.ErrNotFound` does now, everything else wraps `ErrMetadataStorage`. No caller in the tree currently branches on `errors.Is(err, backend.ErrFileNotFound)` from this path, so this closes the gap before anything comes to depend on the old, incorrect classification.
  - `vault.Backend.ListKeys` had the identical per-key collapse (falling back to a bare `{CN: cn}` entry on any metadata read failure, not just `storage.ErrNotFound`); it now returns `vault.ErrKeyRetrievalFailed` instead of silently truncating the list.
