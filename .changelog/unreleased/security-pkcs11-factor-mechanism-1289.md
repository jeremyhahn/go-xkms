- **The PKCS#11 auth factor recorded a signing mechanism at enrollment but never checked it at verification** (#1289 item 4). `Enroll` stored `mechanism` in the enrollment's metadata and `Challenge` already copied it into `MethodData["mechanism"]`, but `Verify` never read it: it chose ECDSA vs. RSA PKCS#1 v1.5 purely from the enrolled key's Go type, so a corrupted or hand-edited challenge whose mechanism no longer matched the enrolled key's algorithm, or a response that named a different mechanism than the one recorded at enrollment, verified anyway as long as the signature itself checked out. `Verify` now reads the mechanism from `challenge.MethodData["mechanism"]` — never from the response — and refuses with `AuthFactorVerificationFailedError` when it is missing, when its family (`CKM_ECDSA*` vs. an `RSA` mechanism) is inconsistent with the enrolled key's algorithm, or when `response.Metadata["mechanism"]` names a different mechanism than the enrolled one. It never selects *how* a signature is checked from anything the response supplies; the mechanism only ever gates a refusal.
  - `Enroll` now applies the same family check to the mechanism it is about to record, refusing an EC key enrolled with an RSA mechanism or an RSA key enrolled with an ECDSA mechanism. This also fixed a latent bug: `Config.DefaultMechanism` (`CKM_ECDSA_SHA256`) was applied to every enrollment regardless of key type, so an RSA key enrolled without an explicit `"mechanism"` MethodParam was recorded with an ECDSA mechanism. RSA enrollments without an explicit mechanism now default to `CKM_SHA256_RSA_PKCS`.
