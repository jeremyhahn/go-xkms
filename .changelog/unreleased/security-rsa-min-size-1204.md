- **RSA keys under 2048 bits can no longer be generated or imported through the RPC service, or generated directly on the PKCS#11 and TPM backends.** `pkg/xkms/servicer_key.go`'s `buildKeyAttributes` (GenerateKey) and `applyKeyTemplate` (the template resolver shared by ImportKey, GetImportParameters and UnwrapKeyByID) built a `types.KeyAttributes` and handed it straight to a backend without ever calling `KeyAttributes.Validate`, so its existing 2048-bit RSA floor never ran on the RPC surface. `pkg/backend/pkcs11.Backend.GenerateRSAWithSize` only raised sizes below 512, silently promoting anything in between (say, 1024) unchanged, and `pkg/tpm2.TPM2.CreateRSA` applied no floor at all — a `GenerateKeyRequest` naming 1024 bits reached hardware key generation unchecked on both backends. The minimum now lives in one place, `types.ValidateRSAKeySize` (`pkg/types/algorithms.go`), returning the typed `*types.RSAKeySizeError` rather than an `fmt.Errorf`, and is enforced at every layer that can generate or describe an RSA key: `KeyAttributes.Validate`; `buildKeyAttributes` and `applyKeyTemplate` (via a shared `validateKeyAttributes` helper, `pkg/xkms/servicer_key.go`); `pkcs11.Backend.GenerateRSAWithSize`, which now refuses an undersized modulus before ever touching the HSM session instead of after; `tpm2.TPM2.CreateRSA`, which validates the resolved key size independently of the TPM-2.0-defined-sizes check `KeyTemplate` already performs (that check is a device-capability question and still permits 1024, since TCG's reference implementation defines it); and `compositeBackend.GenerateRSA` (`pkg/xkms/composite_keys.go`), the one `xkms.Backend` implementation every caller in the module reaches — including the REST and gRPC transport handlers that build their own `KeyAttributes` independently of the RPC service, and the CA and PIV key-generation helpers — before a concrete backend ever sees the request. A caller that names no size at all (`RSAAttributes` nil, or `KeySize` zero) is left alone everywhere: resolving that to the 2048-bit default remains each call site's own job, never a size `ValidateRSAKeySize` treats as "too small". 2048, 3072 and 4096 bits continue to work unchanged. Not yet covered: `pkg/api/rest/handlers.go`'s `ImportKeyHandler`/`GetImportParametersHandler` and `pkg/api/grpc/service.go`'s `ImportKey` each build import attributes independently of `pkg/xkms/servicer_key.go` and do not yet run this check; tracked as a follow-up (go-xkms#1204).
  - Files: `pkg/types/algorithms.go`, `pkg/types/types.go`, `pkg/xkms/servicer_key.go`, `pkg/xkms/composite_keys.go`, `pkg/backend/pkcs11/pkcs11.go`, `pkg/tpm2/rsa.go`.
  - Verified by `pkg/types/rsa_keysize_test.go` (every size below 2048, including zero and negative, refused with `*types.RSAKeySizeError`; 2048/3072/4096/8192 accepted), `pkg/xkms/servicer_key_test.go` and `servicer_key_import_test.go` (GenerateKey, GetImportParameters and ImportKey all refuse 1024-bit RSA with `ErrInvalidKeyAttributes`; GenerateKey and GetImportParameters accept 2048/3072/4096), `pkg/xkms/composite_keys_test.go` (`compositeBackend.GenerateRSA` refuses an explicit 1024-bit request without ever calling the underlying backend, and still defaults a zero `KeySize` through to it), `pkg/backend/pkcs11/pkcs11_test.go` (`GenerateRSAWithSize` refuses undersized and negative sizes with the typed error before reaching the HSM pool check; zero still selects the default), and `pkg/tpm2/rsa_keysize_simulator_test.go` (`CreateRSA` against the TPM simulator refuses a 1024-bit request and still creates a 2048-bit key).
