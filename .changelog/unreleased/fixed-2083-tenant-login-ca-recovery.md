- **A revived tenant keeps its published login CA certificate.** When a stale provisioning pass of a removed tenant overwrites the certificate of the same tenant ID created again, the repair now writes back the certificate the live generation published (the DER go-qrdb registers as the tenant's issuer) instead of signing a new one, so the certificates issued against it keep authenticating; it fails closed when no published certificate is over the stored key.
- **AWS KMS key deletion releases the key's alias.** `Delete` now removes `alias/<cn>` before scheduling the key for deletion (only when the alias still targets that key), so a tenant whose creation was rolled back can be provisioned again under the same ID instead of resolving the alias to a pending-deletion key for the 7-day waiting period; an alias that cannot be removed is returned as an error.
- **AWS KMS key deletion no longer orphans an alias-only key.** `Delete` now schedules the key for deletion before it releases `alias/<cn>`, so when scheduling fails (or the process stops between the two calls) a key with no local metadata stays reachable through its alias and a retry can delete it.
- **Native onboarding of an undone tenant ID gets its login CA.** When a wrapped tenant create was rolled back and go-qrdb's native onboarding then creates the same ID, the login CA factory revives the tenant before provisioning it instead of refusing it as removed forever.
- **The login CA served is always over the live key.** The provider read path checks the saved login CA certificate against the live signer and restores the published certificate when a stale pass left a certificate over an old key.
- **Tenant administrators can issue certificates under the xkms login CA.** The login CA provider no longer carries go-qrdb's tenant request scope into its own key and certificate stores, which refused every `IssueCert` with "identity not in target tenant".
- **A restart finishes a tenant create rollback whose login CA cleanup failed.** The rollback is recorded before its CA cleanup, and the boot pass resumes it once the key backend recovers instead of failing server startup on the tenant's CA tombstone; a tenant natively re-created under an undone ID gets its login CA at boot.
- **Azure Key Vault key deletion keeps the key discoverable until it is deleted.** `Delete` now deletes the Key Vault key before its metadata, treats only a 404 as already gone, and returns any other failure (access denied, outage) with the metadata kept, so the key stays listed and can be reclaimed.
