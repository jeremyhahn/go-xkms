- **A malformed CTAP2 `setPIN`/`changePIN` request could crash the xkey FIDO2 daemon instead of being refused.** `xkey/pkg/authenticator/cmd_clientpin.go` `decryptPIN` checked only a minimum length on `newPinEnc` before calling `cipher.CBCDecrypter.CryptBlocks`, which panics when its input is not a whole number of AES blocks; a 65-byte (protocol 1) or 81-byte (protocol 2) `newPinEnc` reached that panic with nothing on the CTAP/uhid path to recover it. Separately, a decrypted plaintext starting with `0x00` made the old zero-length check fall through to treating the entire 64-byte buffer as the PIN instead of an empty one. `decryptPIN` now requires `newPinEnc` to be exactly 64 bytes (protocol 1) or exactly 80 bytes -- a 16-byte IV plus 64 bytes of ciphertext -- (protocol 2), refusing any other length with `ErrInvalidParameter` (`CTAP1_ERR_INVALID_PARAMETER`) before `CryptBlocks` runs. The decrypted plaintext is then validated per CTAP 2.1 §6.5.5.5 step 5 by a new `extractPaddedPIN`/`validatePINLength`: the PIN is every byte before the first `0x00` terminator, every byte from the terminator onward must also be `0x00`, and the PIN itself must be non-empty, at most 63 bytes, and at least the configured `minPINLength` in Unicode code points -- every violation, including a buffer with no terminator at all, reports `ErrPINPolicyViolation` (`CTAP2_ERR_PIN_POLICY_VIOLATION`). `decryptBlock`'s V2 branch (the `pinHashEnc` decrypt shared by `changePIN`, `getPinToken`, and `getPinUvAuthTokenUsingPinWithPermissions`) is tightened from a minimum to the same exact-length check for CTAP conformance; it already sliced a fixed-size window before `CryptBlocks` so it could not panic. `pin_protocol_v1.go`/`pin_protocol_v2.go` `Decapsulate` and `ext_hmac_secret.go` `decryptSalts` already guarded their `CryptBlocks` calls with an exact or block-multiple length check and needed no change. As defence in depth, `authenticator.go`'s `ProcessCBORWithContext` now dispatches every CTAP2 command through a single recover boundary (`dispatchCommand`/`recoverCommandPanic`): a handler panic is logged with the command byte and a stack trace and reported as the new `ErrCommandPanicked`, which maps to `CTAP2_ERR_OTHER` instead of crashing the daemon. Verified by `xkey/pkg/authenticator/cmd_clientpin_decryptpin_security_test.go` (a table test over the 65/81/63/0-byte lengths confirming none panics and each returns `ErrInvalidParameter`; a well-formed-length ciphertext with a stray non-zero byte after the terminator, a plaintext with no terminator at all, and a leading `0x00` all return `ErrPINPolicyViolation`; a valid PIN still round-trips for both protocols; `FuzzDecryptPIN` seeded with all of the above; and `recoverCommandPanic` mapping a simulated panic to `ErrCommandPanicked`/`StatusOtherError`). go-xkms#1149.
