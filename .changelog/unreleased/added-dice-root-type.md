- **DICE evidence reports its root of trust: hardware or software.** A device's alias chain declares where its UDS lives in DiceTcbInfo (TCG DICE Attestation Architecture r0.23 §6.1.1): `vendorInfo` is the DER OID 1.3.6.1.4.1.29377.101.24.1 (hardware, a secure element) or .24.2 (software, device storage), and a set `notSecure` flag is a software root whatever `vendorInfo` says. `dice.Verify` reports it as `Evidence.RootType`. CA m452: it is read only from the certificates on the paths that verified to a configured trusted root (`dice.RootTypeFromPaths`, sdk `DICERootTypeFromPaths`), so an unanchored chain, including a device-attest-01 raw DeviceIDKey record, reports unreported and certificates off the verified path are never read; a software root on any layer makes the identity software, and it is refused unless the policy permits `NotSecure`. `attestation.Verifier` anchors a `dice` statement through `dice.VerifyChain`, which handles the critical DiceTcbInfo. `attestation.Verifier.Verify` now returns the `*Result` with `RootType` (breaking: it returned only an error), device-attest-01's `VerifiedAttestation` and its persisted record carry it (`RegisteredDeviceVerifier.VerifyRegisteredDevice` now returns the `*VerifiedAttestation`), as does the AVR backend's `Attestation`; `sdk/go` re-exports it as `DICERootType`.
