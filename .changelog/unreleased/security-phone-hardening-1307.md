- **Three phone-pairing weaknesses let a corrupt record, a second BLE central, or a peer-chosen name undermine the pinned-key guarantee `xkey device pair` is supposed to give** (#1307).
  - `phone.NewBLEPeripheral` accepted an `ExpectedRemoteStatic` that decoded to nothing usable: `device_listen.go` base64-decodes the paired device's stored `NoisePublicKey`, and decoding `""` yields a non-nil, zero-length slice rather than an error, which the Noise session's `PeerStaticKey` then silently treats as "nothing to pin" — a corrupt or empty stored key downgraded a supposedly pinned connection to an unpinned one. `NewBLEPeripheral` now refuses a supplied `ExpectedRemoteStatic` that is not empty-and-nil (unpinned, still allowed) or exactly `pairing.NoiseKeySize` bytes, returning `ErrPeripheralInvalidPin`; `device listen` performs the same check on the decoded key before any TPM/bridge setup runs, returning `ErrDevicePinInvalid`.
  - `BLEPeripheral`'s GATT control-point `WriteEvent` fed every write into one shared `incomingData` channel and reassembler regardless of which central sent it, so a second central connected during a session could inject fragments into the legitimate phone's handshake or request stream. `handleWrite` now binds the session to whichever central's write arrives first and drops a write reporting a different one (logged at debug); the binding is reset when a session starts and again when it ends, so the next session is not refused for the previous one's central. This corrects the write path everywhere `bluetooth.Connection` identifies the writer per-connection (the `hci`/`ninafw`/`cyw43439` backends); BlueZ's D-Bus backend (`gatts_linux.go`, what a normal Linux build compiles) does not expose per-write connection identity at all and reports every write as the same handle, which is a documented upstream limitation this change cannot itself close.
  - The paired-device record's `Name` is peer-chosen and untrusted — the CLI stores the BLE-advertised local name, the GUI stores the name the phone returns in the pairing confirmation RPC — yet both use it as the record's lookup key. An empty, oversized, or control-character name could reach storage and a display prompt unvalidated; two devices given the same name made every later name lookup silently take the first match, deciding (by list order, which an attacker choosing when to pair controls) which pinned key a connection trusted; and the CLI's `--force` re-pair deleted *every* record sharing the advertised name, including an unrelated device's own pairing. `pkg/pairing` gained `ValidateDeviceName` (length bound, printable, no control characters), `ConflictingPairedDevice` (refuses a name already used by a different device — matched by neither address nor pinned key), `SamePairedDeviceIndices` / `ReplacePairedDevices` (identify and collapse every stale record for the *same* device, matched by address or pinned key so Android's RPA address rotation and a reinstall's key rotation both resolve correctly), and `FindPairedDeviceByName` (refuses an ambiguous name instead of returning the first match). The CLI's `device pair` and `device listen`, and the GUI's `Pair`/`Connect`/`Unpair`, all now go through these instead of ad hoc name comparisons; no storage migration was needed — the paired-device slice shape is unchanged, only how it is searched and mutated.
