- **In a cluster, a certificate revoked on one node is now refused by every node, and every revocation check fails closed.** Revocation records replicate through the CA's revocation store, but `CA.IsRevoked`, and so `CA.Verify` and `CA.VerifyPeerCertificate`, read only the node's in-memory map. That map is filled at `Load` and by the node's own revocations, so a certificate revoked on node A still verified on node B. CRL generation built from the same map, so node B's regenerated CRL overwrote the shared `crl/<ski>` record without node A's revocations. `IsRevoked` and the OCSP responder now share one read path: the map first, then the store. A hit from the store is cached (revocation is permanent), and a miss is never cached. CRL generation now builds from the store's full record set. Each reader treats only a definite not-found as "not revoked". A store fault is `ErrStorageError`, with the storage cause kept in the chain, and refuses the check. A corrupt record is the new `ErrRevocationRecordCorrupt`, naming its key, and now fails `Load` instead of being skipped with a warning, which had silently un-revoked it. A revocation listing failure aborts CRL generation, and nothing is published. An unreadable previous CRL number fails generation instead of restarting the sequence at 1. `VerifyPeerCertificate` refuses a certificate whose revocation status cannot be read instead of accepting it, and OCSP answers `unknown` (go-xkms#1116).
