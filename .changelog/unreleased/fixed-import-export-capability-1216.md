- **The service layer, the tenant-scoped and PIV backend wrappers, and REST/gRPC/MCP's import ceremony RPCs now resolve import and export capability independently, so a backend implementing only one direction (AWS KMS's real shape for import) is reachable for that direction on every transport.** `pkg/xkms/backend_importexport.go`'s `importExportFor` resolved a `Backend` to `ImportExporter`, the *union* of `backend.ImportBackend` and `backend.ExportBackend`, via one assertion against `backend.ImportExportBackend`; `XKMSService.ImportKey`, `GetImportParameters`, `WrapKey` and `UnwrapKey` (`pkg/xkms/servicer_key.go`), the package-level embedded API (`pkg/xkms/service.go`), `TenantScopedBackend` (`pkg/xkms/backend_tenant.go`) and the PIV key generator (`pkg/xkms/piv_keygen_backend.go`) all resolved through it, so a genuinely import-only backend failed the union check and lost the import half it did support — reachable over REST and gRPC only because those two transports separately reimplemented the narrower assertion themselves, bypassing the service (and its tenant scoping) in the process. `importExportFor`/`ImportExporter` are replaced with two capability interfaces (`keyImporter`, `keyExporter`) and two resolvers (`importBackendFor`, `exportBackendFor`), each asserting one direction; every call site now resolves only the direction the operation actually uses (`WrapKey`/`UnwrapKey` resolve import, since both are half of the import ceremony; `CopyKey` resolves its source as export and its destination as import). `TenantScopedBackend` gained `importer()`/`exporter()` accessors in place of one `importExporter()`, so a tenant-scoped view of a single-direction backend offers exactly that direction, scoped, instead of refusing both.
  - REST's `GetImportParametersHandler`, `WrapKeyHandler`, `UnwrapKeyHandler` and `ImportKeyHandler`, and gRPC's `GetImportParameters`, `WrapKey`, `UnwrapKey` and `ImportKey`, are now thin adapters over `XKMSService`, the same conversion `GenerateKey` received in #1214 — their local `types.KeyAttributes`-building switches, `types.KeyAttributes.Validate()` calls and (REST's `resolveImportBackend`, gRPC's `importBackend`) capability-resolution helpers are deleted, since the service now does all three itself with per-direction capability resolution. MCP's `handleWrapKey`/`handleUnwrapKey` are converted the same way (`handleGetImportParameters`/`handleImportKeyMaterial` already called the service). The "service drops fields" rationale that had kept `WrapKey`/`UnwrapKey` transport-local was checked against the current code rather than assumed: `transport.WrapKeyRequest`/`Response` and `UnwrapKeyRequest`/`Response` already carry `KeySpec`, `Metadata`, `ImportToken` and `WrappingPublicKey`, so it was stale and no transport field had to be added. Wire shapes are unchanged on every transport.
  - Converting gRPC's `ImportKey` surfaced and fixed a real drift from the service's own symmetric-key validation: the RPC's hand-rolled switch refused `key_size: 0` for a symmetric import, while the service's `unwrapSymmetricAlgorithms` table has always defaulted a zero size to AES-256-GCM, matching REST, MCP and the embedded transport.
  - A backend-layer capability or policy sentinel (`backend.ErrKeyNotExportable`, `backend.ErrImportNotSupported`, `backend.ErrExportNotSupported`, `backend.ErrAsymmetricKeyExportNotAllowed`) can now reach a transport's error mapper wrapped in the service's own `xkms.ErrOperationWrap` rather than only ever arriving bare from a direct backend call; each transport's `mapKeyOpError` was extended (gRPC and MCP consult `apierrors.ImportExportSentinelClasses` as a fallback tier; REST's own `keyOpSentinelStatus` table gained the same four sentinels) so the classification, and the wire status code, is unchanged by which path a given error takes.
