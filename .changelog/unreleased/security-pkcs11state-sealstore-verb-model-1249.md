- **BREAKING: `PKCS11State*`/`SealStore*` permission names changed on gRPC and MCP; `EnableUser`/`DisableUser` permission names changed on all three transports and REST's enable/disable route shape changed.** go-xkms#1249's audit of the "single verb/api model" ruling found two families gated on different, internally-consistent permission models across transports. The PKCS#11 remote-state and platform-sealed-store families: REST's `/api/v1/pkcs11state/*` and `/api/v1/platform/secrets*` routes already carried per-verb CRUD actions (`keys:create`/`get`/`list`/`update`/`delete`), while gRPC's seven `PKCS11State*` RPCs and all six `SealStore*` RPCs (plus MCP's `sealStore.*` methods) collapsed every mutation to a coarse `keys:write` and every read to `keys:read`. Every transport now carries the identical per-verb action: `Put`/`PutIfAbsent`/`SealStorePut` → `keys:create`, `CAS`/`SealStoreReseal` → `keys:update` (a compare-and-swap and a reseal-in-place are both mutations of an existing record, not the creation of a new one), `CAD`/`Delete`/`SealStoreDelete` → `keys:delete`, `Get`/`SealStoreGet`/`SealStoreStatus` → `keys:get`, `List`/`SealStoreList` → `keys:list`. A role granted only `keys:create`/`keys:delete`/`keys:get`/`keys:list` can no longer reach the PKCS#11-state or seal-store CAS/reseal routes over gRPC or MCP (it needs `keys:update` too, same as REST already required); a role granted only `keys:write`/`keys:read` on gRPC or MCP for these operations must be re-granted the per-verb equivalents. REST's own routes are unchanged.
  User enable/disable: gRPC's `EnableUser`/`DisableUser` RPCs and MCP's `user.enable`/`user.disable` methods required the coarse `users:update`, and REST served both directions from a single `PUT /api/v1/users/{username}` route with an `{"enabled": bool}` body — which could also only carry `users:update`, since the static permission gate runs before the body is decoded and so cannot see which direction a request means. All three transports now require go-qrdb's own `users:enable`/`users:disable` (`permission.UsersEnable`/`UsersDisable`): REST serves `POST /api/v1/users/{username}/enable` and `.../disable` as their own routes (no body), matching gRPC and MCP exactly. `PUT /api/v1/users/{username}` is gone entirely — it had no purpose beyond the enable/disable toggle, and pre-release carries no compat shim. A role granted only `users:update` can no longer enable or disable a user on any transport; it needs `users:enable`/`users:disable`.
  - Retired the xkms-minted `keys:read`/`keys:write` permission names entirely (`pkg/apimodule/module_scopes.go`'s `selfScopedPermissions`): nothing gates on them anymore now that the PKCS#11-state and seal-store families use qrdb's own per-verb `keys:*` actions, which qrdb already declares tenancy scope for. `keys:update` remains xkms-owned (qrdb's `keys:*` vocabulary has no `update` member) and keeps its `ScopeSelf` declaration.
  - `pkg/api/authz_consistency_test`'s cross-transport golden gained seven `pkcs11state.*` entries (one per RPC/route) and `users.enable`/`users.disable` entries covering all three transports, and dropped the `pkcs11state.*` and `users.update` carve-outs it used to allowlist.
  - `sdk/ts/src/clients/users.ts`: `update(username, {enabled})` replaced by `enable(username)`/`disable(username)`; `UpdateUserRequest` removed from `sdk/ts/src/types/users.ts` (nothing else used it). `web/app/src/views/UsersView.svelte`'s toggle button now calls `users.enable`/`users.disable` directly and gates on `can("users","enable")`/`can("users","disable")` instead of `can("users","update")`. `xkmsctl user update` (`cmd/xkmsctl/user.go`) is unchanged at the CLI surface — it already went through the SDK's `EnableUser`/`DisableUser` transport methods, not a raw HTTP call, so only its doc comment needed updating.
- **BREAKING: `POST /api/v1/passwords/access-mode` now requires `passwords:write` on REST, closing the last #1249 exception.** The owner ruled (2026-09-29) that the password vault is not a login feature, so this route drops its `RouteAuthSession` tier (any authenticated caller, no RBAC check) and joins its `passwords:*` siblings on the qrdb-native coarse read/write model gRPC's `PasswordStoreSetAccessMode` and MCP's `password.setAccessMode` already required — the passwords family is deliberately coarse (qrdb declares no per-verb CRUD for it), so `passwords:write` is the correct grant, not a new per-verb action. A caller without `passwords:write` who previously could still change the access-control strategy over REST alone now gets the same `403` gRPC and MCP already gave. No SDK or web-app change was needed: neither `sdk/ts` nor `web/app`/`xkey` gate a `can("passwords", ...)` UI control on this route (there is no such call site in either app), and `xkey`'s CLI/GUI already called this operation through the gRPC/Unix transport clients, which already required `passwords:write`.
