- **The xkey authenticator's hmac-secret extension returned the derived secret in plaintext and refused every conformant platform.** `xkey/pkg/authenticator` read plaintext `salt1`/`salt2` string keys from the getAssertion extension input and wrote `HMAC(credentialKey, salt)` unencrypted into the signed authenticator data, so the secret a platform uses as a disk or vault key was readable by anything observing the CTAP transport. Chrome's PRF, libfido2, systemd-cryptenroll and this repository's own `pkg/fido2` `DeriveSecret` all send the CTAP 2.1 §12.5 integer-keyed input and were refused with `ErrGetAssertionHMACSecretInvalidSalt`. The extension also ran with `up=false`, and one secret served both the user-verified and unverified cases. The spec-shaped `ProcessHMACSecretExtension` was never called, and it could not have worked: it ran ECDH against a fresh ephemeral key the platform never saw. Protocol 2 was also wrong in two places. It keyed AES with the HMAC key, and it padded with PKCS#7. The whole implementation is replaced by one code path, `processHMACSecret` (`ext_hmac_secret.go`), implementing §12.5 exactly. It takes keyAgreement (1), saltEnc (2), saltAuth (3) and an optional pinUvAuthProtocol (4, default 1). It agrees the shared secret with the key `getKeyAgreement` issued, through the clientPin code's own ECDH and kdf: the new `agreeSharedSecret`, factored out of `deriveSharedSecret` so the extension leaves the clientPin session's active protocol and keys untouched. It verifies saltAuth in constant time and returns `CTAP2_ERR_PIN_AUTH_INVALID` on a mismatch. It requires the salts to decrypt to exactly 32 or 64 bytes and returns `CTAP1_ERR_INVALID_PARAMETER` otherwise. It returns `encrypt(shared secret, HMAC-SHA-256(CredRandom, salt1) [|| … salt2])`. An hmac-secret request whose assertion does not collect user presence is refused with `CTAP2_ERR_UNSUPPORTED_OPTION`, as §12.5 requires. CredRandomWithUV and CredRandomWithoutUV are derived from the credential's stored 32-byte secret by HKDF-Expand-SHA-256 under distinct labels and selected by the assertion's UV bit. The storage format does not change. A credential with no secret gets no output, per §12.5. Extensions are now processed before `signCount` is incremented, so a refused input does not spend a counter value. A new shared `decryptData` is the protocol's `decrypt`, and `decryptPIN`/`decryptBlock` now delegate to it. The new `ErrUnsupportedOption` maps to `CTAP2_ERR_UNSUPPORTED_OPTION`. Verified by `xkey/pkg/authenticator/ext_hmac_secret_test.go`, which drives the authenticator with `pkg/fido2` over an in-memory CTAPHID loopback. It covers `DeriveSecret` with one and two salts, protocols 1 and 2 with and without UV (outputs differ by UV state, match across protocols and are stable), and ciphertext that never contains the output. It also covers each refusal (bad or truncated saltAuth, 16/48-byte and non-block-aligned salts, plaintext `salt1`, a missing keyAgreement, protocol 3, `up=false`), with `signCount` left unchanged. go-xkms#1146.
