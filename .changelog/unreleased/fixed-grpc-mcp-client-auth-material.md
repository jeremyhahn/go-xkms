- **The gRPC and MCP client transports now carry the authentication material a caller configures, and xkey can present an mTLS client credential to xkmsd.** The gRPC transport ignored a caller-built `tls.Config` (`transport.WithTLSConfig`, which `sdk/go`'s `WithTLS` and xkey use), so a CA bundle supplied in memory was never the trust anchor and every TLS connection fell back to the system pool; it now uses the given configuration (TLS 1.3 minimum). Neither gRPC nor MCP sent `transport.WithJWTToken`: gRPC now presents it as `authorization: Bearer` per-RPC metadata (TLS only -- a bearer token never crosses plaintext, so a token on a plaintext `grpc://` connection is refused at dial), MCP as an `Authorization` header. xkey reads `XKMSD_TLS_CERT` / `XKMSD_TLS_KEY` for an mTLS client credential, which the unified server's gRPC and MCP transports require for module calls. Found by the OIDC credentials integration suite driving xkey over every transport. Tests: `pkg/api/transport/grpc/transport_bearer_test.go`, `pkg/mcptool/client_bearer_test.go`, `xkey/cmd/xkey/cmd/xkmsd_client_test.go`.
