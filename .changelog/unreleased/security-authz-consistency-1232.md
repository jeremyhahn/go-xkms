- **REST's `/keys/wrap` and `/keys/unwrap` required the wrong permission, and `internal/authzscan` did not cover REST, `pkg/acme/admin`, or MCP's own permission table, so nothing would have caught it.** `pkg/api/rest/routes.go` gated `POST /api/v1/keys/wrap`/`unwrap` on `keys:encrypt`/`keys:decrypt` while the identical operation — the same request fields, same underlying `XKMSService.WrapKey`/`UnwrapKey` call — required `keys:wrap`/`keys:unwrap` on gRPC's `WrapKey`/`UnwrapKey` RPCs and MCP's `xkms.wrapKey`/`xkms.unwrapKey` methods (the by-id variants, `/keys/wrap-by-id`/`unwrap-by-id`, already used the correct pair). A caller granted only `keys:wrap` could not reach the plain route; a caller granted only `keys:encrypt` could reach a wrap operation gRPC and MCP both gate more narrowly. Both routes now carry `auth.ActionWrap`/`auth.ActionUnwrap`. Two of the same routes also carried the raw string literals `"derive"`, `"wrap"`, `"unwrap"` instead of `auth.ActionDerive`/`ActionWrap`/`ActionUnwrap` — a retyped literal is a silent authorization change, since it stops matching the qrdb grant with no compile error — with no test that would have caught it.
  - `internal/authzscan.Seam` gained `Bare` (match a plain identifier call, not just a method selector — REST's route-table helpers are local closures) and `LabelArgs`/`LabelPrefix` (key a `Site` by a call's own literal arguments, e.g. the HTTP method and path, instead of the enclosing function name — REST and `pkg/acme/admin` each register dozens of gates from a single function). A new `internal/authzscan.ScanMap` resolves a `map[string]T{"key": {resource, action}}` composite literal the same way `Scan` resolves a call's arguments, for MCP's `methodPermissions`, which is data rather than a sequence of gate calls.
  - New wire-contract goldens: `pkg/api/rest/authz_golden_test.go` (174 routes), `pkg/acme/admin/authz_golden_test.go` (51 `gate.Wrap` registrations), `pkg/api/mcp/authz_golden_test.go` (165 `methodPermissions` entries, reusing the package's existing `goldenMethodPermissions` table so the value-comparison and the literal-rejection tests cannot drift apart). Each fails if a gate is added, removed, repointed, or spelled as a literal — verified by temporarily reintroducing the literal and by deleting a gate, both while writing this fix.
  - New cross-transport consistency golden, `pkg/api/authz_consistency_test` (`TestCapabilities_RequireSamePermissionOnEveryTransport`): re-derives gRPC's, REST's, and MCP's tables from their own source and asserts every capability in a hand-built, audited 157-entry table requires the identical `resource:action` pair on every transport that exposes it. Two further mismatches the audit found are allowlisted (excluded from the checked table) pending a product decision, not fixed here: `POST /api/v1/passwords/access-mode` is REST session-only with no RBAC permission where gRPC/MCP require `passwords:write`; the `PKCS11State*`/`pkcs11state/*` family uses REST per-verb CRUD actions where gRPC collapses to a coarser write/read tiering. Both are two internally-consistent but different design choices, not a wrong-table typo.
