- **A negative `page` or `page_size` query parameter, or a page far enough past it to overflow int arithmetic, panicked a list handler instead of returning an error; the metrics server was also missing three of the four HTTP timeouts every other internal listener carries.** `ApplyPagination` checked `PageRequest.IsUnpaginated` (`Page==0`) before calling `Normalize`, which clamps a negative `Page` to zero — the same value `IsUnpaginated` treats as "return everything." A `Page` of `-1` was not zero when checked, fell through to `Normalize`, came out as zero, and `start := (Page-1)*PageSize` went negative; `items[start:end]` then panicked the handler's goroutine. A `page_size` large enough that `(Page-1)*PageSize` itself overflowed `int` reached the same panic from the other direction.
  - `PageRequestFromQuery` now rejects a negative `page` or `page_size` at parse time with `*InvalidPaginationParamError`/`ErrNegativePaginationValue`, so REST's existing `page`-parse-error handling returns 400 instead of the request ever reaching `ApplyPagination`. A new `transport.ValidatePageRequest` gives the MCP JSON-RPC handlers (`handleListBackends`, `handleListKeys`, `handleListCerts`), which decode a `PageRequest` from JSON params rather than a query string, the identical rejection as `ErrCodeInvalidParams`.
  - A new exported `transport.MaxPageSize` (1000, matching the existing `pkg/xkms` audit-query cap) bounds `PageRequest.Normalize`'s `PageSize`: an oversized `page_size` is capped, not rejected, so "as many as possible" still gets an answer. `ApplyPagination` itself now clamps a still-negative `Page` to the first page after `Normalize` and checks its `(Page-1)*PageSize` and `start+PageSize` arithmetic for overflow before indexing, so a `PageRequest` built programmatically (every servicer construct one via `ListOption`, bypassing HTTP query validation entirely) can no longer panic it either. `PageRequest.ToDAOPageQuery`'s unpaginated branch is untouched and its literal explained in place: it has no production caller today, and capping it would silently truncate a future "give me everything" DAO query instead of erroring.
  - The metrics server (`pkg/server/server.go`, `startMetrics`) set only `ReadHeaderTimeout`, leaving `ReadTimeout`, `WriteTimeout` and `IdleTimeout` unbounded — a slow-body request or an idle connection was not mitigated even though a slow-header one was. A new `server.ApplyHardenedTimeouts` helper (with exported `Hardened{ReadHeader,Read,Write,Idle}Timeout` constants matching the values the ACME listener already used) is now shared by both the metrics server and `cmd/xkmsd/acme.go`'s dedicated ACME HTTPS listener, instead of each hand-copying the same four-field literal.
