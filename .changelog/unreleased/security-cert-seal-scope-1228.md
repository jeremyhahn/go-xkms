- **High: one tenant could read, overwrite, list and delete another tenant's certificates and the platform's, and seal and unseal under another tenant's keys, on every transport.** REST's certificate handlers (`SaveCertHandler` through `GetTLSCertificateHandler`, `pkg/api/rest/handlers.go`) called the unscoped backend; gRPC's (`SaveCert` through `GetCertChain`, `pkg/api/grpc/service.go`) called whichever backend the registry listed first, unscoped; MCP's (`handleSaveCert` through `handleGetCertChain`, `pkg/api/mcp/handlers.go`) called the unscoped default keystore. A cross-tenant test confirmed the leaks before the fix. A tenant could name the platform's unprefixed certificate on all three transports, or tenant B's namespace (`tenant-b/web`) on gRPC, on MCP and in REST's save, and read, overwrite or delete that certificate. Listing returned every tenant's certificates. REST's `GetTLSCertificate` resolved the key by common name across tenants: it returned the platform's bundle, and its answer revealed whether another tenant's key existed. gRPC's and MCP's `GetTLSCertificate` were already scoped. REST and gRPC `Seal` and `Unseal` resolved `key_id` over the unscoped backend, so a tenant holding tenant B's blob and the name of B's key recovered the plaintext, and could seal under B's key or the platform's. `XKMSService.Seal` used one untenanted default sealing key for every caller, so any caller of the service could unseal any other tenant's default-key blob. Every transport is now a thin adapter over the `XKMSService` certificate and seal methods. Those methods resolve the backend through the caller's tenant (`resolveTenantBackend`): the certificate methods with a request struct, and Seal and Unseal, take the tenant from `TenantID`, which each transport fills from the identity; the rest read `scopedTenantIDFromContext`. Another tenant's certificate or key is exactly as absent as a missing one, with the same status and body. A key ID containing `/` is refused as malformed. `TenantScopedBackend.Seal` and `Unseal` now stamp the tenant on the sealing key's attributes, which makes the default sealing key per tenant through the existing mechanism: the same deterministic `xkms-sealing-key-<type>` name, generated on first use in the caller's tenant, with no new config, storage or migration. A tenant-scoped caller is refused on TPM 2.0 (`ErrBackendUnsupported` carrying `ErrSealingNotSupported` and the new `ErrSealNotTenantBound`), because a TPM-sealed blob is not bound to any key and unseals for whoever presents it. Platform-scoped TPM sealing is unchanged. Wire changes: REST, gRPC and MCP now seal and unseal without `key_id` on key-based backends (previously they failed with no default key); `GetTLSCertificate` reads the leaf and chain from the certificate store without loading the private key, and `chain_pem` omits the leaf when the stored chain opens with it; REST `ListCerts` fills the certificate details; gRPC certificate RPCs use the default backend and report `Unavailable` with no service; a missing certificate is `404`/`NotFound`/Not found; a malformed PEM or certificate (`ErrInvalidEncodingPEM`, the new `ErrInvalidCertificate`) and an unparseable key ID (`ErrKeyIDParse`) are `400`/`InvalidArgument`/Invalid params on every transport; an unknown seal backend is `404`/`NotFound`; MCP's seal `key not found: <id>` is now `keystore: key not found`. `XKMSService.ListCertificates` honours its list options. The per-instance `XKMSService.SealWithBackend`/`UnsealWithBackend`, gRPC's `parseCertFromPEM`/`encodeCertToPEM`, and MCP's `certOperationError`, `getCertError` and `operationBackend` are deleted.
