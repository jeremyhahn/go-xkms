- **The `fido2` auth factor accepted an assertion that only proved user presence, and never checked the clientData `origin`** (#1289). `Verify` checked `authenticatorData`'s user-present flag but not its user-verified flag, and no enrollment recorded either a user-verification requirement or an expected origin, so `Verify` had nothing to check `clientDataJSON.origin` against. An assertion produced with a PIN/biometric bypass, or against a spoofed page that relayed a genuine authenticator's touch, still verified.
  - `Enroll` now records both at enrollment time: `"origins"` (a string or `[]string` MethodParam, defaulting to `["https://" + rp_id]`) and `"require_user_verification"` (a bool MethodParam, defaulting to **true** — the WebAuthn/CTAP2 best practice for a factor used to unseal or authenticate). `Challenge` carries both into `MethodData` (`origins` as `[]string`, `require_uv` as `bool`) alongside the existing enrolled key and rp id.
  - `Verify` now refuses when the enrollment requires verification and `authenticatorData`'s user-verified flag is clear, and refuses when `clientDataJSON.origin` is not exactly one of the enrolled origins — checked with go-webauthn's own `protocol.IsOriginInHaystack` comparator rather than a re-implemented string match. An enrollment missing either field (for example, one recorded before this change) leaves the corresponding `MethodData` key unset; `Verify` treats that the same as any other incomplete challenge and refuses — go-xkms is pre-release and carries no compatibility path for such enrollments.
  - The FIDO2 CTAP2 local enrollment ceremony (`LocalCeremony.Enroll`, used at init/administrator enrollment) now records the same origin (`"https://" + rp_id`) and user-verification requirement it actually presented to the authenticator, rather than relying on `Factor.Enroll`'s defaults to happen to agree.
