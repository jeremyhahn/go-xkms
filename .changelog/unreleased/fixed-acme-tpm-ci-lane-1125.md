- **`test/integration/acme-tpm` and the runnable part of `test/integration/challenges` now have Makefile targets and run under `make integration-test` / the nightly job** (#1125). Neither had a target before, so `make integration-test` and the nightly workflow never built or ran them — the device-attest-01, enroll-01 and permanent-identifier ACME+TPM end-to-end tests, and the enroll01/endorse01 challenge-framework tests, were silently dark.
  - `integration-test-acme-tpm` brings up a dedicated swtpm plus an xkmsd instance with its embedded ACME server enabled (`test/integration/acme-tpm/config.acme-tpm.yaml`, `challenges.enroll01`/`endorse01`) and runs the suite (`-tags='integration,tpm2,codec_cbor,codec_json,codec_msgpack,gms_pure_go'`) against both. `test/integration/acme-tpm/certgen` generates the ACME listener's throwaway TLS cert with the Go stdlib rather than shelling out to `openssl`, which the runtime image does not carry.
  - `integration-test-challenges` runs `test/integration/challenges/{enroll01,endorse01}` (`-tags=integration`) against the same acme-server config; `dns01` and `http01` are excluded on purpose — they are their own multi-service E2E stacks that still build against the pre-merge `go-trusted-ca` sibling checkout, tracked separately from this issue.
  - Both targets are added to the `integration-test` aggregate, so the nightly workflow (`.github/workflows/nightly.yml`, which invokes `make integration-test` wholesale) now exercises them with no workflow YAML change needed.
  - `config.acme-tpm.yaml` uses `storage.backend: "file"`, not `"qrdb"`: `"qrdb"` flips on the embedded qrdb node's own barrier, which for `barrier.strategy: "passphrase"` never auto-unseals at construction (only `"none"` and a provisioned `"tpm2"` do) and blocks boot behind a pre-boot sealed-window listener that `pkg/server/sealed_window.go` refuses to open on a non-loopback `server.host` — nothing in this repository drives that ceremony unattended today, `configs/xkmsd-integration.yaml`'s own `KNOWN GAP (go-xkms#653)` comment included. `test/integration/api/config.test.yaml` is the proven fixture this now matches: `storage.backend: "file"` never constructs the embedded qrdb node at all, so the daemon boots and serves with the barrier simply left sealed-but-inert, which this lane's ACME/software-keystore path never touches. One consequence: `protocols.rest/grpc/quic/mcp` are all off (only `"qrdb"` storage may serve network protocols per `Config.Validate`'s `NetworkServing` check) — harmless here since the ACME listener is its own dedicated `net.Listener`, independent of `protocols.*`.
  - Files: `test/integration/acme-tpm/{docker-compose.yml,config.acme-tpm.yaml,certgen/main.go}`, `test/integration/challenges/docker-compose.yml`, `Makefile`.
  - Verified statically: `make -n integration-test-acme-tpm`/`integration-test-challenges`, `docker compose -f <file> config`, `go vet -tags=... ./test/integration/acme-tpm/... ./test/integration/challenges/{enroll01,endorse01}/...`, and — the strongest check available without docker — a local `pkg/config` test loading `config.acme-tpm.yaml` through the real `config.Load` + `(*Config).Validate` + `(*Config).ComplianceGaps`, which returns no error and no gaps. The owning session's first real docker run caught the qrdb/sealed-window failure this entry fixes; the lane still deserves a close first run for anything a static check cannot see (e.g. whether `challenges.enroll01`/`endorse01: true` is sufficient for the device-attest-01 tests specifically — `cmd/xkmsd/acme.go`'s challenge map only registers `enroll-01`/`endorse-01` verifiers, no separate `device-attest-01` entry).
