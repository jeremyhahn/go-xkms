- **The Encrypt RPC now refuses a reused AEAD nonce (#1201).** REST, gRPC and MCP all passed a caller-chosen nonce straight to the backends. The only reuse check was the provider's `AEADSafetyTracker`, and it did not hold: its check and record are separate steps, it ignores any key not generated in the current process, and it keys by key id, so one key under two names escaped it. An encrypt-only principal could therefore reuse a victim's nonce with chosen plaintext, recover the keystream, and forge tags. `XKMSService.Encrypt` now claims every AES-GCM and ChaCha20-Poly1305 nonce in the process-wide guard the AES-GCM wrap already used, now named `aead.SharedAEADNonceGuard` (formerly `SharedGCMNonceGuard`). The claim and the record are one atomic step. A caller-supplied nonce is claimed before the seal. A generated nonce is claimed after it, so it cannot be replayed. The key identity is the key material where the backend releases it and the store-qualified key id otherwise, and it comes from one helper, `aeadKeyIdentity`, shared with wrap. A reuse is refused with an error wrapping `aead.ErrNonceReuse` and no ciphertext is returned. The paired-phone backend's `Raw` now also reports `backend.ErrNotSupported` like every other sealed backend. PKCS#11 `C_EncryptInit` caller IVs still encrypt once and are refused on reuse. **Limit:** the guard is per-process memory. It does not survive a restart and is not shared between cluster nodes; persistence awaits an owner ruling on #1201.
