- **The LUKS passphrase, the SO PIN guarding TPM certificate storage, and key material unwrapped by the TPM2 backend no longer cross the TPM bus in plaintext.** Three callers drive go-tpm on their own transport and so were missed by the #1147 session hardening. `pkg/luks.TPMSealer` sent the passphrase in the clear in the `TPM2_Create` sensitive area, and received it in the clear from `TPM2_Unseal`. `pkg/storage/hardware.TPM2CertStorage` authorized `TPM2_NV_DefineSpace`, `TPM2_NV_Write`, `TPM2_NV_Read` and `TPM2_NV_UndefineSpace` with a `TPM_RS_PW` password session, which carries the owner hierarchy authorization (the SO PIN) verbatim. `pkg/backend/tpm2.Backend.UnwrapKey` received the recovered key material in the clear from `TPM2_Unseal`. Each now uses `pkg/tpm2`'s session layer through three new transport-level entry points. `HierarchyAuthSession` proves a hierarchy auth through a salted HMAC session bound to the hierarchy. `CommandEncryptionSession` and `ResponseEncryptionSession` attach a salted session that encrypts the first command or response parameter. All three salt against an ephemeral NULL-hierarchy key and never touch the EK or any SRK. The LUKS sealing parent (the SSRK, pending #917) and its PCR policy are unchanged. A salt key the TPM refuses to flush no longer fails the session it salted. Its error is now returned by the session's closer rather than only logged. Verified by bus-capture tests on the TPM simulator for each path, using the recorder, now shared as `pkg/tpm2/tpm2test/tpmbus`. These tests assert that the secret appears in no command or response, that the operation still succeeds, and that the protecting session is salted. A wrong SO PIN is refused with `TPM_RC_BAD_AUTH`. Documented in `docs/tpm2/engineering.md` §"Bus protection" and `docs/luks/` (go-xkms#1164).
