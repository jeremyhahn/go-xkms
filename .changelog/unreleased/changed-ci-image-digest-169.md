CI: a new `ci-images` job hands the toolchain and integration images to the nine jobs that use them (ruling 169, the go-qrdb #1135 pattern). On a push to main it publishes them from the release runner with that runner's `RELEASE_REGISTRY*` credential (ruling 173). On other events, consumers pull main's image by digest when main published the same content hash, and otherwise build it locally with no push. Before this change, every job built its own image (17.5 min per PR). Each pulled image is held until the job's teardown; the reaper also removes stale registry-named CI images and keeps held ones; `internal/buildgates/ci_image_digest_test.go` enforces the handoff. The lookup speaks the registry API with curl, on the forge's own scheme from `github.server_url`, so a plain-HTTP forge registry is read over HTTP and any other registry over verified HTTPS. Main publishes under the forge's public `agent-ci-images/` namespace, since only its owner or an admin can write a user namespace (#1730). Every read is anonymous: the lookup answers the registry's Bearer challenge with no credential (OCI Distribution Spec v1.1.1 "Pulling manifests"; Distribution token authentication), and consumers `docker pull` the digest with no login and no `buildx imagetools`. An empty resolve comes with one warning naming the case: not published, refused (401/403), no answer, or an unexpected reply. The publish log shows the login, lookup, push and digest, and warns when `RELEASE_REGISTRY` is not the forge's registry host that pull requests read.
CI: on the forge, the resolve takes an anonymous pull token from the forge's `/v2/token` (service `container_registry`, Distribution token authentication "Requesting a Token") and reads the digest from a `HEAD` of the manifest's `Docker-Content-Digest` ("Checking if content exists in the registry"), with the token handed to curl on a pipe, never in its arguments or the log. `ci.yml`'s workflow env names the namespace as `CI_REGISTRY_OWNER` (`agent-ci-images` on the forge), and the digest gate pins it (ruling 217).
CI: only the forge's public namespace is read anonymously. A GHCR package is private when published, so every read step again hands `scripts/ci-registry.sh` the run's token: a GHCR resolve answers the registry's challenge with it and a GHCR `use` logs in with it before `docker pull` (a refused login warns and reads anonymously; a step with half the token fails naming the missing half). The digest gate requires the token on every read step and keeps it off the forge (ruling 217).
