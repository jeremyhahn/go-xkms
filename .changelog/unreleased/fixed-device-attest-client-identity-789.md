- **The `DeviceAttest` client sent its IP address as the order identifier, which the attested-identity check of #828 refuses** (#789, #1370 review). The order now names the device's own identity: `TPMModule` gains `DeviceIdentity` (the IAK certificate's RFC 4043 `permanentIdentifier`), read by the new exported `deviceattest01.DeviceIdentityFromCertificate`, the rule the server applies to the evidence (the `dice` form is the lowercase-hex `Ueid`). `sdk/go/acme` aliases it, with `ACMEAttestedKey`, `ACMEDeviceAttestObject`, the identity sentinel errors and the attestation formats. The simulator IAK certificate (`tpm2test.ProvisionIAKCertificate`) now carries a `permanentIdentifier`.
  - **Finalize binds the key of the device the request names.** The binding no longer depends on the order's first identifier (a `dns` identifier ahead of a `permanent-identifier` skipped it), and with several devices in one order it selects the attestation record of the `permanentIdentifier` the CSR names rather than the first recorded.
  - A TCG-CSR-IDEVID or endorse-01 finalize request for an order a `device-attest-01` challenge validated is refused (`badCSR`); it carries keys nothing attested and used to skip the key binding. A device identity that happens to decode as a public key is no longer taken for an endorse-01 order.
  - An `ip` identifier is declined (`rejectedIdentifier`) when no non-attestation challenge with a registered verifier remains, instead of being offered `device-attest-01` or failing with a 500.
  - A TPM leaf with two `permanentIdentifier` otherNames is refused as ambiguous.
  - The dial this client's identity would have broken is gone: see `security-device-attest-01-client-posts-attestation-737-789.md`.
