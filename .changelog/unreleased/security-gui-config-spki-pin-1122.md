- **The xkey GUI silently disabled TLS certificate pinning (and reset the FIDO2 firmware version) on every settings save.** `services.GUIConfigData` (`xkey/pkg/gui/services/app_service.go:81`), the DTO the Settings screen reads and writes through `AppService.GetConfig`/`UpdateConfig`, had no field for `GUIConfig.ServerSPKIPin` (the hex SPKI pin that lets a first-contact connection trust a server without a CA certificate) or `GUIConfig.FIDO2FirmwareVersion`. The `ConfigUpdater` callback wired in `NewApp` (`xkey/pkg/gui/app.go:2401`) persisted every save by rebuilding a whole new `GUIConfig` from that DTO alone (`dataToConfig`), so any settings change — theme, window size, anything — zeroed both fields in memory and on disk, silently disabling certificate pinning. `dataToConfig` is now `applyDataToConfig` (`app.go:281`): it merges the DTO onto a **copy of the existing** `GUIConfig` instead of rebuilding one, so a field the DTO does not carry is always preserved from the pre-existing config. Neither field gained a Settings UI control — `ServerSPKIPin` is set only via the `gui.server_spki_pin` CLI flag/env or by editing `gui.json` directly, and `FIDO2FirmwareVersion` only once at startup from the build version string — so no new editable surface was added. `TestConfigDataRoundTrip` (`xkey/pkg/gui/config_data_roundtrip_test.go`) walks every exported `GUIConfig` field via reflection and fails the build if a future field is added without either a DTO mapping or a documented entry in `unmappedGUIConfigDataFields`; `TestApplyDataToConfig_PreservesUnrelatedSettingsSave` proves the SPKI pin and firmware version survive an unrelated settings save both in memory and in the file `SaveGUIConfig` writes (go-xkms#1122).
