- **`xkey`'s device-selection helpers stopped silently taking the first match when a paired-device name was ambiguous** (#1315). `#1307` gave `pkg/pairing` a refusing `FindPairedDeviceByName` (returns `ErrDeviceNameAmbiguous` for more than one match, `(nil, nil)` for no match) and wired it into `device listen`, but `cmd/xkey/cmd/device.go`'s own `findDeviceByName` -- the lookup every other device command goes through, directly or via `selectDevice` -- still returned the first record sharing a name, deciding by list order (which an attacker choosing when their device pairs controls) which pinned key a command trusted. `findDeviceByName` now delegates to `pairing.FindPairedDeviceByName` and returns `(*PairedDevice, error)`, wrapping the pairing package's error in the CLI's own `ErrDeviceNameAmbiguous` sentinel (promoted out of `device_listen.go`, which duplicated it, into `device.go` so it is available to every command regardless of its own build tag); `selectDevice` (the name-or-default helper `device attest`, `backup to-device`/`from-device`, `device enroll-phone`, `piv phone-list`/`phone-push-cert`/`phone-pull-cert`/`phone-generate`, `oath sync`/`push`/`pull`, and `device share`/`import` all resolve a device through) propagates the same error instead of swallowing it. None of the affected commands register an `--address` flag, so there is no by-address escape hatch to point operators at; the error message names the count and says to re-pair or remove the duplicate.
