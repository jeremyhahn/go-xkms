# secure-analyzer allowlist (go-xkms#549, re-keyed by go-xkms#607)
#
# Every non-comment line is one exempted finding, in the form:
#
#   <repo-relative path><TAB><rule><TAB><symbol><TAB><reason>
#
# scripts/secure-analyzer.sh matches a diagnostic's path + rule + symbol
# against the first three fields, VERBATIM -- not a glob, not a package, an
# exact triple. <rule> is 1, 2 or 3, matching pkg/secure/analyzer's three
# rules. <symbol> is:
#
#   rule 1 -- the forbidden import path (always "github.com/awnumar/memguard";
#             go-qrdb's analyzer bans exactly one import).
#   rule 2 -- the call expression's own source text, e.g.
#             "ssh.ParsePrivateKey(buf.Bytes())".
#   rule 3 -- "<Struct>.<Field>", e.g. "PKCS11Config.PIN".
#
# rule 1's symbol is read straight out of the diagnostic message (the
# message quotes the constant it banned); rule 2 and rule 3's are not --
# rule 2's message is the identical fixed string for every call site, and
# rule 3's never names the struct -- so both are read back out of the
# source at the diagnostic's own file:line:col by
# scripts/secure-analyzer-symbol, a go/ast-based helper built alongside the
# analyzer itself.
#
# THIS IS THE SECOND KEY SCHEME. The first (go-xkms#549) keyed on
# <path>:<line>, and an edit anywhere above an exempted line silently
# invalidated the entry by shifting the line number -- with no signal
# beyond a red Lint job on main days later. It broke twice within a week
# (fido2.go 208->207 after go-xkms#181, mock_extended.go after go-xkms#154)
# before go-xkms#607 replaced it with this one. A symbol survives everything
# that does not touch the finding itself: reformatting, adding code above
# it, renaming the file's OTHER fields. It stops matching only when the
# finding's own shape changes -- the call is rewritten, the field is
# renamed, the struct is renamed, or the field is fixed -- which is exactly
# when the exemption SHOULD stop matching.
#
# One consequence of keying on the call expression's source text rather
# than its line: multiple call sites in the same file that are textually
# identical (same receiver, same arguments) collapse onto the same key. See
# pkg/ssh/keys/signer.go below -- three call sites, one entry -- which is
# correct here because the three call sites really are the same shape for
# the same reason (see that entry's reason). A file whose sites differ in
# any way (different variable, different argument) still gets one entry per
# distinct call text.
#
# This file is not a baseline. Rules 1 and 2 (raw memguard import,
# ssh.ParsePrivateKey) are absolute everywhere except the two classes below;
# nothing here is a general suppression of either rule, and a new violation
# of any other shape fails the gate the same as it would with an empty file.
#
# Two exemption classes:
#
# 1. go-truststrap#60 (rule 1) -- go-truststrap v0.4.0-alpha's p256proto
#    functions (NewStaticKey, EncodeStaticKey, DecodeStaticKey) take a
#    *memguard.LockedBuffer directly. go-qrdb's secure.Buffer wraps its
#    LockedBuffer in an unexported field with no accessor -- correctly,
#    since exposing it would hand back the handle the boundary exists to
#    withhold -- so a caller of those three functions has no way to reach
#    them without importing memguard itself. Filed upstream as
#    jeremyhahn/go-truststrap#60, with noiseproto's plain-[]byte
#    EncodeStaticKey/DecodeStaticKey cited as the shape that already works.
#    Every other memguard call in each of these files IS the SDK wrapper
#    (secure.Wipe, secure.Buffer) and is not part of the exemption; only the
#    import line is listed -- the symbol is always the banned import path
#    itself, and a file only ever imports a given path once.
#
# 2. rule-2 narrowing filed on go-qrdb (rule 2) -- pkg/ssh/keys already
#    parses only *secure.Buffer/*secure.Secret-backed bytes at every one of
#    these sites (see pkg/ssh/keys/parse.go's ParsePEM and signer.go's
#    enclaveSigner). ssh.ParsePrivateKey is called first ONLY to distinguish
#    an unencrypted key from *ssh.PassphraseMissingError, because
#    ssh.ParsePrivateKeyWithPassphrase cannot parse an unencrypted key at
#    all -- there is no other way to support both key kinds through one
#    entry point. The rule's own diagnostic asks for
#    "ParsePrivateKeyWithPassphrase on *secure.Buffer-backed bytes", and the
#    second half already holds at every site below; the narrowing needed is
#    upstream, in the rule's detection, not in this package.
#
# A third class -- pre-existing rule-3 findings -- is listed at the bottom.
# These are NOT rule-1/rule-2 exemptions and none of the reasoning above
# applies to them; see that section's own header.
