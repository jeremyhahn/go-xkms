# Static Passwords — Architecture

> **Status: NORMATIVE** · Feature: `password` · Module: `go-xkms/xkey` · Last verified: 2026-09-27

## Scope

YubiKey-style static password storage for `xkey`: the credential model and
store (`go-xkms/pkg/staticpw` in the root module, reached by xkey only
through `xkey/pkg/staticpw`'s re-export, per the SDK boundary in
`xkey/CLAUDE.md`), the CLI (`xkey password`, `xkey touch`), the virtual USB
keyboard that types passwords (`xkey/pkg/keyboard`), and the GUI's
`StaticPasswordService` (`xkey/pkg/gui/services/staticpw_service.go`),
including folder organization, KeePass/CSV/XML import, and backup/restore.

Out of scope: browser-extension autofill, which reads through this same
store but adds its own domain-matching and CTAP2-authentication policy —
see [autofill/](../autofill/). Team- and tenant-scoped password sharing
(`staticpw.TeamStore`, `TenantDAOFactory`, re-exported as
`xkms.StaticPasswordTeamStore`/`StaticPasswordTenantDAOFactory` in
`sdk/go/staticpw.go`) is server-side multi-tenant infrastructure with no
`xkey` CLI or GUI surface today; it is noted in engineering.md for
completeness but not otherwise documented here.

## Components

### Credential model and stores (`go-xkms/pkg/staticpw`, root module)

`StaticPassword` (`pkg/staticpw/types.go`) holds `Name`, `Title`, `Username`,
`Password`, `URL`, `MatchPatterns` (glob patterns consulted by the browser
extension in addition to `URL`-based matching — see
[autofill/architecture.md](../autofill/architecture.md)), `Notes`,
`FolderPath`, `ExpiresAt`, `CreatedAt`/`UpdatedAt`, and `ReadOnly` (an
entry generated by a policy, e.g. TPM, and never user-editable).

- `BackendStore` (`store.go`) is the implementation `xkey` actually uses
  (via `xkms.NewStaticPasswordStore`/`NewStaticPasswordTenantStore`,
  re-exported through `xkey/pkg/staticpw`): it persists each entry as its
  own key under any `storage.Backend`, so when that backend is the barrier
  every entry is opaque ciphertext at rest. `NewStore`, `NewTenantStore`,
  `NewSharedTenantStore`, `NewPersonalTenantStore` all build one, scoped
  differently.
- `EncryptedStore` (`encrypted_store.go`) wraps any `Store` and additionally
  encrypts the `Password` field itself with a `types.SymmetricEncrypter` —
  a second, field-level layer independent of whatever encrypts the backend
  as a whole. Values would be stored as `ENC:<base64(json(EncryptedData))>`;
  a value without that prefix predates encryption and would be refused
  (`GetDecrypted` returns `ErrPasswordNotEncrypted`, no silent plaintext
  fallback). **Not reachable from `xkey` today** — no CLI command or GUI
  service constructs one (`grep` finds zero call sites outside
  `pkg/staticpw` itself and `xkmsd`-side code out of this module's scope).
  `xkey`'s own protection of the `Password` field is whatever the
  underlying `storage.Backend` provides (the barrier's AES-256-GCM over the
  whole entry), not this field-level layer.
- `PINAccessStore` and `SessionStore` (`access.go`) wrap an `EncryptedStore`
  with the two access-control modes described below, and are likewise
  **not imported by `xkey`** (see the Rejected alternatives / engineering.md
  note): the CLI's `password unlock`/`lock`/`access-mode` verbs reach an
  access mode entirely through a remote `xkmsd` server's `transport.Client`,
  not through these types in-process. They may be what a session-owning
  `xkmsd` server uses internally, but that server lives outside this
  module's SDK boundary and is not this document's concern.

### Access modes

Two mutually exclusive decrypt-time policies, selected by
`xkey password access-mode`:

- **`pin_per_operation`** — every decrypt requires the PIN again.
- **`session_based`** — one `Unlock(pin)` grants decryption until `Lock()`.

The mode and the lock/unlock state belong to whichever `xkmsd` server holds
the session (`transport.PasswordService`); the on-disk store itself has no
notion of "locked" outside that server.

### CLI (`xkey/cmd/xkey/cmd/password.go`, `touch.go`)

The CLI treats the password store's *location* and its *session state* as
two different authorities, stated directly in the command's own `--help`
text: **the store lives with whoever holds the barrier** — the running
daemon first (queried over the local IPC socket,
`ipc.Client.StatePasswordList`/`StatePasswordStore`), the on-disk store
directory otherwise (`add`, `get`, `remove`, and the disk fallback of
`list`/`status` all open a plain `BackendStore` directly via
`openPasswordStore`). **A remote `xkmsd` server owns the session verbs** —
`unlock`, `lock`, `access-mode` — and is consulted for `status` only with
`--source xkmsd`. `--xkmsd-url` selects that server; it is unrelated to
where the store's data lives.

`list`/`status` accept `--source auto|daemon|disk` (`status` additionally
accepts `xkmsd`) via the same `stateSource` mechanism `xkey barrier status`
uses — see [seal/architecture.md](../seal/architecture.md). Password
*values* are never returned over the daemon IPC socket
(`ErrPasswordValuesNotOverIPC`): `--show-passwords` requires `--source
disk`, because the daemon socket's only authentication is filesystem
permission, reachable by every process running as the same user.

`xkey password type` and `xkey touch` connect to the running `xkey fido2`
daemon over the same local IPC socket and ask it to type a password through
the virtual USB HID keyboard (`xkey/pkg/keyboard`) — see
[autofill/architecture.md](../autofill/architecture.md) for the daemon's
IPC protocol, which this feature shares (`touch`, `type_password` message
types).

### GUI (`xkey/pkg/gui/services/staticpw_service.go`)

`StaticPasswordService` is the frontend-facing surface: CRUD, folder
management (`ListFolders`, `CreateFolder`, `MoveToFolder`, `RenameFolder`,
`DeleteFolder`), search, backup/restore to an encrypted file, and KeePass
KDBX / CSV / XML import (`xkey/pkg/pwimport`) — **GUI-only**, no CLI
verb calls `pwimport`. It also drives the session verbs
(`Unlock`/`Lock`/`GetStoreStatus`/`SetAccessMode`) through the same
`transport.Client` the CLI's session verbs use, plus `TryAutoUnlock` for
barrier PCR-policy auto-unseal at GUI startup.

## Data flow: adding a password with autofill metadata

1. `xkey password add --name ... --password ... --url ...` (or the GUI
   equivalent) builds a `StaticPassword` with `Title`/`Username`/`URL`/
   `MatchPatterns` populated.
2. `StaticPassword.Validate()` checks required fields.
3. `store.Add` persists it through the resolved backend (barrier-encrypted
   when a barrier is unsealed).
4. Later, the browser extension's `AutoFillService.SearchCredentials`
   matches page domains against `URL`/`MatchPatterns` via
   `xkms.AutoFillMatchesEntry` — see [autofill/architecture.md](../autofill/architecture.md).

## Rejected alternatives

- **Having the CLI's session verbs (`unlock`/`lock`/`access-mode`) call
  `staticpw.PINAccessStore`/`SessionStore` in-process**, the way the legacy
  documentation described. Access mode and lock state are properties of a
  running `xkmsd` session server (`transport.PasswordService`), not of a
  one-shot CLI process with no session to hold open — an in-process
  `SessionStore.Unlock` would unlock nothing anyone else could observe. The
  CLI instead always talks to the server that owns the session.
- **Returning password values over the daemon IPC socket for
  `password list --show-passwords`.** The socket's authentication is
  filesystem permission only (mode `0600`, but shared by every process
  running as the same user); a verb that hands out plaintext there widens
  the exposure past what the on-disk store's own permissions already limit.
  `--source disk` is required instead, so the value only ever leaves the
  process that already has filesystem access to the store.
